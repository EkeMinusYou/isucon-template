# データベースのロック保持時間と競合範囲を短縮する

## 概要

予約、在庫、残高、カウンタ、クォータのように、同じ正本データを複数リクエストが同時に更新する処理では、ロックの保持時間とロック対象の範囲がスループットを決める。ロック待ち時間は、別のトランザクションがロックを保持している時間の影響を受けるため、単に `FOR UPDATE` を削除するのではなく、正しさを保つクリティカルセクションを小さくする。

基本形は次のとおりである。

1. 入力の解析、変更されない条件の検証、候補の絞り込みをトランザクションの外で行う。
2. 最終的な競合チェックと正本行のロックを、コミットまでの短いトランザクションにまとめる。
3. ロック中はメモリ上の小さな判定と必要な `UPDATE`・`INSERT` だけを行い、直ちにコミットする。
4. 外部 API、ファイル I/O、大きなレスポンス生成、重い計算はコミット後へ移す。永続的なイベントが必要なら、イベント行だけを同じ短いトランザクションへ含める。

ロック保持時間の短縮と、ロックされる行・インデックス範囲の縮小は別の改善である。適切な索引、明示的なリソース行、全経路で統一したロック順を組み合わせることで、競合の連鎖とデッドロックも抑えられる。

## 適用条件・制約

- 同時実行時にも一つの正本を基準に、在庫が負にならない、同じ席を二重予約しない、残高を二重に消費しない、といった不変条件を守る必要がある処理を対象にする。単なる読み取りには、ロックを追加するのではなく通常の一貫性読み取りを検討する。
- 最終チェックと、それに基づく更新は同じトランザクション内に置く。トランザクション外で空き状況を確認しただけでは、確認直後に別のリクエストが状態を変更できるため、正しさの根拠にしてはならない。
- ロックを取った後の処理をトランザクション外へ移す場合、外へ出した処理が失敗したときの意味を定義する。外部通知や非同期処理の取りこぼしを許容できない場合は、通知対象を outbox 行として正本の更新と同じトランザクションで記録する。
- MySQL/InnoDB では、`SELECT ... FOR UPDATE` や更新文が探索したインデックスレコードにロックを取る。範囲検索や非ユニークな索引では、レコードだけでなく gap/next-key lock が競合範囲を広げることがある。ユニークキーによる完全一致の対象行など、意図した粒度で検索できる索引を設計する。
- 分離レベルを `READ COMMITTED` へ変更すると、MySQL/InnoDB では検索時の gap lock などの挙動が変わるが、ファントム行を防ぐ要件や再読み取りの意味も変わる。分離レベル変更を一般的な高速化スイッチとして扱わず、対象処理の不変条件と DB・バージョンの仕様を確認する。
- 予約や在庫を「予約済み行が存在しない」ことで表現している場合、存在しない行そのものを正確にロックすることは難しい。空き席・在庫枠・スロットのような明示的なリソース行を用意し、そこを正本のロック対象にする設計が候補になる。ただし、行の生成・削除・再初期化、容量、複数ホストからの所有権を一緒に設計する。
- 複数行・複数テーブルを更新する経路は、すべての呼び出し元で同じキー順・テーブル順にロックする。デッドロックを完全に排除できない場合、ロールバックされたトランザクション全体を新しいトランザクションで再実行できるよう、処理を冪等にする。
- `NOWAIT` は競合時に即時失敗し、`SKIP LOCKED` はロック中の行を結果から除外する。後者は結果の一貫性を変えるため、キューのワーカーなど「別の行を処理してよい」処理に限定し、予約・残高の最終判定へ無条件に使ってはならない。構文と利用可能なバージョンも確認する。
- キャッシュ、オンメモリ状態、read model はロック対象を減らす補助にはなるが、同時更新の正本を置き換えるとは限らない。再起動、複数アプリホスト、鮮度、認証・認可、復旧時の再構築を満たさない限り、正本の代わりに使ってはならない。
- SQL ドライバによって `RowsAffected` の扱い、トランザクションの自動コミット、タイムアウト、エラー分類が異なる。デッドロック・ロック待ちタイムアウト・業務上の在庫切れを同じ成功条件として扱わない。

## 探索方法

1. `docs/official/` のアプリケーション仕様と当日マニュアルから、同時実行時に守る不変条件、成功・失敗レスポンス、更新の可視性、許される遅延や非同期化を確認する。仕様で正しさが要求される部分を、ロック削減のためにキャッシュや事前判定へ移してはならない。
2. トランザクションの入口と境界を探す。`Begin`、`BeginTx`、`BeginTxx`、`START TRANSACTION`、`COMMIT`、`ROLLBACK` を検索し、HTTP ハンドラからサービス・リポジトリ・ORM 呼び出しまでの経路をたどる。トランザクション開始、最初のロック文、最後の更新、コミットの間に、外部通信・ファイル操作・大きな読み取り・重い計算が挟まっていれば、保持時間を延ばす候補である。
3. ロックを発生させる SQL を列挙する。`FOR UPDATE`、`FOR SHARE`、`NOWAIT`、`SKIP LOCKED`、`UPDATE`、`DELETE`、upsert、外部キーや一意制約に関わる `INSERT` を、通常の `SELECT` と分けて読む。読み取り結果を後続の更新のために保護しているのか、単にレスポンスを作るだけなのかを呼び出し側で確認する。
4. ロック対象の表現を確認する。`id = ?` のような一意行、`IN` で列挙した複数行、時間・状態の範囲、`NOT IN` や `IS NULL` による「存在しない候補」のどれに該当するかを分類する。業務上は一つの席だけを取りたいのに、SQL は同じイベントの予約範囲全体を探索している、といった粒度のずれがあれば、明示的なリソース行または候補を絞った後の最終ロックが適用候補になる。
5. スキーマの正本と SQL の探索条件を照合する。`CREATE TABLE`、`PRIMARY KEY`、`UNIQUE KEY`、`KEY`、マイグレーションを確認し、必要なら `SHOW CREATE TABLE`、`SHOW INDEX`、`EXPLAIN` で、ロック文の `WHERE`・結合条件・順序に対応する索引があるかを見る。非ユニークな広い索引、先頭列が合わない複合索引、関数適用や `OR` で索引を使えない条件は、保持時間と競合範囲の両方を広げる可能性がある。
6. 複数の入口が同じ正本を更新する場合、各経路が触るテーブル・行の順序を並べる。A が `parent` → `child`、B が `child` → `parent` の順にロックしていないか、同じキー集合を異なる順序で更新していないか、失敗時に同じ操作を安全に再実行できるかを確認する。
7. 変更対象を、(a) トランザクションの開始を遅らせる、(b) ロック対象を明示的な行へ変える、(c) ロック検索を一意・狭い索引へ合わせる、(d) ロック順と再試行単位をそろえる、のいずれか一つの境界へ分ける。インデックス追加、キャッシュ、非同期化を同時に適用する前に、それぞれの正本と整合性の責務を分離する。

予約枠や在庫の更新を例にすると、仕様の上限、ハンドラのtransaction境界、`FOR UPDATE`の対象、
schemaの主キーを一つの経路として対応づける。これは現行アプリへ無条件に変更を適用する指示ではない。

## 実装方法

### トランザクションを正しさが必要な区間へ縮める

ロックを取らない処理を先に済ませ、正本を再確認する直前にトランザクションを開始する。候補を外で取得できる場合でも、候補がまだ有効かどうかはロック後に再確認する。

```text
parse and validate immutable request data
resolve candidate IDs without locking

begin transaction
lock the authoritative row(s) in a stable order
recheck mutable state
apply the smallest atomic update
insert an outbox record if a durable event is required
commit immediately

build the response and call external services after commit
```

トランザクション中に、HTTP/RPC、決済、メール、ファイル I/O、bcrypt、全件の JSON 化、無関係な一覧取得を置かない。コミット後の処理が正本の状態とずれる場合は、正本更新と outbox 記録を同じトランザクションに置き、配信側で再実行できるようにする。

### 条件付き更新で単一行の競合区間を減らす

単一の在庫・カウンタなら、値を読み出してから更新する代わりに、条件を `UPDATE` へ含めて一つの原子的な変更にできる場合がある。次は説明用の MySQL/InnoDB の SQL であり、テーブル名・列名・不足時のエラーへ対象アプリの仕様を置き換える。

```sql
START TRANSACTION;

UPDATE inventory
SET remaining = remaining - ?
WHERE item_id = ?
  AND remaining >= ?;

-- The application checks that exactly the intended row changed.
COMMIT;
```

この形でも、対象行が存在すること、`item_id` で適切に絞れること、更新件数の意味がドライバと DB の設定に合うことを確認する。更新後に別テーブルへ整合性上必要な行を追加するなら、その処理とコミットまでを同じ短いトランザクションに残す。

### 「空き」を明示的な正本行にする

空き席や空き枠を「予約レコードがない」ことで表現すると、空きレコード自体を `FOR UPDATE` で一点ロックできない。競合の単位が席・枠・リソースなら、次のような行を初期化時またはリソース生成時に用意し、その行の状態・残数を正本にする。

```sql
CREATE TABLE resource_slots (
  resource_id BIGINT NOT NULL,
  slot_id BIGINT NOT NULL,
  remaining INT NOT NULL,
  PRIMARY KEY (resource_id, slot_id)
) ENGINE = InnoDB;
```

複数枠を扱う場合は、リクエスト内の `(resource_id, slot_id)` をアプリケーションで正規化し、全経路で同じ順番にロックする。ロック後は残数を再確認して更新し、空きがなければロールバックする。空き行の事前生成は、初期化・削除・容量変更・再起動後の復元を含めて正本のライフサイクルへ組み込む。

### 候補の絞り込みと最終ロックを分ける

候補検索が広い場合は、通常の読み取りで候補 ID を絞り、トランザクション内では候補行だけを一意キーまたは狭い複合キーでロックする。候補検索と最終更新の間に状態が変わるため、ロック後の再検証を省略してはならない。

```sql
START TRANSACTION;

SELECT resource_id, slot_id, remaining
FROM resource_slots
WHERE resource_id = ?
  AND slot_id IN (?, ?, ?)
ORDER BY resource_id, slot_id
FOR UPDATE;

-- Recheck capacity and update only the selected rows.
UPDATE resource_slots
SET remaining = remaining - ?
WHERE resource_id = ?
  AND slot_id = ?;

COMMIT;
```

`NOT IN` のサブクエリに `FOR UPDATE` を付けて利用済み行を除外する設計は、DB の分離レベル・索引・存在しないキーの扱いによって広い範囲をロックし得る。空き行を正本にできない場合は、対象 DB のロック仕様を踏まえ、最終更新を一意な条件付き DML にするなど、競合範囲を明示できる別の表現へ置き換える。

### 索引とロック順を正本へ合わせる

ロック文の検索条件には、等価条件・結合キー・状態や時間の範囲を反映した最小限の索引を用意する。索引定義は稼働中の DB へ手で追加するのではなく、対象プロジェクトの初期化 DDL またはマイグレーションの正本へ記録する。索引を追加すれば必ず速くなるわけではなく、書き込み時の索引維持コストと、範囲ロックの変化も含めて対象 SQL の意味を保つ。

複数行を更新する処理は、キーを同じ順序で処理する。異なる経路が逆順に同じ行をロックし得る場合は、順序を共通化するか、競合単位を一行のカウンタやキューへ再設計する。デッドロックが発生し得る設計では、DB がロールバックしたトランザクションを新しいトランザクションで最初から再試行し、外部副作用をトランザクション内で重複実行しない。

### `NOWAIT`、`SKIP LOCKED`、分離レベルは意味を確認して使う

処理がキューから任意の一件を取るワーカーで、別の行へ進めることが正しいなら、対象 DB が提供する `SKIP LOCKED` を候補にできる。反対に、予約・残高・一意性のように「指定した対象を確保できたか」を返す処理では、行を飛ばすことで成功・失敗の意味が変わるため、単なる待ち時間削減として使ってはならない。

分離レベルの変更や `NOWAIT` も、ロック待ちを短くする代わりにエラーや可視性の契約を変える。対象 DB のバージョン、トランザクション単位、リトライ方針、実サービスが期待するレスポンスを満たす範囲に限定する。
