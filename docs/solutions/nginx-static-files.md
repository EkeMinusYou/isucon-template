# 静的データをファイル化してnginxから配信する

## 概要

DB、外部ストレージ、アプリケーションの生成処理などにある画像・添付ファイル・生成済みコンテンツを、リクエストの
たびにAPIが読み出してレスポンスするのではなく、ファイルストレージへ展開し、nginxから直接配信する実装パターンを示す。

元データの正本はその保存場所（DB、外部ストレージ、生成物管理など）に残し、ファイル本体の読み出し・シリアライズ・
APIプロセスのレスポンス処理を配信経路から外す。CSS、JavaScript、画像、生成済みHTMLなど、リクエストごとの業務処理が
不要なデータに適用できる。

nginxが元データの保存先へ直接アクセスするわけでもない。API、同期処理、ビルド処理などが元データをファイルとして
保存し、クライアントにはファイルのURLを返す。

## 適用条件・制約

- 配信する内容が公開データ、またはファイル配信前に認可を完了できるデータであること。リクエストごとに内容を生成・
  変換するデータは、APIや専用の配信処理に残す。
- 元データの識別子とファイルの対応を一意に決める。ユーザーが送ったファイル名やパスをそのままファイルシステムの
  パスに使わず、ID・検証済みの拡張子・content hashなどから生成する。
- メタデータだけが存在する状態や、元データから参照されるファイルが存在しない状態を、公開URLから見せない。新規
  データの公開順序、更新時の新旧ファイル、削除時の参照停止を定義する。
- 更新されないファイルには、content hashや世代を含むURLを使うと長いキャッシュ期間を設定しやすい。上書きする同一URLを
  使う場合は、Cache-Control、ETag、Last-Modified、更新後の可視性をそろえる。
- 複数のアプリ・nginxホストから配信する場合は、すべての配信ホストが同じファイルを参照できるようにする。共有ファイル
  システム、オブジェクトストレージ、専用ファイルホスト、所有ホストへのルーティングとreverse proxyなどを選ぶ。
  プロセスやホストのローカルディスクだけに保存する場合は、リクエストが別ホストへ送られたときの扱いを決める。
- 認証が必要なファイルを公開用のnginx locationに置かない。認可をAPIで行い、nginxにはファイル本体だけを送らせる構成が
  必要なら、`X-Accel-Redirect` などの内部リダイレクト機構を使い、公開URLから直接到達できないlocationを用意する。
- `root` と `alias` の対応、親ディレクトリの権限、MIME type、ディレクトリ一覧の無効化、シンボリックリンクの扱いを確認
  する。ファイル保存先をHTTPのパスとして無制限に公開しない。

## 探索方法

1. 元データの保存場所と取得経路から、BLOB・大きな本文・画像・添付ファイル・base64値・生成済みレスポンスなどを探す。
   DBのスキーマや読み取りSQL、外部ストレージのclient、アプリ側の`[]byte`、`base64`、`Content-Type`、
   `Content-Disposition`、`send_file`、`ServeFile`、`io.Copy`、レスポンスへのファイル埋め込みを検索する。
2. ファイル本体を返すAPIと、ファイルを作成・更新・削除する全経路を追う。所有者、公開範囲、認可、更新時刻、削除後の
   可視性を、DBのメタデータとアプリケーションの処理から整理する。
3. nginxの`location`、`root`、`alias`、`try_files`、`proxy_pass`と、アプリが静的ファイルや画像を返すルートを対応づける。
   同じURLがAPIへproxyされる経路と、ファイルを直接返せる経路を分ける。
4. ファイルを保存するホスト、nginxが配信するホスト、ロードバランサーの振り分けを確認する。複数ホストでローカルファイル
   が分散している場合は、共有ストレージ、専用配信ホスト、所有ホストの識別子を含むURL、reverse proxyのいずれが成立するかを
   判断する。
5. URLの安定性とキャッシュ方針を確認する。内容が不変なら hash・世代付きのURL、更新されるなら失効・置換・fallbackを
   実装できるかを確認する。

## 実装方法

### 元データをファイルとして公開する

元データの正本（DB、外部ストレージ、生成処理など）からファイル本体を取り出し、アプリまたは専用の保存処理で
ファイルストレージへ保存する。保存先の例は次のとおり。

```text
/var/lib/app-assets/<kind>/<content-hash>.<validated-extension>
```

ユーザー入力のファイル名をそのまま使わず、MIME typeと拡張子の対応を許可リストで管理する。元データのメタデータには、
ファイルID、保存先の論理キー、サイズ、MIME type、content hash、公開状態を保持する。

新規ファイルは一時パスへ書き込み、完成したファイルを確定パスへ移してから、公開URLとメタデータの対応を利用可能にする。
更新では同じファイルを上書きせず、新しい世代のパスを作ってメタデータを切り替えると、配信中の古い内容と新しい内容が
混ざりにくい。不要になった旧ファイルの削除は、参照がなくなったことを確認してから行う。

### APIとnginxの責務を分ける

公開データの場合、APIはファイル本体を返さず、メタデータと配信URLを返す。nginxにはファイル保存先だけを割り当てる。

```nginx
location /assets/ {
    alias /var/lib/app-assets/;
    autoindex off;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

この例は、URLの`/assets/`と保存先の対応を表す概念例である。実際の`alias`、ファイル権限、キャッシュ期間、MIME typeは
対象の保存レイアウトと更新規則に合わせる。更新で同じURLを再利用する場合は、`immutable`を付けず、失効やvalidatorを
設計する。

非公開データでは、APIで認証・認可と公開可否を決めた後、nginxの`internal` locationへ`X-Accel-Redirect`で委譲する方法が
ある。この場合も、クライアントからファイル保存先の実パスへ直接アクセスできないようにする。

### 複数ホストで配信する

複数のnginxホストへ同じファイルを配る方法は、データの更新頻度、容量、可用性、競技中に許される構成から選ぶ。

- 共有ファイルシステムやオブジェクトストレージを各配信ホストから参照する。
- 専用のファイルホストへ保存し、各nginxからreverse proxyする。
- ファイルを所有ホストへ保存し、URLに所有ホストやシャードを表す情報を含めて、そのホストへルーティングする。
- 各ホストへ複製し、更新・削除・再起動後の同期を管理する。

どの方式でも、アップロード直後にどのホストから見えるか、ファイルがないときにAPIへfallbackするか、所有ホストが停止した
ときの応答を仕様に合わせる。nginxが元データの保存先を参照して別ホストを探す構成にはせず、配信先をURLまたはnginxの設定で解決できる形にする。
