# Goのバージョンを上げる

## 概要

Goのビルド用ツールチェーンを更新し、新しいコンパイラ・ランタイム・標準ライブラリを組み込んだ
アプリケーションを作るパターン。コンパイラの最適化や、メモリ割り当て・GC・標準ライブラリの
実装改善によって、同じ処理のCPU時間や資源消費を減らせる可能性がある。

具体例として、[Go 1.24のリリースノート](https://go.dev/doc/go1.24#runtime)にはmap実装や
メモリアロケータの変更が記載されている。これはそのリリースの事実であり、どの更新でも高速化する
という一般則ではない。対象コード、更新前後のバージョン、実行環境によって効果は異なり、
DBのクエリ数や外部サービスの待ち時間は更新だけでは減らない。

更新の対象はバイナリを生成するGoである。実行サーバーのGoだけを更新しても、既存バイナリに
新しいランタイムは反映されない。ソースから新しいツールチェーンで再生成する必要がある。
互換性保証もソースを対象としている。[Goの互換性方針](https://go.dev/doc/go1compat)

## 適用条件・制約

- アプリケーションをソースから再生成でき、更新先が対象OS・CPUをサポートしていること。
  cgoを使う場合は、対象向けCコンパイラと実行先の共有ライブラリも整合させる。
  cgo必須の依存を含む構成へ、`CGO_ENABLED=0`を無条件に適用しない。
- ツールチェーンの更新と`go.mod`の`go`行の変更を分けて考える。`go`行は言語バージョンを指定し、
  Go 1.21以降では最低要求バージョンとしても強制される。`toolchain`行は推奨ツールチェーンであり、
  厳密なバージョン固定ではない。[Go Toolchains](https://go.dev/doc/toolchain)
- Go 1の互換性には、未規定の挙動・バグへの依存、`unsafe`、セキュリティ修正などの例外がある。
  古い依存ライブラリがランタイム内部へ依存する場合は、更新に必要な修正も対象になる。
  新しいGoでコンパイルできるだけでは、APIの振る舞いが維持されたとは限らない。
- 言語バージョンを上げる場合は、例えば[Go 1.22のループ変数の変更](https://go.dev/doc/go1.22#language)を確認する。
  ランタイム・標準ライブラリにも、[Go 1.23のTimerの変更](https://go.dev/doc/go1.23#timer-changes)のように
  メインモジュールの`go`行で有効化される変更がある。更新区間のリリースノートと`GODEBUG`設定を確認する。
- ツールチェーンの自動取得を利用する場合はビルド環境から取得できることが必要。
  取得できない環境では、利用するGoを事前に用意する。サービス起動時のダウンロードに依存させない。
- 認証認可、レスポンス、初期化、永続性を維持する。[`docs/official/`](../official/)の当日マニュアルで、
  追試として再起動後の動作と書き込み済みデータの取得が要求されていないかを確認する。
  複数ホストでは、各サービスが起動する成果物とビルド入力の対応を保つ。

## 探索方法

1. `go.mod`、`go.work`、Taskfile、Dockerfile、CI設定、バージョン管理ツールの設定を探す。
   `go`・`toolchain`行、`GOTOOLCHAIN`、`GOROOT`、`PATH`、`golang:`、`go-version`、`go build`を検索し、
   ソースから成果物、サービスの起動先までを追う。古いGoで実際に生成している経路が更新候補になる。
2. 対象モジュールのディレクトリで`go version`、`go env GOTOOLCHAIN GOWORK GOOS GOARCH CGO_ENABLED`を確認する。
   これらはGo 1.21以降の例であり、自動選択による取得が起こる場合がある。
   既存成果物は`go version -m <binary-path>`で確認できる。`<binary-path>`は実際の配布物へ置き換える。
   シェルのGoと成果物のGoが異なる場合は、成果物を生成した経路を優先して追う。
3. 保存済みprofileの`runtime.mallocgc`、GC、map操作、標準ライブラリの処理と、更新区間の
   リリースノートを照合する。頻出処理に関係する改善があれば、更新によって減る仕事の仮説を立てられる。
   リクエスト時間の大半がDB待ちである状況などでは、Go更新だけでその待ちが減るとは説明できない。
4. `unsafe`、`go:linkname`、`import "C"`、ビルドタグ、タイマー、ループ内のクロージャ、`GODEBUG`を探す。
   更新先で変更された機能への依存があれば、互換性修正の対象を特定する。

入口は、`task setup-webapp`で取得したアプリの`go.mod`と、[Taskfile.yml](../../Taskfile.yml)の
`build`、`build-pgo`、`GO_BUILD_ENV`である。`go.mod`の`go 1.18`だけでは、実際のビルド用Goが
1.18とは判断できない。collectorなどは別モジュールなので、アプリの`go.mod`変更だけでは更新されない。

## 実装方法

1. 更新前の指定と実際のビルド用Goを把握し、候補リリースの改善内容・互換性・対象OSの条件を根拠に
   更新先を具体的なパッチバージョンまで決める。既存のビルド設定を正本として記録し、暗黙の`latest`へ任せない。
2. ビルド用Goを明示する。Go 1.21以降のランチャーでは`GOTOOLCHAIN=go1.N.P`で具体的なバージョンを指定できる。
   古いランチャーでは、ビルド環境の既存のGo導入方法を使って更新する。
   `GOTOOLCHAIN=local`はPATHで選ばれたGoに同梱のツールチェーンを使う指定であり、それ単体ではバージョン固定にならない。
3. 新しい言語機能や依存の最低要求に合わせる必要がある場合に`go.mod`の`go`行を更新する。
   `go.work`がある場合は各モジュールとの要求を整合させる。依存ライブラリは互換性修正に必要な範囲で変更し、
   `go.sum`の変更理由も対応させる。[ツールチェーン選択の仕様](https://go.dev/doc/toolchain)
4. 選択したGoと既存ソースから、対象OS・CPU用の成果物を生成し、既存の配布経路がその成果物を参照する形にする。
   バージョン更新だけではソースのタイムスタンプが変わらないため、ビルドの省略条件やキャッシュキーにも
   ツールチェーンの変更を反映する。

以下は、このリポジトリのTaskfileへ翻訳する場合の設定例。`go1.N.P`は構文を示すプレースホルダーであり、
選択した実在するリリースへ必ず置き換える。`TARGET_OS`・`TARGET_ARCH`は実ホストで確認した値を使う。

```yaml
vars:
  GO_TOOLCHAIN: go1.N.P
  GO_BUILD_ENV: GOTOOLCHAIN={{.GO_TOOLCHAIN}} CGO_ENABLED=0 GOOS={{.TARGET_OS}} GOARCH={{.TARGET_ARCH}}
```

この例では`GO_BUILD_ENV`を共有するアプリとcollectorへ指定が及ぶ。ホスト上で動かすローカルツールの
ビルドは別経路なので、必要な対象にだけ同じ指定を反映する。Goはローカルで選択し、既存の
`task build`・`task deploy-*`につながる構成を使う。サーバー上での手動ビルドや生成物の直接編集を追加しない。
PGOも利用する場合は、同じツールチェーン指定を`build-pgo`へ通し、プロファイルの扱いは
[PGOの実装パターン](pgo.md)を参照する。
