# ユーザーIDによるデータベース水平分割

## 概要

同一テーブルの行を所有者キー（ユーザーIDなど）で複数のデータベースホストへ分け、1リクエストの
読み書きが1ホストで完結するようにする実装パターンを示す。単一DBのCPU・ディスクI/O・ロック競合・
接続数が律速で、かつアプリケーションホストに余剰資源がある場合に、書き込みを含めて分散できる。

読み取り専用レプリカとは異なり、書き込みも分散する。テーブル単位で配置先を分ける垂直分割とも
異なり、同じテーブルを行で分けるため、特定テーブルへの集中が解消できる。1ホストあたりのテーブル
サイズ、バッファプールに載せるべき作業集合、初期データのロード量も分割数に応じて減る。

代わりに、所有者からホストを決めるルーティング層、分割済み初期データの生成と検証、所有者をまたぐ
処理の扱い、採番の衝突回避が新しい実装対象になる。これらを設計できない場合、このパターンは
正当性を壊す。

## 適用条件・制約

### 分割軸と所有者キー

次の条件をすべて満たす所有者キーが必要である。

- リクエストを処理する前に、パス・セッション・ヘッダ・リクエストボディのいずれかから確定できる
- 対象テーブルの各行が、ちょうど1つの所有者に属する
- 所有者の分布が偏らず、分割数で割った結果が均等に近い

| 分割軸の候補 | 向いている構造 | 主な制約 |
| --- | --- | --- |
| ユーザーID | ユーザーが自分のデータだけを読み書きするAPI | ログイン前・登録時は所有者が未確定 |
| テナントID・組織ID | テナント内で完結する業務データ | テナントごとの規模差が偏りになる |
| 親エンティティID（部屋、出品、機器など） | 親に紐づく履歴・明細が支配的なテーブル | 親をまたぐ一覧・検索が残りやすい |
| 地域・カテゴリなど属性値 | 属性で読み書きが分かれる構造 | 値の追加・偏り・再配置が難しい |

所有者列の命名が規約化されている場合（`users.id` と `user_*.user_id` のように）は判別が容易だが、
それはスキーマごとの性質であり一般則ではない。外部キー、JOIN条件、WHERE句から実際の所有関係を
確認する。

### 所有者をまたぐ処理

所有者をまたぐ読み書きは、分割後は複数ホストへの問い合わせか、専用の集約先が必要になる。
次のいずれかに当てはまる処理を列挙し、件数と頻度を確認する。

- 全体ランキング、全件集計、管理画面の一覧・検索
- 所有者を指定しない更新（マスタ更新、一括処理）
- 複数の所有者を1つのトランザクションで更新する処理

これらが主要導線の大半を占める場合、分割の効果は出ない。頻度が低く、かつ結果の鮮度要件が緩い
場合だけ、全ホストへの並行問い合わせとマージ、または集約専用ホストで扱う。分散トランザクションは
実装量と失敗時の復旧が競技時間に見合わないため、所有者をまたぐ原子的更新が仕様上必要な場合は
このパターンを適用しない。

### 一意性と採番

分割すると、テーブル単位のグローバルな一意性がDBだけでは保証できなくなる。次を確認する。

- `AUTO_INCREMENT` の採番がホストごとに独立し、同じ値が複数ホストで発行され得る
- ログイン名・メールアドレスなど所有者キー以外のユニーク制約が、ホストをまたいで検証できない
- 所有者そのものを新規作成する経路（ユーザー登録）は、作成前に配置先が決まらない

### 初期化と再起動

公式の初期化要件を満たすには、分割後も次が成立する必要がある。

- 初期化APIまたは初期化手順で、全ホストを分割済みの初期状態へ再構築できる
- 分割した初期データの行の集合が、分割前と完全に一致する（欠落も重複もない）
- マスタデータ、グローバル状態、採番状態の配置先が決まっており、再起動後も復元できる
- 負荷走行中に書き込まれたデータを、追試や検証で取得できる

### 適用できない条件

- 単一DBが律速であることを計測で確認できていない
- 所有者を決められないリクエストが主要導線に含まれ、転送もできない
- 所有者をまたぐ原子的更新や、強い一貫性を要する全体集計が仕様上必要
- 分割先に割り当てるホスト資源がない、またはアプリと同居させるとCPUが不足する

## 探索方法

1. [`docs/official/`](../official/) の資料から、初期化の要件、整合性チェックの内容、全体集計や
   管理機能の仕様、失格条件を確認する。所有者をまたぐ参照が仕様上必須かどうかをここで確定する。
2. 計測結果から、単一DBが律速であることを確認する。DBホストのCPU使用率、ディスクI/O、ロック待ち、
   スロークエリ、接続数を、アプリホストの余剰資源と同じ時間窓で比較する。DBが飽和していない場合、
   分割は複雑さだけを増やす。
3. スキーマから所有者列の候補を探す。`CREATE TABLE` の列名、外部キー制約、`user_id`・`tenant_id`・
   `owner_id` のような列、および所有者テーブル自身の主キーを列挙する。各テーブルを「所有者付き」
   「マスタ」「グローバル状態」に分類する。
4. アプリの全SQLを列挙し、WHERE句に所有者列が含まれるかを確認する。含まれないクエリ、複数所有者を
   またぐJOIN、所有者を指定しない集計が、クロスシャード処理の候補になる。`JOIN`、`GROUP BY`、
   `ORDER BY` + `LIMIT`、`COUNT(*)` が手掛かりになる。
5. ルーティング可能性を確認する。HTTPハンドラの登録箇所から、所有者IDがパスパラメータ、セッション
   取得関数、リクエストボディのどこで決まるかを追う。ボディを読まないと決まらない経路、ログイン前の
   経路、所有者を新規作成する経路を個別に列挙する。
6. 採番と一意制約を確認する。`AUTO_INCREMENT`、`LAST_INSERT_ID`、UUID生成、`UNIQUE` 制約、
   採番専用テーブルを検索する。
7. 初期データの形式を確認する。ダンプがどの形式か（拡張INSERT、TSV、個別INSERT）、各行から所有者を
   取り出せるか、データ量はどれだけかを確認する。

## 実装方法

### ルーティングの位置

所有者からホストを決める位置には次の選択肢があり、所有者が確定するタイミングで選ぶ。

| 位置 | 仕組み | 向いている条件 | 制約 |
| --- | --- | --- | --- |
| リバースプロキシ | パス中の所有者IDでupstreamを振り分ける | 所有者がURLに現れる | ボディやセッションを見る経路は振り分けられない |
| アプリの接続先選択 | 全アプリが全DBへ接続し、所有者から接続先を選ぶ | アプリが同型で、DBだけ分けたい | アプリ・DB間の接続数が分割数倍になる |
| アプリ間転送 | 受けたアプリが所有者のノードへリクエストを転送する | 所有者がボディやセッションでしか決まらない | 転送分のレイテンシと再シリアライズが増える |

プロキシで振り分ける場合、nginx 単体では剰余を計算できない。所有者IDの末尾桁を正規表現で取り出す
分割（分割数が10の約数のときだけ均等）か、`map` による範囲指定に限られる。アプリ側の分割関数と
同じ結果になることを確認してから採用する。

```nginx
# Route on the last digit of the owner id. Valid only when the shard count
# divides 10; the application must use the same rule.
map $uri $owner_upstream {
    default              app_0;
    "~^/user/\d*[13579]/" app_1;
}
```

所有者が確定しない経路（ログイン、登録、ヘルスチェック）は、分割しない既定ノードへ送るか、所有者が
判明した時点で転送する。転送する場合は、読み終えたボディを再利用し、再デコードと二重読み込みを
避ける。

### 分割関数とテーブルの分類

分割関数は、アプリ、初期データ生成、デプロイ、設定のすべてが同じ定義を読むようにする。定義が
分かれると、投入したデータと参照先がずれ、整合性チェックで検出されないまま不正な応答を返す。

```go
// Owner routing keeps one request inside one node. Every component that
// places or looks up data must use this same rule.
func shardFor(ownerID int64, shards int) int {
	return int(ownerID % int64(shards))
}
```

剰余は単純で偏りが小さいが、分割数を変えると全データの再配置が必要になる。競技中に分割数を変える
可能性があるなら、初期データの分割結果を分割数ごとにキャッシュしておくと再生成の待ち時間を避け
られる。

テーブルは次のように配置する。

- 所有者付きテーブル: 所有者の属するノードにだけ行を置く
- マスタ・参照専用テーブル: 全ノードへ複製するか、参照が少なければ1ノードへ集約して問い合わせる
- グローバル状態（採番、全体設定、集約結果）: 単一ノードに置き、更新経路を1本にする

複製する場合は、更新経路が本当に存在しないこと（初期化時のみ書かれること）を確認する。更新がある
なら複製ではなく単一ノード＋問い合わせにする。

### 初期データの分割と検証

公式の初期データを、投入前に所有者ごとへ振り分ける。実装上の要点は次のとおりである。

- ダンプの構文を保ったまま行単位で振り分ける。拡張INSERTは1文に多数の行が入るため、文を分解して
  行ごとに配置先を決め、配置先ごとに文を組み直す
- 所有者列の位置は `CREATE TABLE` の列順から決める。列名でのマッチングをダンプの列順と突き合わせる
- スキーマ定義（`CREATE TABLE`、インデックス、`LOCK TABLES`）は、そのテーブルを置くノードすべてへ出力する
- マスタや所有者のないテーブルは、配置を決めた単一ノードへだけ出力する

**分割結果は必ず検証してから投入する。** 分割後の全ファイルを独立に読み直し、行の多重集合が分割前と
一致することを確認する。加法的なハッシュ（各行のハッシュの総和など順序に依存しない集計）と行数の
両方を突き合わせると、欠落・重複・順序差を区別して検出できる。検証を通らない成果物を投入すると、
整合性チェックで落ちるか、より悪い場合は検出されないまま不正なデータで走行する。

### 採番の衝突回避

分割後も一意なIDが必要な場合、次のいずれかを選ぶ。

```sql
-- Node k of n: each node issues a disjoint arithmetic sequence.
SET GLOBAL auto_increment_offset = 1;    -- 1..n, distinct per node
SET GLOBAL auto_increment_increment = 4; -- the shard count
```

- ノード別オフセット: 既存の `AUTO_INCREMENT` を活かせる。分割数を変えると設定を変える必要がある
- アプリ側生成（UUID、Snowflake形式など）: DB設定に依存しない。ID長と索引サイズが増える
- 採番専用ノード: 連番を維持できる。採番が新しい律速になり得る

所有者キー以外のユニーク制約（ログイン名など）がある場合は、その制約を検証できるノードを1つ決めるか、
制約キー自体を分割軸にした別の配置を検討する。

### 所有者をまたぐ読み取りと初期化

管理画面や全体ランキングは、全ノードへ並行問い合わせして結果をマージする。件数が多い順位付けでは、
各ノードから上位N件を取得してマージすれば全件走査を避けられる。鮮度要件が緩ければ、集約結果を
単一ノードまたはキャッシュへ書き出す方式も選べる。

初期化では、全ノードを同時に初期状態へ戻す。分割済みのスキーマとデータを各ノードへ投入し、複製した
マスタ、グローバル状態、採番状態もあわせて再構築する。一部のノードだけが初期化される状態、および
初期化前の行が残るノードを作らない。アプリ側にキャッシュや所有者テーブルの写しがある場合は、
初期化で同時に破棄する。
