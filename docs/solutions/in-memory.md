# オンメモリ化

## 概要

データベースへの繰り返しアクセスや高頻度の集計・変換を、アプリケーションのプロセス内メモリまたは
共有インメモリストアへ移す実装パターンを示す。

オンメモリ化は「すべてのテーブルを map に読み込む」ことではない。データベースを正本として残し、負荷
の高い読み取りや再計算だけを、鮮度・整合性・再起動後の復元を設計した cache または read model に置き
換える。書き込みの正しさを犠牲にして古い値を返す実装は、このパターンの適用対象にしない。

プロセス内メモリ、memcached・Redis、nginx の HTTP キャッシュ、更新時に再構築する辞書、部屋単位で所有する
リアルタイム状態などは、データの性質に応じて使い分ける。

## 適用条件・制約

### 正本とデータの分類

次のように、データの共有範囲・変更頻度・復元方法から方式を選ぶ。

| 方式 | 向いているもの | 主な制約 |
| --- | --- | --- |
| プロセス内キャッシュ | 小さいマスタ、低頻度更新のプロフィール、コンパイル済みデータ | プロセス・ホストごとに内容が分かれ、再起動で消える |
| 起動時スナップショット | 小さく、ほぼ不変な辞書・設定 | 起動時間、初期化、更新時の再ロードを管理する |
| 共有インメモリストア | 複数ホストが参照するセッション、キャッシュ、カウンタ | ネットワーク往復、容量、障害時の挙動、永続性を設計する |
| 集計済み read model | ランキング、件数、最新状態、シリアライズ済みレスポンス | 書き込みとの整合性、世代、再構築を管理する |
| 所有者付きのメモリ状態 | 部屋・接続など、所有者を固定できる一時状態 | 所有権、再接続、ホスト障害、復旧を設計する |
| HTTP/nginx キャッシュ | 静的ファイル、公開 GET、変更頻度の低いレスポンス | 認証、Cookie、レスポンスヘッダ、更新後の可視性を壊さない |

カテゴリ、キーワード、テンプレート、変更頻度の低いユーザー情報、完了済み処理の結果は候補になりやすい。
画像・動画・大きな本文をプロセス内メモリや Redis へ無制限に載せず、静的配信、ディスク、`try_files`、
`Cache-Control`、ETag などデータの大きさに合う経路を選ぶ。

在庫、座席、残高、予約枠、決済、権限、重複防止キーなど、同時実行時の一意性や原子性が必要な状態は、
表示用のキャッシュと更新時の正本処理を分ける。パスワードや秘密情報を平文でキャッシュしたり、ハッシュ
方式・コストを変えたりしない。セッションやレート制限カウンタを移す場合も、複数ホストと再起動後の扱いを
明示する。

### 鮮度・整合性・ライフサイクル

- 更新後の反映期限、read-after-write の要否、並び順、認証・認可の境界を公式仕様から確定する。
- cache key には、ユーザー、権限、テナント、言語、ページング、検索条件などレスポンスを変える条件を
  すべて含める。
- TTL だけに頼るのか、DB commit 後に明示的に失効・置換するのか、世代番号や通知を使うのかをデータごと
  に決める。DB commit より先にキャッシュを更新しない。
- 初期化、デプロイ、プロセス再起動、共有ストア障害の後でも、正本から再構築できるようにする。キャッシュ
  が空のときに正本へ fallback するか、再構築が終わるまで受け付けないかを仕様に合わせる。
- アプリの heap・GC・ロック・swap・ネットワーク転送が新しい制約になり得る。最大サイズ、eviction、所有
  範囲を説明できないデータは、オンメモリ化の対象にしない。

## 探索方法

1. [`docs/official/`](../official/) の資料から、更新後の反映期限、読み取り順序、レスポンスの完全一致、
   初期化・再起動後の復元、最終チェック、失格条件を確認する。
2. 既存の負荷上位経路と、alp・slow query・pprof などの計測結果をコードの読み取り経路へ対応づける。
   「同じマスタを毎回 SELECT する」「履歴から同じ `COUNT`・`SUM`・最新値を再計算する」「同じテンプレート
   や正規表現を何度も構築する」といった繰り返しを探す。
3. 候補の読み取り関数と、そのデータを書き換える全経路を検索する。`SELECT`、`COUNT`、`SUM`、`ORDER BY`、
   `cache`、`sync.Map`、`RWMutex`、初期化 API、削除・更新処理が手掛かりになる。
4. データがプロセス内だけで完結するのか、複数アプリホスト・複数 worker・共有ストアへまたがるのかを確認
   する。ロードバランサーの振り分けが変わっても、同じキーに正しい値を返せるかを考える。
5. 正本、キャッシュ、read model の更新順序と再構築元を図にする。更新経路をすべて列挙できない場合は、
   長い TTL やプロセス内キャッシュではなく、正本へ戻る設計を優先する。

## 実装方法

### 小さな cache-aside

最初の実装は、読み取り時にキャッシュを確認し、miss のときだけ正本から取得して成功した値を保存する
cache-aside とする。DB エラーや変換エラーを通常値として保存しない。

```go
entry, ok := cache.Load(key)
if ok && time.Now().Before(entry.ExpiresAt) {
	return clone(entry.Value), nil
}

value, err := loadFromSource(ctx, key)
if err != nil {
	return zeroValue, err
}

cache.Store(key, cacheEntry{
	Value:     clone(value),
	ExpiresAt: time.Now().Add(ttl),
})
return clone(value), nil
```

`[]byte`、slice、map、ポインタを共有する場合は、保存時・返却時にコピーするか、不変オブジェクトとして
扱う。`RWMutex`、`sync.Map`、atomic なスナップショットなどは読み取り競合とデータサイズに合わせる。同じ
キーの miss が集中する場合は singleflight、キー単位のロック、stale-while-revalidate を候補にするが、
ロック待ちや stampede を別の律速にしない。

### 集計済み read model

履歴から毎回 `COUNT`、`SUM`、最新時刻、ランキング、ステータスを計算している場合は、現在値または集計
結果を別の read model として保持できる。代表的な方式は次の二つである。

- 書き込みトランザクション内でカウンタや現在値を更新し、読み取りはその値を取得する。read-after-write
  を保ちやすい一方、書き込み競合が増える。
- 正本の更新を記録し、ワーカーや再構築処理で read model を更新する。書き込みを軽くできる一方、遅延・
  再試行・重複処理・停止時の復旧が必要になる。

どちらを選んでも、正本から再生成できる状態を保つ。0 件の集計、更新直後の値、更新失敗時の表示を別々に
定義し、単にメモリへ置いただけで正しいとはみなさない。

### TTL、失効、複数ホスト

変更がないと保証できる値は起動時ロードや長い TTL を使える。更新経路を把握できる値は、DB トランザク
ションの commit 成功後に該当キーを失効または置換する。更新経路が増える場合は、共有世代番号、失効通知、
または許容範囲の短い TTL と正本 fallback を組み合わせる。

プロセス内キャッシュを複数ホストで使う場合は、所有プロセスへ固定する、世代の変化で捨てる、共有ストア
から失効通知を受ける、短い TTL で正本へ戻る、のいずれかを明示する。部屋 ID などで状態の所有者を固定
する場合は、所有者の停止・再接続・再配置・履歴復元も実装対象に含める。

### 初期化と再起動

正本だけを初期化してキャッシュを残すと、初期化前のデータが見えたり、ホストごとに異なる結果が返ったり
する。初期化世代の更新、全キャッシュのクリア、起動時ロード失敗時の fallback、複数ホストへの反映を、
初期化 API やスクリプトの責務としてそろえる。キャッシュが消えても正本から再構築でき、再構築中の応答が
仕様上許されるかを明確にする。
