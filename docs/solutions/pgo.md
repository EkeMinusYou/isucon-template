# PGO を有効にする

## 概要

Go の CPU プロファイルをビルド時に利用し、Profile-Guided Optimization（PGO）が有効なバイナリを
作る実装パターンを示す。実際の処理頻度を反映したプロファイルを使うことで、コンパイラがよく実行
される関数のインライン化やコード配置を判断しやすくなる。

PGO はビルド時の最適化であり、実行中のバイナリへプロファイルを置くだけでは有効にならない。CPU
実行が支配的な Go アプリケーションには向くが、DB・ネットワーク・外部サービスの待ち時間やロック競合
を直接解消するものではない。

## 適用条件・制約

- プロファイルを取得したバイナリと、PGO を適用するソース・依存関係・主要な処理経路が対応している
  必要がある。大きくコードやルーティングを変えた後の古いプロファイルは、そのまま使わない。
- プロファイルは実際に頻繁に実行される API・ジョブ・バッチを含む代表的な負荷から作る。特殊な API
  だけを含むプロファイルを通常 API のバイナリへ適用すると、最適化の方向がずれる。
- PGO の対象は通常のアプリケーションバイナリである。計測用 listener やデバッグ機能を、PGO のために
  業務経路から削除してはいけない。
- `default.pgo` はビルド入力であり、実行サーバーへ配布するランタイム設定ではない。プロファイルを
  配るのではなく、プロファイルを読み込んだバイナリを配布する。
- Go のツールチェーンが使う PGO の指定方法と、対象アーキテクチャのビルド方法をそろえる。プロファイル
  取得時と配布時で、OS・アーキテクチャや重要なビルドタグが異ならないようにする。
- PGO 用のビルド経路と通常ビルド経路を残す。PGO の入力がない環境でも、同じサービスを通常バイナリで
  ビルド・起動できる構成にしておく。

このリポジトリでは、`webapp/go` が Go の main package であり、`Taskfile.yml` のローカル
Linux/amd64 クロスビルドを前提とする。`webapp/go/default.pgo` と `webapp/go/app` はそのための
ローカル生成物であり、他のリポジトリへそのまま持ち込めるファイル配置ではない。

## 探索方法

1. アプリケーションの CPU プロファイルを取得できる入口と、実際に対象経路を処理するプロセス・ホストを
   確認する。プロファイル用の listener が業務用 listener と別なら、対象を取り違えない。
2. ビルド対象の main package、Go のバージョン、依存関係、OS/アーキテクチャ、ビルドタグを調べる。
   `go build`、`CGO_ENABLED`、`GOOS`、`GOARCH`、`-pgo`、`default.pgo` が探索の手掛かりになる。
3. デプロイ経路を確認し、サーバー上で再ビルドしていないか、生成したバイナリをどの unit が起動するかを
   追う。プロファイルだけを配置して再起動する経路は PGO の適用経路にならない。
4. このリポジトリを例にする場合は、`Taskfile.yml` の `build-pgo` と `deploy-app`、
   [`webapp/go/main.go`](../../webapp/go/main.go) の listener、`runs/` に保存された CPU プロファイルの
   対応関係を確認する。これらのタスク名・保存場所はリポジトリ固有の例である。

## 実装方法

PGO の入力から配布物までを、次の役割に分けて実装する。

1. 対象のソースと処理経路に対応する CPU プロファイルを用意する。プロファイルの取得元とソースの対応を
   分かる形で管理し、コード変更で対応関係が崩れたら入力を更新する。
2. main package の近くへ `default.pgo` を置くか、ビルド時に明示的なプロファイルパスを渡す。`auto` を
   使う配置の代表例は次のとおりである。

   ```shell
   go build -pgo=auto -o app ./
   ```

3. 通常ビルドと同じソース・依存関係から、配布対象の OS/アーキテクチャ向けに PGO バイナリを生成する。
   たとえばこのリポジトリでは、サーバー上でビルドせず、ローカルの Linux/amd64 クロスビルドで
   `webapp/go/app` を作る。
4. サービス unit が参照するバイナリを、既存の正規デプロイ経路から配布する。プロファイルの配置や
   サーバー上の手動ビルドを、PGO の適用とみなさない。
5. PGO の有無を切り替えられるよう、プロファイルを除いた通常ビルドも同じ出力・起動条件で維持する。
   PGO は CPU 最適化の一要素なので、DB 接続設定、listener、環境変数、サービスの責務を同時に変更しない。
