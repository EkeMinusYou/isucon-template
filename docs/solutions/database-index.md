# DBに適切なインデックスを追加する

## 概要

テーブル全体を走査してから `WHERE` で絞り込む、結合先の行を毎回探す、全行を並べ替えてから `LIMIT` を適用する、といった SQL のアクセス経路を、検索条件に合うインデックスへ置き換える実装パターンである。単一列インデックスだけでなく、複数の条件・結合・並び順を一つのアクセス経路にまとめる複合インデックスを対象にする。

インデックスは、SQL の結果やトランザクションの正しさを変えずに、DB が候補行を絞り込むための構造である。特に、次のような読み取りが繰り返されるサービスで候補になりやすい。

- `WHERE` でテナント、ユーザー、状態、時刻などを絞り込む検索
- `JOIN` の外部キー側を親 ID で探す処理
- `WHERE` で絞った結果を `ORDER BY ... LIMIT` で最新順・価格順などにする一覧
- `UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` で対象行を特定する処理

インデックスを追加するだけで N+1 クエリ、不要な列の読み出し、アプリケーション側の全件ソートが解消されるわけではない。これらは別の改善と組み合わせる対象であり、インデックスは対象 SQL のアクセス経路を支える。

## 適用条件・制約

- 対象 DB がインデックスをサポートし、SQL の方言・ストレージエンジン・バージョンが決まっていること。以下の DDL は MySQL/InnoDB を主な例とし、PostgreSQL などへは正本のマイグレーション方式と実行計画の読み方を置き換える。
- インデックスの候補は、実際の `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY`、`LIMIT` の組み合わせから決めること。列が `WHERE` に登場するだけで単独インデックスを追加してはならない。
- 複合インデックス `(a, b, c)` は、一般に `(a)`、`(a, b)`、`(a, b, c)` の左端の並びを使う検索に向く。`b` だけ、または `(b, c)` だけを条件にする検索のために、そのインデックスが自動的に代用されるとは限らない。複数の SQL 形状がある場合は、各クエリの共通する左端を確認する。
- `WHERE` の等価条件、範囲条件、並び順を同じ複合インデックスで扱えるとは限らない。典型的には等価条件を先に置き、その後に範囲や順序に使う列を置くが、範囲条件を挟んだ後の列まで絞り込みやソートに使えるかは DB とクエリ形状に依存する。`ORDER BY` の列順・方向・同値時の tie-breaker を仕様と実行計画の両方で確認する。
- `ORDER BY` をインデックスで処理できるかは、`WHERE` の条件、列の方向、NULL の扱い、DB バージョンで変わる。MySQL 5.7 と 8.0 では降順インデックスや生成列の扱いが異なるため、バージョンを跨いだ DDL をそのままコピーしてはならない。
- インデックスは読み取り専用の構造ではない。対象列が `INSERT`、`UPDATE`、`DELETE` されるたびに維持コスト、ディスク容量、バッファプール消費が発生する。高頻度の書き込みテーブルに、使途の重なるインデックスや大きなカバリングインデックスを増やしてはならない。
- `PRIMARY KEY`、`UNIQUE KEY`、外部キー、既存の単一・複合インデックスを先に調べる。既存の左端一致で足りるのに重複インデックスを作ると、容量と書き込みコストだけが増える。Unique Index は高速化のためだけに使わず、重複禁止という仕様がある場合にだけ使う。
- `WHERE LOWER(name) = ?`、`WHERE DATE(created_at) = ?` のように列へ関数を適用する SQL、暗黙の型変換、照合順序の不一致、`LIKE '%prefix'` のような前方ワイルドカードは、通常の B-tree インデックスをそのまま利用できないことがある。範囲条件への書き換え、生成列・関数インデックス、照合順序の変更は、意味と DB バージョンを確認した別の設計として扱う。
- `TEXT`、`BLOB`、長い `VARCHAR` を含めるカバリングインデックスは、キー長・照合順序・メモリ容量の制約を受ける。全文検索は `FULLTEXT`、地理検索は `SPATIAL` など、検索の意味に合う専用インデックスを選ぶ。B-tree を追加すれば全文・空間検索が解決すると考えてはならない。
- インデックスの有無でレスポンスの意味、アクセス権、並び順、ロック対象、重複判定を変えてはならない。特に予約、在庫、残高、決済、idempotency key などの一意性は、表示用の検索インデックスとは別に正本の制約として設計する。
- 複数のアプリケーションホストから同じ DB を参照する構成では、インデックスは DB 側のスキーマとして全ホストの SQL と整合させる。初期化処理がテーブルや DB を作り直す場合、実行時に手で追加しただけのインデックスは初期化後に失われるため、初期化元の DDL またはマイグレーションの正本へ記録する。

## 探索方法

1. まず `docs/official/` のアプリケーション仕様・当日マニュアルから、検索結果の完全性、並び順、更新直後の可視性、重複禁止、ロックや同時実行時の制約を確認する。Index 追加で結果を省略したり、順序を変えたり、Unique 制約を後付けしたりできるとは限らない。
2. スキーマの正本を見つける。`CREATE TABLE`、`PRIMARY KEY`、`UNIQUE KEY`、`KEY`、`CREATE INDEX`、外部キー、生成列、マイグレーションファイルを検索し、テーブルごとの既存インデックスを表にする。稼働 DB の状態を調べられる場合は `SHOW CREATE TABLE` と `SHOW INDEX` も使い、DDL と実際のスキーマのずれを分けて扱う。
3. SQL の呼び出し経路をたどる。HTTP ハンドラ、サービス、リポジトリ、ORM の preload・scope・自動生成 SQL を確認し、`SELECT`、`UPDATE`、`DELETE`、`JOIN`、`WHERE`、`ORDER BY`、`GROUP BY`、`FOR UPDATE`、`LIMIT` を検索する。文字列定数だけでなく、条件を組み立てる分岐、ページング、ソート指定、テナントや認証ユーザーの暗黙条件も含める。
4. SQL ごとに、次の情報を抽出する。
   - 最初に絞る等価条件、範囲条件、NULL 条件、`IN`、`OR`
   - 結合の左右、結合先で行を探すキー、結合後に追加する状態条件
   - `ORDER BY` の列順・方向、同値時の安定した順序、`LIMIT`
   - 取得列の大きさ、集計列、更新される列、トランザクションとロックの境界
5. 既存インデックスの左端一致と重複を照合する。たとえば `(tenant_id, user_id, created_at)` が既にあれば、`tenant_id` だけを使う検索は候補になり得る一方、`user_id` だけを使う検索には別の先頭列が必要になる。外部キーがあることだけを根拠にせず、実際に結合先を探す側へインデックスがあるかを確認する。
6. DB の `EXPLAIN` または同等の実行計画表示で、候補インデックスが SQL の形状に対応しているかを読む。対象は、選択されたキー、利用されたキー部分、推定される候補行数、結合順、追加のソート・一時表・全走査の有無である。これは候補 SQL とスキーマの対応を確認するための探索であり、別の SQL の結果や仕様を省略する根拠にはしない。
7. 最後に書き込み経路を列挙する。追加候補の列が高頻度で更新される、バルク投入される、またはロック中に更新される場合は、読み取り側だけでなくインデックス維持とロック範囲を実装判断へ含める。読み取り候補と書き込み候補が衝突する場合、単一列を大量に増やすのではなく、同じクエリ形状を支える最小の複合インデックスへ整理する。

たとえば、一覧取得で使う外部キー条件と作成日時の降順を、schemaの複合indexと照合する。
中間テーブルでは、joinに使う両側の外部キーも確認する。これは無条件にindexを追加する指示ではなく、
SQLの条件・順序とschema定義を対応づける探索方法である。

## 実装方法

### スキーマの正本へ追加する

Index はアプリケーションの起動時に暗黙に作るのではなく、対象 DB のスキーマ正本へ名前付きで追加する。新規テーブルなら `CREATE TABLE` 内の `KEY`、既存テーブルなら利用しているマイグレーション方式の `ALTER TABLE ... ADD INDEX` を使う。初期化用 DDL と稼働中 DB の更新履歴が分かれている場合は、両者が同じ最終スキーマになるようにする。

以下は `orders` という説明用テーブルの例であり、このリポジトリの実テーブルへそのまま適用してはならない。

```sql
ALTER TABLE orders
  ADD INDEX idx_orders_user_status_created (
    user_id,
    status,
    created_at,
    id
  );
```

この Index は、次のような「ユーザーと状態で絞り、作成時刻と ID で安定して並べる」クエリ形状の候補である。

```sql
SELECT id, status, created_at
FROM orders
WHERE user_id = ?
  AND status = ?
ORDER BY created_at DESC, id DESC
LIMIT ?;
```

`user_id` と `status` が等価条件、`created_at` が時系列の範囲・順序、`id` が同時刻の tie-breaker という役割を持つ。別の SQL が `status` だけで検索する、時刻の範囲を先に絞る、価格で並べる、といった形なら、この定義を無条件に共有せず、別の列順または別の Index が必要かを調べる。

### 複合 Index の列順をクエリ形状に合わせる

代表的な候補は次のように考える。ただし、これは機械的な公式ではなく、DB の実行計画と仕様に合わせて置き換える。

- `WHERE tenant_id = ? AND owner_id = ?` のような等価条件は、同じ検索で必ず使う識別子を先頭候補にする。
- 等価条件の後ろに、時刻・価格・ID などの範囲または順序へ使う列を置く。範囲列の後ろの列がさらに検索やソートへ使えるかは DB の仕様による。
- `JOIN child ON child.parent_id = parent.id` で親ごとの子行を探すなら、通常は子テーブルの `parent_id` を先頭候補にする。さらに `child.status` で絞るなら `(parent_id, status)` などを SQL の結合順とともに検討する。
- `ORDER BY ... LIMIT` の一覧では、絞り込み列だけでなく並び順と同値時の順序を含める。混在する昇順・降順を扱う場合は、接続先の DB バージョンに対応した降順 Index、生成列、クエリの並び替えなどを選ぶ。
- `SELECT` する列を Index へ追加してカバリングさせる場合は、検索・結合・順序に必要な列を優先する。大きな本文、画像、秘密情報をカバリングのために Index へ入れない。

`OR`、関数適用、前方ワイルドカード、複数の独立したソート条件などは、Index 追加だけでは十分に絞れないことがある。`UNION ALL` への分解、検索用の生成列、専用の全文・空間 Index などは、結果の重複・NULL・権限・バージョン互換性を確認したうえで、別の SQL／スキーマ変更として実装する。

### 制約用 Index と検索用 Index を分ける

重複禁止が仕様であるセッションキー、外部イベント ID、idempotency key などは、検索が速くなるからではなく、重複を受け付けない正本の制約として `UNIQUE KEY` を定義する。

```sql
ALTER TABLE sessions
  ADD UNIQUE KEY uq_sessions_token (token);
```

既存データに重複がある状態で Unique Index を追加すると、DDL の成功可否だけでなく、以後の書き込み結果が変わる。Unique 制約が必要か、既存の主キー・一意キーと重複していないかを、アプリケーション仕様とデータモデルから確定する。単なる絞り込みには通常の非 Unique Index を使う。

### 初期化・複数ホストとの整合性を保つ

アプリケーションの DB 初期化処理がテーブルを再作成する大会では、Index 定義を初期化用スキーマへ含める。稼働中 DB へ適用する履歴だけを変更して初期化用 SQL を変更しない、またはその逆にすると、再初期化後のアクセス経路が別物になる。

このリポジトリ固有の例では、`webapp/sql/initdb.d/10_schema.sql` が `app` の初期スキーマに含まれるため、そこにある Index 定義は初期化後にも復元される前提で管理されている。別のアプリケーションでは、`migrations/`、ORM の schema 管理、IaC など、そのプロジェクトで定めた正本へ置き換える。アプリホストへ個別の SQL を配るのではなく、同じ DB スキーマを参照する全経路で定義を共有する。
