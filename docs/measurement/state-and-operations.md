# 状態・操作の計測

永続化方式にかかわらず、得点につながる操作の件数・進行・待ち時間を確認できるようにする。bootstrapで新実装へ組み込み、agentが実装変更に合わせて維持する。計測のために永続化方式を変更しない。

## 何を観測するか

- 公式の得点条件と新実装から、観測単位と主要な段階を定める。利用者、注文、予約などを区別し、開始・得点操作・完了・次の開始を実際の状態遷移に対応付ける。開始前や次へ進まない対象も調べられるようにする。
- 段階ごとの到達件数、段階間の経過時間、成功・失敗・再試行の件数を、得点の制約を調べるために必要な範囲で集計する。得点の価値・減点は公式出力等の内訳を使い、未観測の損失を推測で数値化しない。
- 時刻、利用者・対象の識別、初期化の世代、順序、成功・失敗の意味を揃える。HTTP成功と業務上の完了を区別し、観測終了による打ち切りを失敗や未開始と混同しない。

## どこから取得するか

まずアクセスログ・既存指標で分かる範囲を確認し、不足する境界だけをアプリ内のカウンター、時刻、イベント記録などで補う。採用した実装に合わせて取得元を選ぶ。

現在の状態やスナップショットだけでは、過去の遷移順序・時刻を復元できない場合がある。復元用データにも、読み取り操作・失敗・未開始の履歴があるとは限らない。得られない情報を0や成功で補わず、必要なら追加観測を設ける。観測できた事実と、その原因の推測を分ける。

## 標準の集計結果を保存する

- 負荷終了後、次の初期化やデータ削除で情報が失われる前に、RUNごとの標準の集計結果を生成する。既存のcollector/digester・`after-bench`へ生成・回収を接続する。
- 到達件数や経過時間の分布・代表値などを保存する。RUN、集計定義のversion、情報源、対象ホスト、世代・対象範囲、母数・時間窓、欠損・途中処理の扱いも記録する。
- 競技・実装に依存する集計処理は`tools/contest/`、タスクは`Taskfile.contest.yml`へ置く。`tools/analysis/sources.yaml`へ接続し、`task q`で比較できるようにする。負荷期間に限定できない集計はRUN成果物に残し、期間限定の分析値へ混ぜない。
- 通常の分析DBは保存済みの集計結果から再構築できるようにする。追加の状態履歴・復元用データ全体を、毎RUN回収して取り込み続けることは標準にしない。生成失敗・欠損は成果物の検査で検出する。

## 重要な操作間の標準集計

bootstrapで、得点機会の進行を見るための重要な操作の組み合わせを
`tools/contest/user-transition-routes.json`の`operation_pairs`へ設定する。
「処理完了→次の開始」など、途中に別APIが入る区間も対象にする。全APIの総当たりは行わない。
通常は`session_id`が同じ利用者の区間を扱う。対象IDや応答本文が必要な業務上の完了は、この集計で
代用せず、必要なイベント・カウンターで補う。

```json
"operation_pairs": [
  {
    "name": "completion_to_next_start",
    "from": {"method": "POST", "route": "/api/complete", "statuses": [200]},
    "to": {"method": "POST", "route": "/api/start", "statuses": [201]}
  }
]
```

`route`は同じファイルの`routes[].name`を使う。`statuses`省略時は2xxを対象とし、
HTTP statusだけでは業務上の成功を判別できないAPIは選ばない。
RUNごとに設定を保存し、`task q-sync`が負荷期間内の完了応答から次の開始要求までを
`operation_progress`へ集計する。追加のログ回収は行わず、API時系列と同じ読込みを使う。

- `from_events`・`from_sessions`：識別できた起点操作の件数・セッション数。`unidentified_from_events`は識別できず、次の操作を追跡できなかった起点の件数。
- `reached_events`・`reached_sessions`：次の対象操作が観測された件数・セッション数。
- `gap_avg_ms`・`gap_p50_ms`・`gap_p95_ms`と時間帯別件数：起点の応答完了から次の要求開始まで。
- `not_observed_events`：負荷期間の終了まで次の対象操作がなかった件数。失敗や失った得点とはみなさない。
- `superseded_events`：次の対象操作の前に、新しい起点操作があった件数。次の対象操作を複数の起点へ重複計上しない。
- `overlap_events`：次の対象操作が起点の完了前に始まった、または開始時刻が同じ件数。順序や待ち時間を確定せず、時間分布から除く。

起点も到達先も、要求開始と応答完了が負荷期間に収まるものだけを使う。期間末にまだ応答が終わっていない
対象操作は到達件数に含めない。時間分布は到達した対象だけの値であり、未到達件数と一緒に読む。
古いRUNで設定が保存されていない場合や負荷期間が判定できない場合は、0件ではなく集計なしとなる。

例：`task q -- "SELECT * FROM operation_progress WHERE run_id='RUN_ID';"`

接続の基本集計は`connection_reuse`に保存する。接続IDはホスト・プロセスの起動世代内で一意にし、
欠損を0回利用した接続として扱わない。RTTの計測や操作速度との相関は、通信待ちの仮説を調べるときに追加する。

## 同時に進行している操作と空き時間

bootstrapで`operation_intervals`に開始・終了を指定する。`operation_pairs`が「完了から次の開始まで」を見るのに対し、こちらは「開始から完了まで」の進行中の区間を見る。

```json
"operation_intervals": [
  {
    "name": "active_operation",
    "start": {"method": "POST", "route": "/api/start", "statuses": [201]},
    "end": {"method": "POST", "route": "/api/complete", "statuses": [200]}
  }
]
```

開始の成功応答から終了の成功応答までを同一`session_id`で対応付け、負荷期間の`operation_concurrency`へ集計する。一つの定義につき同一セッションで同時に一つだけ進行する操作が対象。並行した注文等は、対象IDを識別する別のイベント計測で補う。

- `peak_concurrent`・`avg_concurrent`：観測した同時実行数の最大・時間平均。
- `active_person_seconds`：各セッションの進行中の秒数の合計。
- `idle_seconds`：該当する操作が一件も進行していなかった秒数。
- `observed_peak_occupancy_ratio`：平均同時数÷観測した最大同時数。ベンチの仕様上の上限や稼働率とは決めつけない。
- `open_intervals`：終了を観測できず、観測上は負荷終了まで継続していた区間の件数。

開始が見つからない終了、開始の重複、時刻の同一、識別情報の欠落がある場合は件数と`status=partial`を残し、`idle_seconds`をNULLにする。欠落を空き時間と解釈しない。
ログの読込み・API分類は既存の進行集計と共有し、DBには定義ごとの集計だけを保存する。

例：`task q -- "SELECT * FROM operation_concurrency WHERE run_id='RUN_ID';"`

## 必要時の詳細分析と確認

標準の集計結果で仮説を区別できない場合は、対象RUN・問い・必要な履歴の範囲を決めて追加分析する。原文を保存するなら、容量と保持期間を決め、Git対象外の`runs/<RUN_ID>/raw/`等へ置く。過去のデータが失われた場合は、そのRUNで保存した集計の範囲だけを扱い、現在の状態で代用しない。

検証用RUNで元の観測と集計を照合し、重複・再試行・世代違い・識別欠損・途中処理の扱いを確認する。収集と解析の時間・メモリ・保存容量も確認し、上限超過や一部取得を不完全な結果として示す。計測の都合で、復元に必要なデータや永続性要件を変更しない。

WALを取得元に選んだ場合だけ、[WALの分析と保存](wal-analysis.md)も参照する。
