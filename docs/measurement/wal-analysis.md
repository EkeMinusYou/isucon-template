# WALの分析と保存

通常の分析DB（`runs/analysis.duckdb`）には、RUNごとの標準の集計結果を保存する。WAL全件の継続的な取り込みと、毎RUNのWAL原文の回収は標準にしない。

## 標準の集計結果

競技の得点条件に合わせて、段階ごとの到達件数、時間帯別の件数、段階間の経過時間、成功・失敗・再試行の件数などを定める。経過時間は分布や代表値を保存し、利用者・処理対象ごとの更新明細を全件保存する方式にはしない。WALで判定できない項目はアクセスログ等で補い、未観測を0件や失敗に置き換えない。

RUN、集計定義のversion、情報源、対象ホスト、世代・sequenceの範囲、母数・時間窓、欠損・解析失敗・途中処理の扱いも記録する。集計結果から答えられる問いと、詳細な履歴が必要な問いを区別する。

## 通常のベンチ後処理

- 負荷終了後、次の初期化やrotationで情報が失われる前に、そのRUNの標準の集計結果を生成する。対象ホストでWALを順に読んで集計するなど、原文全体をローカルへ転送せずに済む方法を優先し、実際の解析時間・メモリ・I/Oで実行場所を選ぶ。
- 非同期WALは受理済み・追記済みの範囲を区別し、集計した世代・sequenceと時刻を確定する。回収不足や負荷終了による打ち切りを、業務上の失敗・未開始と混同しない。
- 標準の集計結果をRUN成果物として回収し、`tools/analysis/sources.yaml`にはその成果物の取り込みを接続する。通常の同期やDB再構築でWAL全件を再解析せず、保存した集計結果から分析DBを作れるようにする。
- 成果物宣言・読み手・検査を揃え、標準の集計結果の欠損や生成失敗を検出する。WAL原文を保存しない通常RUNを、原文の取得失敗として扱わない。

## 必要時の詳細分析

標準の集計結果では仮説を区別できない場合に、対象RUN・調べる内容・必要な履歴の範囲を決める。利用できるWALを順に読むか、調査用の一時的なDuckDBへ必要な列・範囲を取り込む。調査が終わったら一時DBを片付け、全更新明細を通常の分析DBへ追加しない。

詳細分析で原文を回収・保存する場合は、圧縮し、保存先・保存量・保持期間を決める。ローカルではGit対象外の`runs/<RUN_ID>/raw/`等を使い、`after-bench`の自動コミット対象に混ぜない。原文を保存したか、いつまで利用できるかもRUNと対応付けて示す。原文が失われた過去RUNについては、保存済みの集計で分かる範囲だけを扱い、現在のWALで代用しない。

## 確認すること

- 検証用RUNのWAL・アクセスログと標準の集計結果を照合し、重複、世代違い、再試行、識別欠損、途中処理の扱いを確認する。
- 集計結果の保存容量、処理時間、最大メモリ、一時ファイルと原文の保存容量を確認し、計測環境に合わせて上限を決める。超過・解析中断・一部のみの取得を黙って切り捨てず、不完全な結果として示す。

この保存方針を理由に、サービスの復元に必要なWALを削除したり、WALの永続性要件を変えたりしない。競技固有の実装・SQLは`tools/contest/`へ置き、[既存の分析契約](../../tools/README.md#分析)へ接続する。
