# ISUCON 問題と解決策の整理

## 読み方

以下は、公式の問題説明・出題者の解説・リポジトリ・参加者の公開記事を突き合わせて整理した要約である。公式に明示された内容と、実装・参加者記事から読み取れる典型的な解法を分けるため、各節に次の印を付ける。

- 公式: 問題説明または公式解説で明示された仕様・意図
- 実装/参加者: 公開ソースコードや参加者記事から確認できる解法
- 一般化: 複数回に共通する、計測後に検討できる手筋

スコアを上げるだけの近道ではなく、ベンチマークの採点条件・再起動後の復元・同時実行時の整合性を満たすことが前提である。SQL の変更やキャッシュ導入は、alp、slow query、pprof、アプリケーションログなどの計測結果と、docs/ にある仕様を確認してから適用する。

## ISUCON1: ブログ/コメントサイト

公式資料: [開催概要](https://isucon.net/archives/41251889.html)、[公式問題の再現](https://isucon.net/archives/30155170.html)、[ソースコード](https://github.com/tagomoris/isucon/tree/ISUConRelease)

### 問題

- 公式: 記事の表示、投稿、コメント投稿、コメントされた記事のサイドバー表示を行うシンプルな Web アプリケーション。
- 実装/参加者: トップの記事一覧とコメント履歴の取得で、毎回 MySQL に同じ読み取りを発行する。サイドバーはコメントを結合して最新順に並べるため、アクセスが集中すると DB 負荷になりやすい。
- 実装/参加者: 更新系 POST と読み取り GET の性質が異なるのに、同じ経路で処理されている。

### 解決策

- 実装/参加者: nginx のリバースプロキシで GET の結果を短時間キャッシュし、POST 後に該当キャッシュを失効させる。公開記事では数秒単位の TTL が使われた。
- 実装/参加者: MySQL のクエリキャッシュや適切なインデックスを確認し、DB で毎回同じ結果を計算しない。
- 実装/参加者: 静的なレスポンスや静的ファイルを nginx から返し、アプリケーションプロセスと DB の仕事を減らす。

### 注意点

- 公式/参加者: サイドバーのキャッシュを短時間にすることは性能に効くが、投稿直後の表示と採点の整合性を壊さない TTL・失効条件が必要。ISUCON3 の公式フィードバックでも、ISUCON1 のサイドバーは 10 秒以内のキャッシュが前提として振り返られている。
- 一般化: 初期の典型は「読み取りの観測可能なキャッシュ」と「更新時の失効」であり、全ページを無期限にキャッシュすることではない。

## ISUCON2: チケット販売

公式資料: [開催概要](https://isucon.net/archives/41251926.html)、[公式問題の再現](https://isucon.net/archives/30154200.html)、[ソースコード](https://github.com/tagomoris/isucon2/tree/isucon2)、[参加者記事](https://sfujiwara.hatenablog.com/entry/20121103/1351959629)、[Redis による解法例](https://unknownplace.org/memo/2012/11/07/1/)

### 問題

- 公式: アーティスト、公演、座席の在庫を表示し、購入処理と売れたチケットの表示を行う。
- 実装/参加者: 購入画面で ORDER BY RAND() によるランダム座席選択があり、在庫更新と結び付いている。大きなテーブルではランダムソート自体が重い。
- 実装/参加者: 在庫・公演・座席の結合条件に必要なインデックスが不足すると、購入と表示の双方でフルスキャンになる。
- 実装/参加者: サイドバーの売却履歴が複数テーブルの結合・ソートを毎回行う。

### 解決策

- 実装/参加者: stock の order_id、variation_id と order_id など、実際の WHERE/JOIN/ORDER BY に沿った複合インデックスを追加し、EXPLAIN と slow query で確認する。
- 実装/参加者: ORDER BY RAND() を、事前に作った候補からの取得や Redis の Set からの atomic pop など、定数に近い在庫取得へ置き換える。
- 実装/参加者: 売れたチケットの履歴や座席マスタを Redis・メモリ・ワーカでキャッシュし、購入時だけ在庫の原子的な更新を行う。
- 一般化: 静的に近いページは Apache/nginx に寄せ、購入という書き込み経路と一覧表示の読み取り経路を分離する。

### 注意点

- 公式/参加者: 在庫をキャッシュする場合は二重販売を防ぐ原子性が最優先。表示キャッシュの TTL と購入時の正本確認を分ける。
- 一般化: Redis に移すこと自体が目的ではなく、DB のボトルネックと競合箇所を特定して、正本・キャッシュ・失効を設計する。

## ISUCON3: ブログ/プライベートメモ

公式資料: [開催概要](https://isucon.net/archives/41252102.html)、[予選問題説明](https://isucon.net/archives/32976287.html)、[予選フィードバック](https://isucon.net/archives/32951806.html)、[公式ソース](https://github.com/kayac/isucon3)、[予選用ソース公開](https://isucon.net/archives/32853582.html)、[本選用ソース公開](https://isucon.net/archives/34085586.html)

### 問題

- 公式: ログイン、セッション、公開/非公開メモ、Markdown 表示、公開メモ一覧、タグやユーザー情報を扱うアプリケーション。
- 公式/実装: 1 リクエスト内の N+1 クエリ、広い行の読み出し、不要な ORDER BY、毎回の Markdown 変換・正規表現処理が重さの中心になる。
- 公式/実装: セッションをファイルや DB に置くと、ログインを含むほぼ全リクエストが I/O を発生させる。
- 公式: Redis や memcached、tmpfs、nginx/Varnish のキャッシュ、アプリケーション内部のメモリ化など、複数の改善方向が成立するよう設計されている。

### 解決策

- 公式: セッションを memcached、tmpfs、またはプロセス内メモリへ移し、MySQL の InnoDB バッファプールを適切に確保する。
- 公式/実装: 複合インデックスを追加し、ユーザー名などリクエスト中に何度も使う値はセッションに入れる。関連データは JOIN、IN、事前取得で N+1 を減らす。
- 公式/実装: 大きな本文を並べ替えのために読み出さず、先に ID だけを絞り込んでから必要な列を取得する。title、content など表示に必要な値はまとめて持つ。
- 公式/実装: 公開メモ一覧と件数を Redis やメモリに保持し、投稿時に更新する。Markdown は外部プロセス起動を避け、アプリ内処理や結果キャッシュを検討する。
- 公式: 静的ファイルは nginx だけで返し、MySQL はアプリケーションの正本データに集中させる。

### 注意点

- 公式: 予選ではキャッシュやオンメモリ化が可能だが、採点条件に反する「キャッシュの穴」を作らない。再起動やデータ更新後の復元を確認する。
- 一般化: SQL を一つにまとめるだけでなく、読み出す列、並べ替える段階、更新時に事前計算できる値を分ける。

## ISUCON4: 銀行ログイン/動画広告配信

公式資料: [開催概要](https://isucon.net/archives/41252218.html)、[予選問題説明](https://isucon.net/archives/40724693.html)、[Redis 参考資料](https://isucon.net/archives/40793620.html)、[オンメモリ参考資料](https://isucon.net/archives/40793605.html)、[本選問題説明](https://isucon.net/archives/41634734.html)

### 予選の問題

- 公式: いすこん銀行のログイン、マイページ、ログイン失敗回数によるロック、全ログイン試行の保存、レポート生成を行う。
- 公式: 同一ユーザーのパスワード誤り 3 回、同一 IP の誤り 10 回でロックされ、ログインのたびに失敗回数を再集計する設計が負荷になる。
- 公式: ベンチマーク終了後 5 秒で状態を確定し、1 分以内にレポートを返す必要がある。状態を単純に捨てることはできない。

### 予選の解決策

- 公式: ユーザー/IP ごとの失敗回数とロック状態をメモリ、Redis、memcached などでカウンタ化し、毎回の全履歴集計を避ける。
- 公式: レポートと再起動後の継続性のため、カウンタやログを高速なストレージへ永続化し、終了時に正本と突き合わせる。
- 公式: ログインページの少数のパターンをキャッシュし、ログを高速に追記する。コンパイル言語も有効な選択肢として示された。

### 本選の問題と解決策

- 公式: 動画広告の登録、リダイレクト、広告抽選、再生、インプレッションカウンタ、レポートを提供する。最大 5 MB の mp4 を扱い、3 VM・各 1 GB の制約がある。
- 公式/参加者: 動画本体を Redis だけに置くとメモリを圧迫して swap する。動画はディスクや静的配信へ置き、Redis にはメタデータだけを置く。
- 公式: Cache-Control と条件付き GET を設定し、CDN やブラウザキャッシュを利用する。アプリはリダイレクトとカウンタなど動的な処理に集中させる。

### 注意点

- 公式: Redis オンリーの構成が必ずしも正解ではない。容量・永続性・ネットワーク転送量を測り、巨大なバイナリと小さな状態を分ける。

## ISUCON5: ISUxi/SNS と AirISU

公式資料: [開催概要](https://isucon.net/archives/45166636.html)、[予選問題説明](https://isucon.net/archives/45627361.html)、[予選ソース](https://github.com/isucon/isucon5-qualifier)、[本選問題説明](https://isucon.net/archives/45905117.html)、[本選ソース](https://github.com/isucon/isucon5-final)

### 予選 ISUxi

- 公式: ユーザー、友達関係、日記、コメント、足あと、ユーザー検索を扱う SNS。
- 公式: メインページで is_friend?、get_user のような処理がユーザーごとに呼ばれる N+1 が大きな問題になる。
- 公式: 友達の日記、コメント、権限確認で同じユーザー情報や関係情報を何度も引く。友達関係は大量になり得る。

解決策:

- 公式: ユーザー情報をまとめて JOIN/IN で取得するか、変更頻度の低いユーザーマスタをキャッシュする。
- 公式: friend_id、user_id、日記・コメントの検索条件に複合インデックスを追加し、権限判定に必要な関係だけを一度に取得する。
- 公式: 同一ユーザー・同一日など、足あとが一意になるデータは REPLACE や UNIQUE 制約で最新だけを保持する。

### 本選 AirISU

- 公式: 航空会社の予約情報を外部 API と結合し、Yahoo Pipes/IFTTT のような外部連携を行う。PostgreSQL と JSON を使った構成。
- 公式: data API が 4〜7 個の外部 API を直列に呼ぶため、I/O 待ちが積み上がる。
- 公式: 同じユーザートークンで HTTP/1.1 の複数接続を並列化すると、外部サーバーの 429 制限に当たる。

解決策:

- 公式: 独立した外部 API 呼び出しを並列化し、結果をまとめて JSON 化する。ただし同じトークンの制限を超えないよう、トークン単位の直列化や HTTP/2 多重化を使う。
- 公式/一般化: 外部 API の結果を TTL 付きでキャッシュし、同じベンチマーク中の重複問い合わせを減らす。アプリケーションのワーカ数・接続数も I/O 待ちに合わせる。

### 注意点

- 公式: 外部サービスの rate limit はアプリ側だけの最適化では消えない。429、タイムアウト、再試行、同一トークンの順序を仕様として扱う。

## ISUCON6: キーワード日記/リアルタイムお絵描き

公式資料: [開催概要](https://isucon.net/archives/48465737.html)、[予選問題説明](https://isucon.net/archives/48697611.html)、[予選ソース](https://github.com/isucon/isucon6-qualifier)、[本選問題説明](https://isucon.net/archives/48778066.html)、[本選ソース](https://github.com/isucon/isucon6-final)

### 予選の問題

- 公式: 匿名日記にキーワード自動リンク、スター、スパム判定を付ける。isuda、isutar、isupam という小さなサービス間通信を含む。
- 公式: サービスを分けたことで、日記 1 件の処理でもネットワーク・JSON・DB の往復が増える。
- 公式: キーワードを毎回 SELECT * し、正規表現を作り直すと、本文処理より準備処理が重くなる。

解決策:

- 公式: isuda と isutar の呼び出しを統合、または同一プロセス内処理にし、不要なネットワーク往復をなくす。
- 公式: キーワード一覧をリクエストごとに DB から取らず、memcached やプロセス内メモリに置く。キーワード更新時に再構築する。
- 公式: 必要な列だけを SELECT し、strings.Replacer など一度構築した置換器を使う。LIKE での大量削除や更新には適切なインデックスを付ける。
- 公式: isupam は主ボトルネックに見せるための要素も含み、全サービスを機械的に最適化するのではなく計測で優先順位を決める。

### 本選の問題

- 公式: Node.js と React の SSR、JSON API、Docker、HTTPS、部屋とストロークを扱うリアルタイムお絵描きアプリ。C10K と長時間接続が課題になる。
- 公式/実装: 部屋ごとの stroke_count や最新 stroke を毎回数える N+1、大きな points の読み出し、SSR と SVG の CPU 負荷が重い。
- 公式: CSRF トークン、セッション、SSE の再接続、TLS、ファイルディスクリプタも性能上の論点になる。

解決策:

- 公式/実装: stroke_count と最新 stroke を非正規化し、書き込み時に更新する。points は必要な形式にまとめて保存し、一覧で全点列を読み出さない。
- 公式: CSRF やセッションを短時間キャッシュし、POST で無効化する。CSRF を HTML キャッシュに埋め込む場合はユーザー単位の整合性を守る。
- 公式: 静的 SVG/HTML は nginx へ寄せ、SSR の結果を条件付きでキャッシュする。SSE は再接続・キープアライブ・HTTP/2・Pub/Sub を測定して調整する。
- 一般化: 長時間接続の数、FD、TLS CPU、アプリのワーカ数を別々に観測する。

## ISUCON7: チャット/Chair Constructor Online

公式資料: [開催概要](https://isucon.net/archives/50949022.html)、[予選問題説明](https://isucon.net/archives/50961706.html)、[予選ソース](https://github.com/isucon/isucon7-qualify)、[本選問題説明](https://isucon.net/archives/51187977.html)、[本選ソース](https://github.com/isucon/isucon7-final)

### 予選の問題

- 公式: 初めての複数サーバー予選。チャットメッセージ取得、投稿、ユーザー、画像アップロード、リアルタイム更新を扱う。
- 公式: /fetch は待ち時間の中で新着を返すロングポーリングで、/message と別の採点上の扱いを持つ。タイムアウト単位の問い合わせが大量に発生する。
- 公式: 画像と静的ファイルをアプリから返すと帯域とワーカを消費し、ユーザー・メッセージ・COUNT の N+1 も負荷になる。

解決策:

- 公式: Cache-Control: public, max-age=3600、ETag/304 を使い、変更されない画像をキャッシュする。
- 公式: メッセージ取得を一括化し、COUNT やユーザー情報を N+1 で取得しない。fetch の待ち時間とバッチ幅を採点条件のタイムアウト内で調整する。
- 公式: 画像を Redis、WebDAV、共有領域などに置き、ホスト名の振り分けや nginx の try_files/reverse proxy で静的配信する。
- 一般化: 複数ホスト間で同じ画像・キャッシュが見えること、キャッシュの失効とアップロード後の可視性を確認する。

### 本選の問題

- 公式: Chair Constructor Online という MO ゲーム。WebSocket、部屋、時刻付きの未来コマンド、大きな整数の計算を使う。
- 公式: 採点対象の状態計算は頻繁で、DB へ毎回保存するよりメモリで持ち、必要な状態だけ永続化する設計が想定される。
- 公式: 部屋を複数プロセス/ホストに固定する必要があり、接続、FD、ポート、WebSocket のルーティングが問題になる。

解決策:

- 公式: 部屋をハッシュで固定プロセス/ホストへ割り当て、部屋内の状態をオンメモリで計算する。MySQL は永続化・復旧用に限定する。
- 公式: calc_item_status のような高頻度計算を LRU などでキャッシュし、大きな整数を毎回十進文字列化しない。
- 公式: 非同期 I/O、WebSocket、適切な FD 上限と接続管理を使い、ホスト間ルーティングを一貫させる。

### 注意点

- 公式: 予選の静的キャッシュと本選のオンメモリ状態は、複数サーバーで正しい所有権を持たせることが前提。単にプロセス数を増やすと状態が分裂する。

## ISUCON8: チケット予約/ISUCOIN 取引所

公式資料: [開催概要](https://isucon.net/archives/52388756.html)、[予選問題説明](https://isucon.net/archives/52520045.html)、[予選ソース](https://github.com/isucon/isucon8-qualify)、[本選問題説明](https://isucon.net/archives/52598691.html)、[本選ソース](https://github.com/isucon/isucon8-final)

### 予選の問題

- 公式: イベントの座席予約・キャンセル、ランダム座席、管理画面、CSV レポートを扱う。ISUCON2 のチケット問題を発展させたもの。
- 公式/実装: get_event が 1000 席を 1 件ずつ取得し、複数の画面から呼ばれる N+1 になる。
- 公式/実装: NOT IN、FOR UPDATE、予約競合、デッドロック、レポートの大量読み出しが同時に発生する。
- 公式: 3 台・DB メモリ制約のため、単純なオンメモリ全量保持だけでは解決にならない。

解決策:

- 公式/実装: 座席を一括取得する JOIN/複数行クエリへ変え、イベント・座席・予約の検索条件に複合インデックスを追加する。
- 公式/実装: ロック範囲を狭くし、ロック取得順を統一する。競合・デッドロックは再試行し、予約の正しさを優先する。
- 公式: CSV は mysql_use_result や SELECT INTO OUTFILE などストリーミングで処理し、全件をアプリメモリへ載せない。
- 一般化: 1000 席のように固定上限が見えるデータでも、全画面で別々に読むのではなく、リクエスト単位で一括取得・再利用する。

### 本選の問題

- 公式: ISUCOIN の入出金・送金・注文・取引・SNS 連携。外部ログ API は同時実行数 10、毎秒 20 リクエスト、bulk API あり。commit は約 300 ms、reserve の有効期間は 5 分。
- 公式/実装: 注文・取引テーブルのパーティションが使われず、最新取引に LIMIT 1 がなく、注文情報やローソク足を N+1 で取得する。
- 公式: bcrypt のコスト、外部 API の 429、遅い commit、5 分間の予約状態がボトルネックになる。

解決策:

- 公式/実装: 不要なパーティションを除去し、最新取引には LIMIT 1 と適切な順序インデックスを付ける。注文・銘柄情報は一括取得する。
- 公式: 銘柄設定などのマスタをキャッシュし、ローソク足は最大 1 秒の鮮度要件に合わせて短時間キャッシュする。
- 公式: 外部ログは同時数・レート制限を守り、可能なところは send_bulk を使う。遅い commit はキューに入れて非同期化する。
- 公式: bcrypt は許容される最小コストを使い、認証処理の CPU を抑える。

### 注意点

- 公式: 429 回避のための過剰な並列化は逆効果。reserve、cancel、commit の順序と残高整合性を壊さない。

### 本選 ISUXPRESS

- 公式: 280 万件規模の時刻表、7 万列車の鉄道予約。列車検索、運賃・座席、予約、外部キャンセル API を扱う。

## ISUCON10: ISUUMO/XSUCON

公式資料: [開催概要](https://isucon.net/archives/54704557.html)、[予選問題説明](https://isucon.net/archives/55025156.html)、[予選ソース](https://github.com/isucon/isucon10-qualify)、[本選問題説明](https://isucon.net/archives/55140539.html)、[本選ソース](https://github.com/isucon/isucon10-final)

### 予選 ISUUMO

- 公式: 不動産検索。価格、人気度、位置、ポリゴン範囲、カテゴリーを組み合わせて検索する。
- 公式: low_priced 検索に ORDER BY 用のインデックスがなく、MySQL 5.7 で人気度降順・ID 昇順の混在順序をそのまま扱いにくい。
- 公式: ポリゴン検索で POINT/ST_Contains と空間インデックスを使わないと、対象範囲の判定が大きな走査になる。

解決策:

- 公式: 人気度の符号を反転した生成列などを用意し、複合 B-tree インデックスで単一方向の ORDER BY に変換する。
- 公式: 位置を POINT として保持し、空間インデックスと ST_Contains を利用する。ポリゴンの N+1 判定をアプリ側で行わない。
- 公式: アプリ/DB の役割を分け、静的ファイルを nginx から返す。規定された bot User-Agent の扱いは採点条件を確認する。

### 本選 XSUCON

- 公式: HTTPS、gRPC、Protocol Buffers、Envoy を使うコンテスト運営ポータル。参加登録、キュー、質問、ポーリング、ダッシュボードを扱う。
- 公式/実装: 静的ファイル、コンテスト設定、チーム情報、リーダーボードを毎回生成すると、同じデータを繰り返し送ることになる。
- 公式: ベンチマーク完了後にリーダーボードを一括更新し、観客向けには 1 秒のキャッシュを許容する。キュー待ちを sleep で実装すると無駄なリクエストになる。

解決策:

- 公式: nginx で静的ファイルを配信し、gzip/brotli と max-age を設定する。設定・チーム情報を protobuf などでキャッシュする。
- 公式: 結果の集計をイベント駆動・非同期にして、完了後にリーダーボードを materialize する。観客向け更新は短い TTL で共有する。
- 公式: Redis の BRPOP など待機型キューを使い、ポーリング間隔を sleep で消費しない。3 台の性能差に合わせて役割を割り当てる。

## ISUCON11: ISUCONDITION/ISUCHOLAR

- 公式: 複数サーバー、GPA 呼び出し抑制、zip の無圧縮化が大きな改善点として示されている。

解決策:

- 公式: 講義・クラス・提出・得点を JOIN/一括取得し、独立した講義・学生処理は並列化する。
- 公式: 完了した講義の GPA や集計結果は不変としてキャッシュし、コース完了後の再計算を抑える。
- 公式: App/DB を分離し、静的な配布物は圧縮方式・CPU・帯域のバランスを測る。3 台構成の役割分担を行う。

## ISUCON12: ISUPORTS/ISU CONQUEST

公式資料: [開催概要](https://isucon.net/archives/56571716.html)、[予選問題説明](https://isucon.net/archives/56850281.html)、[予選ソース](https://github.com/isucon/isucon12-qualify)、[本選問題説明](https://isucon.net/archives/56959385.html)、[本選ソース](https://github.com/isucon/isucon12-final)

### 予選 ISUPORTS

- 公式: テナントごとに SQLite を持つマルチテナント SaaS。MySQL のテナント管理、JWT、player_score 約 370 万行、visit_history、CSV、ランキングを扱う。
- 公式/実装: SQLite の JSON 検索、ランキング・CSV の全件走査、N+1、プロセス間 flock、player_score への頻繁な書き込みが重い。
- 公式: 429 と Retry-After、3 秒以内の鮮度、初期化 30 秒以内、SQLite を維持するか MySQL へ移行するかの判断がある。

解決策:

- 公式: SQLite のログと JSON 条件を確認し、不要な行・列を読まない。ランキング・参加者一覧をキャッシュし、3 秒の鮮度要件内で更新する。
- 公式: player_score の更新をトランザクションと bulk 処理にまとめ、UUID をキーとする検索を適切に索引化する。N+1 を一括取得に変える。
- 公式: flock の競合を減らし、テナント分布とプロセス数を調整する。必要なら大きなテーブルだけ MySQL へ移すが、全移行は必須ではない。
- 公式: CSV はストリーミング、LOAD DATA、事前生成などでアプリのメモリと CPU を抑える。429 の場合は Retry-After に従う。

### 本選 ISU CONQUEST

- 公式: ユーザー/管理 API、ログイン、アイテム、抽選・ゲーム状態、履歴を持つアイドル系ゲーム。書き込みが多く、5 台構成で DB の水平分割がテーマになる。
- 公式/実装: ログインや API の N+1、DB 分割後の cross-shard 集計、マスタの繰り返し取得、現在状態と履歴の過剰な書き込みが負荷になる。

解決策:

- 公式: ユーザー単位のシャードキーを決め、アプリから分割先を選ぶ。現在状態と履歴を分け、必要な履歴だけ非同期に保存する。
- 公式: アイテムなどのマスタをバージョン付きでキャッシュし、更新時に世代を変える。DB 台数を増やす場合も接続・書き込み競合を測る。
- 公式/一般化: アプリ生成 ID にシャード情報や時系列性を持たせ、ランダムな分布と衝突回避を両立する。

公式資料: [開催概要](https://isucon.net/archives/57801192.html)、[公式解説](https://isucon.net/archives/58001272.html)、[公式ソース](https://github.com/isucon/isucon13)、[参加者集計](https://isucon.net/archives/57991509.html)、[参加者記事 LayerX](https://tech.layerx.co.jp/entry/2023/11/26/173000)

### 問題

- 公式: DNS を PowerDNS と MySQL で扱う構成があり、DNS 問い合わせ・TTL・ゾーン/レコードの DB 負荷がボトルネックになり得る。

- 公式/実装: 配信中のコメント、リアクション、Tips は強い鮮度・整合性要求があり得る。長いキャッシュを全 API に適用せず、読み取り種別ごとに TTL と失効を定義する。
- 一般化: 現行リポジトリの ISUPipe 実装を変更する場合は、docs/isupipe.md と本番の API 仕様を先に確認する。

## ISUCON14: ISURIDE

公式資料: [開催概要](https://isucon.net/archives/58818382.html)、[公式問題解説](https://isucon.net/archives/58869617.html)、[公式ソース](https://github.com/isucon/isucon14)、[参加者集計](https://isucon.net/archives/58835757.html)、[参加者記事 kawaemon](https://zenn.dev/kawaemon/articles/isucon14-final)、[参加者記事 iceman](https://zenn.dev/iceman/articles/isucon14-final)、[参加者記事 ganariya](https://zenn.dev/ganariya/articles/isucon14-final)

### 問題

- 公式: 自動運転椅子による配車サービス。乗車要求、椅子の位置・状態、マッチング、移動、到着、決済・クーポン、通知を扱う。
- 公式: 30 ms の tick で状態を更新し、マッチング遅延、到着、実際の移動距離、乗車完了などがスコアに影響する。単純な HTTP レスポンス数の最適化ではない。
- 実装/参加者: アクセストークン、ride の時刻/状態、coupon、chair location/status、current location の読み取りにインデックスがないと、短い tick 内に大量走査になる。
- 実装/参加者: nearby chairs、waiting rides、最新位置を 1 件ずつ問い合わせる N+1 と、総移動距離・最新位置を履歴から毎回集計する処理が重い。

### 解決策

- 実装/参加者: token、ride の状態・時刻、chair の状態・位置、coupon の有効期間など、実際の検索順に沿った複合インデックスを追加する。
- 公式/参加者: 最新位置と累積距離を summary/current テーブルへ UPSERT し、履歴を全走査せずにマッチングとスコア計算を行う。
- 公式/参加者: 待機中の ride と空き椅子を一括取得し、近傍検索・距離・閾値・地域で候補を絞る。複数 matcher を使う場合は同じ ride を二重処理しないロック/所有権を設ける。
- 公式/参加者: 通知は Retry-After、SSE/long poll、短時間キャッシュ、再試行を仕様に合わせて使う。座標更新・決済・キャンセルなど独立した処理は bulk/非同期化する。
- 公式/一般化: idempotency key と状態遷移を保ち、決済や通知の再試行で二重請求・二重完了が起きないようにする。

### 注意点

- 公式: 3 秒の猶予や通知の遅延許容があっても、マッチングや実際の移動の正しさを犠牲にしてはいけない。tick の期限、データベースロック、シミュレーション結果を同時に確認する。

## 年をまたいで共通する解決パターン

各回の問題は異なるが、公開資料に繰り返し現れる順序は次のとおりである。

1. まず採点条件と正しい挙動を確認する。キャッシュ鮮度、再起動後の復元、外部 API の rate limit、予約/決済/在庫の整合性を先に固定する。
2. alp などでエンドポイント別の件数、レイテンシ、ステータスを分け、slow query で SQL の回数・行数・時間を確認する。
3. pprof、CPU/IO、メモリ、swap、FD、ネットワークを別々に測り、アプリ・DB・nginx・外部 API のどこが待ち時間を作っているかを切り分ける。
4. N+1 を JOIN/IN/bulk/preload に変える。ただし巨大な JOIN で不要な列を増やさず、先に ID を絞る、必要な列だけ読む、ページングする。
5. 読み取りを短時間キャッシュし、更新時の失効・世代管理・共有範囲を定義する。静的ファイル、画像、動画、マスタ、集計結果を動的な正本から分離する。
6. 書き込みはインデックス・ロック・トランザクション・キューのコストを測る。bulk 化で速くなる場合も、競合と復旧を含めて確認する。
7. 複数ホストでは状態の所有権、セッション、画像/キャッシュの共有、DB 接続、FD、役割分担を決める。オンメモリ化はホスト間で分裂しない構成にする。
8. 最後にベンチ後のログ・DB・キャッシュを初期化し、同じ変更を再現して、スコアと正しさを比較する。改善が無い変更や観測できない変更は戻す。
