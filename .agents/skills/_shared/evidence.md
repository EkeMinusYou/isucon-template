# Evidence

Evidenceの選択・比較・欠損・因果の扱いを定める。

## 優先するEvidence

1. `docs/official/`の当日マニュアル、アプリケーション仕様、API定義
2. 現行コード、schema、設定、Taskfileの役割定義
3. 対象RUNの`run.json`と保存済み成果物
4. 比較可能なRUN横断値
5. 必要な範囲の読み取り専用実効環境

公式仕様と他の資料が矛盾したら公式仕様を優先する。競技中は外部記事を公式仕様の代わりにせず、
許可された範囲と必要性を確認してから参照する。

## 確認済みEvidenceの再利用

確認済みの事実・集計結果・取得方法は、参照先と対象RUN・コードの時点・集計定義・確認範囲を引き継いで再利用する。同じ数値の再集計や取得方法の再探索、確認済み履歴の全文再読を繰り返さず、入力の変更・不一致・不足があれば該当部分を確認する。

各スキル固有の観点による評価と、結論を左右する独立確認は省略しない。同じEvidenceを別の目的で評価することは必要な作業であり、前工程の結論をそのまま採用することを再利用とは扱わない。独立確認に必要な原資料は参照する。

追加調査の前に、その結果で実装方針・優先順位・変更範囲・改善仮説のどの判断が変わるかを明確にする。判断を変えない精密化や同じ前提の再探索は行わない。正当性に必要な確認は省略しない。対象全体は最新状態を概観し、詳細確認は変更・不一致・未解決の判断に絞る。担当範囲内の対象を黙って除外せず、前回の根拠と再検討条件を再利用する。

以下は必要な局面で使う判断規則であり、毎回すべての指標・経路を再集計するチェックリストではない。共通条件と集計方法は簡潔に記録し、次の報告では差分と参照先を示す。追加計測や同一構成の再ベンチは、判断が変わり得る場合だけ検討する。

## 改善方向と優先順位

改善対象は最新Evidenceから選び、特定API・資源・方式・過去の優先対象を固定しない。得点機会の成立・進行・価値・損失への寄与仮説を起点に、現行から減る仕事・待ちの絶対量と発生頻度、代わりに増える実行時の仕事、改善方向を覆し得る不確実性を比較する。時間・CPU仕事・待ち・処理量は同じ母数と時間窓で比較し、包含値を加算しない。確保量などの機構指標しかない場合は時間や得点への寄与が未確認と記す。

局所改善と構造変更は同じ基準で比較する。どちらも現行との差分、得点への寄与機構、主要な追加コストと正当性の成立条件を検討する。現在の律速や支配的な待ちである証明、正確な削減量、純利益の実測、個別得点への帰属は改善案の報告条件にしない。構造変更だけに全難点の解決を求めず、局所改善も一つの処理の削減だけで優先しない。概算やコード・構成から改善方向を説明できれば、未確定点とその確認方法を示して進める。効果量が未確定なことを改善余地が小さい根拠にせず、根拠のない大きな期待も優先理由にしない。

実行時のCPU・同期・転送等の追加コストと、調査・実装の作業量を区別する。前者は純利益の評価に含める。後者は構成と改善機構を具体化した後、進め方・分担や実際の残り時間内での完遂可能性を判断するために使う。実装の容易さ、変更規模、「難しそう」という印象で探索対象を狭めない。作業量だけから期限や実現不能を仮定しない。

コード上の改善機構が成立したこと、処理指標が改善したこと、得点が改善したことは別々の判断である。局所改善が成立しても後続の変化が確認できない場合、同方向への追加作業を自動的に優先しない。一方、未観測を反証とせず、小改善や同じ対象への追加案を一律に除外しない。

適用後の退行からの部分回復は、変更前に対する純利益とは区別する。直前修正版との比較だけで継続を正当化せず、変更前の状態、減らせる仕事・待ち、残る追加費用と得点への経路を照合する。未観測は反証ではないが、それだけで追加実装を正当化する根拠にもならない。

## 得点への経路の再評価

既存の改善案を再評価するときは、関係するRUNとコード・設定の時点を照合し、当初の仮説、その後の観測、現行との差分を確認する。詳細はRUN成果物から必要な範囲だけ再取得する。

「局所的な仕事・待ち・損失の変化 → 得点機会の成立・進行の変化 → 得点の変化」を、仮説に必要な範囲で観測と照合し、支持・反証・未確認の関係を分ける。局所改善だけで得点への寄与が確認できたとも、スコア横ばいだけで反証したとも扱わない。想定した後続の変化を確認できなければ、成立条件の変化、他の制約、比較条件や観測の不足を保存済みEvidenceから検討する。得点機会の件数・一件の価値・損失のどこが未観測かを示し、処理成功数を得点発生件数と同一視しない。

同じ未確認の寄与関係に依存する追加作業には、新しいEvidence、成立条件の変更、別の寄与経路など、何が追加作業を支持するかを示す。根拠がなければ、未確認の関係を「どの観測・コード・構成を確認し、どの結果なら選択が変わるか」という問いへ分解し、保存済みEvidenceや許可された読み取り調査で進められる部分を選ぶ。同じ理由で同じ調査を反復せず、判断理由と参照するRUNを簡潔に報告する。

## RUNの扱い

- `run.json`のphase、役割、source、artifact statusを先に確認する。
- スコア差分は対象RUNより前でrolesが同一の最新finalized RUNを比較候補にする。比較可能性を確認し、比較不能理由を残して対象RUN単独で確認できる事実と分ける。
- 欠損成果物を0として扱わない。
- 比較RUNは役割・source・計測窓・負荷条件の互換性を確認する。
- 時間、仕事量、待ち、成功数、失敗数、得点を混同しない。単位と母数を併記する。
- 相関と因果を分け、コードまたは仕様から効果の経路を説明する。
- correctness、5xx、OOM、panic、service再起動の確認には、同じload windowのapp journal、nginx error、
  kernel/OOM成果物も使う。
