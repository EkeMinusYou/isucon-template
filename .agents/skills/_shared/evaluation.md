# Evaluationの指定方法

investigateはREADY確定時に、workerは実装前の取得方法確認時とベンチ後に参照方法を解釈する必要があるときに読む。採用条件は[workflow](../../../tools/backlog/backlog-workflow.md#adoption)、比較・欠損・因果の扱いは[Evidence](evidence.md)に従う。

## 何を指定するか

`Evaluation`には、改善対象の機構、悪化させ得る関連処理、正確性条件について、**何を読んで何を判断するか**を対応付ける。成果物名だけでなく、対象API・SQL行・profile関数などの参照先と指標、単位・母数・時間窓、採用・限定修正・不採用へ進む条件を書く。全ホスト・全API・全profileを一式指定せず、その変更の採否に必要な範囲を選ぶ。

「純退行なし」は、全指標が悪化していないことの証明を要求する条件にしない。公式仕様・明示された要求への適合と改善の因果方向が維持され、対処が必要な悪化を支持するEvidenceがなければ、改善量が未確認でもworkflowの条件に従って採用できる。公式の正当性条件やユーザーが明示した数値条件は緩めない。評価時は[workerの採否と修正](../isucon-worker/references/post-benchmark.md#採否と修正)に従い、採用と得点寄与の実証・追加投資の判断を分ける。

新しくREADYへ進めるカードは、既存の`evidence`で抽出できる部分を以下のJSONで指定する。採否の説明と機械抽出できない条件は`checks`・`note`へ残す。形式を埋めるための架空の参照や追加計測は要求しない。抽出可能な指標がない場合は自由文でもよいが、確認対象と判断条件は具体化する。

既存の自由文カードは一括変換しない。workerは初回確認時に必要な参照先を整理し、その結果を今回の確認で再利用する。形式統一だけを目的にAPPLIEDカードの宣言を更新しない。

## 既存CLIが扱う形式

`Evaluation`全体をversion 1 JSONにする（`json`コードフェンスも可）。数値の自動合否判定ではなく、比較値を取り出すための指定である。

```json
{
  "version": 1,
  "artifacts": ["alp.json", "slp.tsv"],
  "endpoints": [
    {
      "name": "icon-post",
      "artifact": "alp.json",
      "method": "POST",
      "uri": "/api/icon",
      "metrics": ["count", "avg", "p99", "2xx", "4xx", "5xx"]
    }
  ],
  "checks": [
    "ID列挙を除去する変更の例: slp.tsvでSELECT `id` FROM `icons` WHERE `user_id` = Nの消失を確認し、置換後DELETEを含むSQL回数・時間を投稿件数あたりで比較する。両RUNのartifact有効性と収集窓を先に確認する。",
    "保存済みの新ID発行・重複画像・rollback検証を再利用し、対象RUNの関連APIと同負荷窓のエラーを確認する。往復削減の方向と正確性が維持され、関連する純退行がなければ採用する。悪化時は置換後SQLと投稿待ちを調べ、同境界で修正可能か判断する。"
  ],
  "note": "参照方法の例であり、そのまま他カードへ転記しない。SQL行の不在はtsv.matchで表現できないためchecksへ記載。処理量・同時変更・比較不能な値を区別し、スコア差だけでは採否を決めない。"
}
```

使用するキーだけ指定する。非空の参照を確定する前に、保存済みSource/Compare RUNでheader、完全一致値、関数名を確認する。未実装のSQL・関数など、まだ成果物に存在しない対象は予定と確認方法を`checks`に書く。

| キー | 指定内容と限界 |
| --- | --- |
| `artifacts` | 使用する成果物名。`run.json`のstatusを確認する。欠損は0ではない |
| `endpoints` | `name`, `artifact`, `method`, `uri`, `metrics`。alpのmethod・uriセルと完全一致。uriに正規表現が保存されている場合も、その文字列を指定する。列名は実在する`count`, `avg`, `p99`, `5xx`などを使う |
| `tsv` | `name`, `artifact`, `match`, `metrics`。`match`は列名とセル値の完全一致。複数一致時は最後の行で、合計・時系列積分はしない。SQLは抽象化後のバッククォート・`N`・`'S'`・`LIMIT`まで転記し、ソースの`?`や部分文字列を使わない |
| `profiles` | `name`, `artifact`, `binary`, `symbol`, `absent`。`go tool pprof -list`の表示と`absent`文字列の有無を要約する。任意の累積時間・配下全体の集計ではない。binaryとの対応とサンプルの限界を確認し、表示上の不在を処理量0と断定しない |
| `checks` | 機構と指標の関係、採否条件、追加集計の実行コマンド・RUNの指定方法・結果の読み方、SQL消失・正確性・別SQLへの置換など人が確認する手順。CLIは表示するが自動判定しない |
| `note` | 比較条件、未観測、個別寄与を分離できない条件、参照方法の限界 |

## 集計の実行方法をカードに残す

investigateは採否条件と比較値の取得方法を対応付けて`Evaluation`へ記載する。既存`evidence`で取得できる項目は構造化指定を使い、重複したコマンド記載は求めない。追加集計が必要な項目は`checks`へ、実行可能なSQLを含む`task q`などのコマンド、比較元・対象RUNの指定方法、結果の読み方を残す。単位・母数・時間窓と欠損・比較不能時の扱い、同時変更による帰属の限界は`checks`または`note`に明記する。

SQL形状が変わる前後の合算や時系列の結合も既存DuckDB基盤を優先する。再利用する集計は、計算方法と、比較RUN・対象RUN・対象API/SQL/関数・出力先の指定を分ける。既存のSQLを優先し、長い処理や繰り返し使う処理だけをファイル化する。その場合は呼び出しコマンドと引数を各カードに残し、RUNごとの一括文字列置換で集計定義ごと複製し続けない。関数名だけでなく、profile種別・sample種別・包含を除く集計範囲が前後で対応するか確認する。

再利用するスクリプトは入力と出力を確認する。データ抽出とSQL生成を分け、抽出の実行で比較SQLや他工程の出力を上書きしない。既存の取得方法で判断できる場合、共通化だけを目的とした大量移行や計測基盤の変更へ広げない。

workerは実装前に取得方法を比較元RUNで確認し、実行したRUN、確認結果、成果物への参照をResultまたはHistoryへ記録する。同じ集計定義・RUNで確認済みなら結果を再利用する。未実装のSQL・関数は予定として区別し、実装レビュー時に旧参照→新参照、除去された処理、追加費用を確認する参照をEvaluationへ補完する。必要な行番号条件も実装に合わせ、旧参照だけを抽出して新経路が抜けないようにする。コードで確定した参照と実負荷成果物での抽出確認は区別し、未収集・未一致を処理量0としない。比較元RUNや必要な成果物がない場合は不足理由を残し、その解消だけを目的に追加計測や実装停止を要求しない。採否条件自体の変更が必要なら理由を記録し、取得方法の補完と区別する。

採否条件と、次の探索の優先度を見直す観測は区別する。後続操作の変化を確認できる既存指標があれば、その参照先と、どの結果をObjective／Target担当へ返すかをchecksに簡潔に残す。新しい計測や全体診断を全カード共通の必須条件にせず、共通観測は参照で共有する。

## 比較要約の入口

```shell
task backlog -- evidence --run <RUN_ID> B-001,B-002
task backlog -- evidence --format json --run <RUN_ID> B-001,B-002
```

対象RUNを明示し、同じRUNのカードはまとめて取得する。要約には自動合否判定がなく、自由文カードでは指標を自動抽出しない。警告・未抽出の`checks`・採否を左右する不足だけを元成果物で補い、根拠が揃ったカードは追加調査を終える。実行手順は[workerのベンチ後手順](../isucon-worker/references/post-benchmark.md)を参照する。
