# Evaluationの指定方法

investigateはREADY確定時に、workerは実装前の取得方法確認時に、verifierはベンチ後に参照方法を解釈する必要があるときに読む。採用条件は[workflow](../../../tools/backlog/backlog-workflow.md#adoption)、比較・欠損・因果の扱いは[Evidence](evidence.md)に従う。

## 役割

`Evaluation`は検証項目の一覧ではなく、Interventionの採否を決めるための判断条件である。結果が採用・限定修正・不採用の判断を変え得る条件だけを、確認対象とEvidence、比較条件、判定の関係が分かる形で記載する。

公式仕様の正当性・認証・初期化・再起動後の永続性など、変更境界に該当する共通条件は省略しない。一方、原因調査の候補、参考計測、次の探索のためだけの観測、workerの実装・deploy手順は`Evaluation`へ混ぜず、`Unknowns`・`Result`・Historyまたは保存済みEvidenceへ記録する。

確認項目の数や本文の長さに固定上限は設けない。変更境界が広ければ評価範囲も広くなり得るが、各項目について変更境界との関係と、結果が採否をどう変えるかを説明できなければREADYへ進めない。

## 何を指定するか

`Evaluation`には、改善対象の機構、変更によって直接影響を受ける処理、正確性条件について、**何を読んで何を判断するか**を対応付ける。成果物名だけでなく、対象API・SQL行・profile関数などの参照先と指標、単位・母数・時間窓、採用・限定修正・不採用へ進む条件を書く。参照先を列挙すること自体を目的にせず、採否条件に必要な範囲だけを記載する。

新しくREADYへ進めるカードは、既存の`evidence`で抽出できる部分を以下のJSONで指定する。採否条件と機械抽出できない判断は`checks`・`note`へ残す。形式を埋めるための架空の参照や追加計測、採否を変えない調査項目は要求しない。抽出可能な指標がない場合は自由文でもよいが、確認対象と判断条件は具体化する。

自由文で記載する場合は、次の形を基本にする。`非退行`は変更から直接影響を受ける場合だけ書き、該当しなければ省略する。

```text
採用条件:
- 正当性: <変更に関係する必須条件>
- 主効果: <Hypothesisを直接評価するEvidence>
- 非退行: <変更から直接影響を受ける条件>

比較条件:
- <Compare Run、負荷条件、時間窓、同時変更>

差し戻し条件:
- <どの失敗ならDOINGへ戻すか>
```

既存の自由文カードは一括変換しない。workerは実装前、verifierはベンチ後の初回確認時に必要な参照先を整理し、その結果を今回の確認で再利用する。形式統一だけを目的にAPPLIEDカードの宣言を更新しない。

## 既存CLIが扱う形式

`Evaluation`全体をversion 1 JSONにする（`json`コードフェンスも可）。数値の自動合否判定ではなく、比較値を取り出すための指定である。

```json
{
  "version": 1,
  "artifacts": ["alp.json", "slp.tsv"],
  "endpoints": [
    {
      "name": "icon-post",
      "artifact": "alp.json",
      "method": "POST",
      "uri": "/api/icon",
      "metrics": ["count", "avg", "p99", "2xx", "4xx", "5xx"]
    }
  ],
  "checks": [
    "採用条件: ID列挙を除去する変更により、対象投稿のSQL仕事が比較可能な単位で減少し、保存済みの正確性確認が維持される。",
    "差し戻し条件: 対象APIの正確性違反、または変更に帰属する純退行が確認され、同じChange boundary内の修正が必要である。"
  ],
  "note": "参照方法の例であり、そのまま他カードへ転記しない。比較RUN、単位、母数、時間窓、欠損・比較不能時の扱いを明記し、スコア差だけでは採否を決めない。"
}
```

使用するキーだけ指定する。非空の参照を確定する前に、保存済みSource/Compare RUNでheader、完全一致値、関数名を確認する。未実装のSQL・関数など、まだ成果物に存在しない対象は予定と確認方法を`checks`に書く。

| キー | 指定内容と限界 |
| --- | --- |
| `artifacts` | 使用する成果物名。`run.json`のstatusを確認する。欠損は0ではない |
| `endpoints` | `name`, `artifact`, `method`, `uri`, `metrics`。alpのmethod・uriセルと完全一致。uriに正規表現が保存されている場合も、その文字列を指定する。列名は実在する`count`, `avg`, `p99`, `5xx`などを使う |
| `tsv` | `name`, `artifact`, `match`, `metrics`。`match`は列名とセル値の完全一致。複数一致時は最後の行で、合計・時系列積分はしない。SQLは抽象化後のバッククォート・`N`・`'S'`・`LIMIT`まで転記し、ソースの`?`や部分文字列を使わない |
| `profiles` | `name`, `artifact`, `binary`, `symbol`, `absent`。`go tool pprof -list`の表示と`absent`文字列の有無を要約する。任意の累積時間・配下全体の集計ではない。binaryとの対応とサンプルの限界を確認し、表示上の不在を処理量0と断定しない |
| `checks` | 採用・限定修正・不採用へ進む判断条件と、その判断に必要な取得方法。採否を変えない調査項目の一覧にはしない。CLIは表示するが自動判定しない |
| `note` | 比較条件、未観測、個別寄与を分離できない条件、参照方法の限界。採否条件と参考観測を混同しない |

## 集計の実行方法をカードに残す

investigateは、各採否条件を判断するための取得方法を`Evaluation`へ対応付ける。既存`evidence`で取得できる項目は構造化指定を使い、重複したコマンド記載は求めない。追加集計が採否に必要な場合だけ、`checks`へ実行可能なSQLを含む`task q`などのコマンド、比較元・対象RUNの指定方法、結果の読み方を残す。単位・母数・時間窓と欠損・比較不能時の扱い、同時変更による帰属の限界は`checks`または`note`に明記する。採否を変えない追加調査は`Unknowns`・`Result`・Historyまたは保存済みEvidenceへ分ける。

SQL形状が変わる前後の合算や時系列の結合も既存DuckDB基盤を優先する。再利用する集計は、計算方法と、比較RUN・対象RUN・対象API/SQL/関数・出力先の指定を分ける。既存のSQLを優先し、長い処理や繰り返し使う処理だけをファイル化する。その場合は呼び出しコマンドと引数を各カードに残し、RUNごとの一括文字列置換で集計定義ごと複製し続けない。関数名だけでなく、profile種別・sample種別・包含を除く集計範囲が前後で対応するか確認する。

再利用するスクリプトは入力と出力を確認する。データ抽出とSQL生成を分け、抽出の実行で比較SQLや他工程の出力を上書きしない。既存の取得方法で判断できる場合、共通化だけを目的とした大量移行や計測基盤の変更へ広げない。

workerは実装前に、`Evaluation`にある採否条件の参照先が比較元RUNと実装範囲に対応することを確認し、実行したRUN、確認結果、成果物への参照をResultまたはHistoryへ記録する。同じ集計定義・RUNで確認済みなら結果を再利用する。実装時のテスト、未実装のSQL・関数の予定、追加の原因調査は`Result`・`History`・`Unknowns`へ分ける。採否条件自体の変更が必要なら理由を記録し、取得方法の補完と区別する。未収集・未一致を処理量0とせず、比較元RUNや必要な成果物がない場合は不足理由を残す。

採否条件と、次の探索の優先度を見直す観測は区別する。後続操作の変化を確認できる既存指標があれば、その参照先と、どの結果をObjective／Target担当へ返すかを`Unknowns`・`Result`・Historyへ簡潔に残す。新しい計測や全体診断を全カード共通の必須条件にせず、共通観測は参照で共有する。

## 比較要約の入口

```shell
task backlog -- evidence --run <RUN_ID> B-001,B-002
task backlog -- evidence --format json --run <RUN_ID> B-001,B-002
```

対象RUNを明示し、同じRUNのカードはまとめて取得する。要約には自動合否判定がなく、自由文カードでは指標を自動抽出しない。警告・未抽出の`checks`・採否を左右する不足だけを元成果物で補い、根拠が揃ったカードは追加調査を終える。実行手順は[verifierのベンチ後手順](../isucon-verifier/references/post-benchmark.md)を参照する。
