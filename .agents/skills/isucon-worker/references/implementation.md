# Implementation

今回選んだ着手範囲のREADYを順に実装・レビューし、完成した複数カードをdeployment batchとして統合検証・適用する。範囲は[workerの優先順](../SKILL.md#優先順)に従って引き継ぎ、カードごとのChange boundaryと採否は維持する。まとめて適用するためにカードを統合しない。

## カードの取得・実装

自分の未完成DOINGを先に処理する。自分のVERIFYは既存の検証結果と現在diffを照合してbatchへ含め、同じ変更境界の修正が必要ならDOINGへ戻す。APPLIEDの限定修正は[post-benchmark](post-benchmark.md)に従い、障害復旧は新規カードの蓄積より優先する。

1. 最新一覧からPriority・Owner・依存・競合と[APPLIED上限](../SKILL.md#優先順)を確認し、実装開始直前に対象READYを1枚だけ再読する。card version、改善目標・評価条件、TargetとObjectiveへのリンクがあればその内容、共通の有効性条件、Change boundaryを確認する。
2. 現在diffと共存できることを確認し、Owner設定と`READY -> DOING`を原子的に行う。
3. [Evaluationの指定方法](../../_shared/evaluation.md#集計の実行方法をカードに残す)に従い、カードに記載された取得方法を実装前に比較元RUNで確認する。未記載の追加集計はEvaluationへ補完し、参照先・単位・母数・時間窓と確認結果を記録する。同じ定義・RUNの確認済み結果とbatch共通の集計は再利用する。
4. 所有・排他・トランザクション・公開順序を変更する場合、変更に関係する通常経路・fallback・再試行について、所有やロックの取得と解放、経路選択や状態の確定時点、途中の状態変化への対応を実装前に整理する。正当性を左右する状態遷移は既存テストと照合し、不足する検証を実装の早い段階で行う。整理・検証の範囲は、今回変更する境界に応じて選ぶ。
5. 公式guardrailを保ちながら境界内だけを実装し、formatterとレビューを行う。必要なテストは変更とともに用意する。
6. [Evaluationの参照補完](../../_shared/evaluation.md#集計の実行方法をカードに残す)に従い、実装で確定した旧参照→新参照と追加費用の取得方法を補完する。実装・レビュー済みで統合検証待ちであることと変更範囲をHistoryへ記録し、DOINGのままbatchに保持する。これは未完成DOINGと区別し、同じ作業を繰り返さず次のREADYの取得判断へ進む。

各カードの差分を一貫した状態まで完成させてから次へ進む。同じファイルでも既存差分を保持して独立にレビューできるなら順に実装してよく、ファイルの重複だけでデプロイを分けない。構造化依存のrequired-statusは省略しない。

次の取得判断では、batchを区切る前に次の順序で依存を確認する。

1. batch内の実装・レビュー済みカードをVERIFYへ進めれば次のカードを取得できる場合は、先に必要な統合検証を行い、成功した先行カードをVERIFYへ進める。
2. 最新の状態・依存を再確認し、取得可能になったカードを同じbatchで実装する。この段階ではデプロイしない。
3. VERIFY依存を解消しても取得可能なカードがない場合や、次の実装に先行カードのAPPLIEDが必要な場合に、下記の区切り条件を判定する。検証失敗時は関係カードの修正を優先する。

## batchを区切る条件

次のいずれかまで、今回選んだ着手範囲内の取得可能なREADYを順に追加する。固定の少数件で区切ったり、1件の実装完了だけを理由に適用したりしない。

- 全Ownerの既存APPLIEDと今回適用予定のカードの合計が10件に達した。
- 上記のVERIFY依存の解消・再確認後も、今回選んだ着手範囲内にOwner・依存・競合の条件を満たして取得できるREADYがない。
- 次の実装にbatch内の先行カードのAPPLIEDが必要、または正規Task経路で一貫した完成snapshotとしてまとめて適用できない。
- 実装・レビューの失敗や具体的な外部条件により続行できない。
- ユーザー指定の件数・範囲を処理した、または停止指示がある。

区切った理由を記録する。未完成差分をデプロイ対象へ混ぜず、関係カードを修正または下記の状態へ収束させる。完成分だけを適用できると確認できた場合に限り、そのbatchを進める。分離できなければ適用を止め、残存差分と妨げを報告する。停止指示があれば追加の検証・適用を行わず現在状態を報告する。

## 統合検証とVERIFY

batchの実装・レビューが完了したsnapshotに、変更のリスクに必要なunit test、race、構文検査、クロスビルド、統合検査を各1回実行する。全体検証で覆える個別テストやビルドをカードごとに重ねない。失敗の切り分けや全体検証で覆えないguardrailの確認に必要な場合だけ個別検証を行う。成功済み検証は、後続変更や新たな不一致がその有効性へ影響する場合に限り再実行する。

成功後に各カードのResult・Historyへ変更範囲と検証結果を記録し、最新versionを確認して`DOING -> VERIFY`へ進める。失敗時は関係カードと、その修正に依存するカードをDOINGに保つ（VERIFYならDOINGへ戻す）。修正後は影響範囲を再検証する。

## まとめて適用

適用直前に全対象がVERIFYであること、現在diffと検証済みsnapshotの一致、他作業の未完成差分を含まないこと、Taskfileの役割・ホスト・影響、進行中RUN、全OwnerのAPPLIED件数を再確認する。既存APPLIEDと今回適用予定のカードをIDで重複排除して数え、デプロイ後にAPPLIEDが10件を超える場合はデプロイしない。ちょうど10件になる場合は適用できる。他workerの適用もこの直前確認に含める。

batch全体を反映できる最小の正規`task deploy-*`経路でまとめて適用する。同じcomponentの転送・restart/reloadをカードごとに繰り返さない。複数componentやschemaを含む場合は現行Taskfileの正規経路を選び、必要な実行順を守る。

本番確認もbatch単位で1回行う。変更が実効する経路に必要なservice・log・代表endpoint・設定hashなどを確認し、カード間で共通する確認は共有する。成功後だけ各対象を`VERIFY -> APPLIED`へ進める。各Historyへbatchの対象ID、Task・host/service・restart/reload、snapshot、共有の検証結果と次の手動ベンチで判定する内容を残す。

適用や本番確認に失敗した場合は部分適用と原因を確認し、関係カードをDOINGへ戻して限定修正・再検証・正規deployを行う。成功を確認できないカードをAPPLIEDにしない。

## 差し戻しと継続

無関係なリファクタを混ぜない。一枚のカード内に別々に採否を判断すべき独立変更が見つかった場合や、境界・因果の再調査が必要になった場合は実装を止め、Ownerを外してINVESTIGATEへ差し戻す。具体的な外部待ちは[workflowのBLOCKED条件](../../../../tools/backlog/backlog-workflow.md#blocked)に従って記録する。実装上の不具合と改善仮説の反証を区別し、同じ境界の修正を優先する。技術的反証や公式仕様・明示された要求への違反により、改善仮説を保った修正が成立しないと判断できる場合は、根拠を記録しREJECTEDにする。適用後の問題は[悪化時の判断と復旧](post-benchmark.md#悪化時の判断と復旧)に従う。

batchの適用・カード更新後は[継続・終了手順](../../_shared/card-continuation.md)で最新一覧を確認し、APPLIED枠に余地があり選択範囲内に取得可能なREADYがあれば次のbatchを続ける。具体的な外部条件で適用できない場合はその状態と再開条件を報告する。
