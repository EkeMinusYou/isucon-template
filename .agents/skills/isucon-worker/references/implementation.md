# Implementation

全READYを[workerの優先順](../SKILL.md#優先順)に従って順に実装・レビューし、完成した複数カードをdeployment batchとして統合検証・適用する。ユーザーが明示した対象制限を守り、カードごとのChange boundaryと採否は維持する。まとめて適用するためにカードを統合しない。

## カードの取得・実装

自分の未完成DOINGを先に処理する。自分のVERIFYは既存の検証結果と現在diffを照合してbatchへ含め、同じ変更境界の修正が必要ならDOINGへ戻す。OwnerなしDOINGは下記の是正手順で取得する。障害復旧は新規カードの蓄積より優先する。

取得条件とChange boundaryを確認したら、READYを取得して実装へ進む。難しさや変更規模だけを理由に着手を延期したり、差し戻し理由を探したりしない。境界内の実装判断はworkerが解決する。境界・正当性・因果について追加調査が必要と判明した場合は、確認した事実・未解決の問い・実装への影響を記録し、[差し戻し手順](#差し戻しと継続)に従ってINVESTIGATEへ戻す。具体的な問題が既に判明している場合、差し戻すためだけのコード編集は不要。

1. 最新一覧からPriority・Owner・依存・競合を確認し、実装開始直前に対象READYのversionと取得条件を確認する。[取得範囲と再利用](../../_shared/card-continuation.md#取得範囲と再利用)に従い、改善目標・評価条件、TargetとObjectiveへのリンクがあればその内容、共通の有効性条件、Change boundaryの未確認部分を読む。
2. 現在diffと共存できることを確認し、空のOwnerと最新versionを条件に、Owner設定と`READY -> DOING`を原子的に行う。
3. [Evaluationの指定方法](../../_shared/evaluation.md#集計の実行方法をカードに残す)に従い、カードに記載された取得方法を実装前に比較元RUNで確認する。未記載の追加集計はEvaluationへ補完し、参照先・単位・母数・時間窓と確認結果を記録する。同じ定義・RUNの確認済み結果とbatch共通の集計は再利用する。
4. 公式guardrailを保ちながら境界内だけを実装し、formatterとレビューを行う。必要なテストは変更とともに用意する。
5. [Evaluationの参照補完](../../_shared/evaluation.md#集計の実行方法をカードに残す)に従い、実装で確定した旧参照→新参照と追加費用の取得方法をEvaluationへ補完する。この補完と、実装・レビュー済みで統合検証待ちであることと変更範囲のHistoryへの記録を、1回の`update`にまとめる。DOINGのままbatchに保持し、未完成DOINGと区別して、同じ作業を繰り返さず次のREADYの取得判断へ進む。

各カードの差分を一貫した状態まで完成させてから次へ進む。同じファイルでも既存差分を保持して独立にレビューできるなら順に実装してよく、ファイルの重複だけでデプロイを分けない。構造化依存のrequired-statusは省略しない。

次の取得判断では、batchを区切る前に次の順序で依存を確認する。

1. batch内の実装・レビュー済みカードをVERIFYへ進めれば次のカードを取得できる場合は、先に必要な統合検証を行い、成功した先行カードをVERIFYへ進める。
2. 最新の状態・依存を再確認し、取得可能になったカードを同じbatchで実装する。この段階ではデプロイしない。
3. VERIFY依存を解消しても取得可能なカードがない場合や、次の実装に先行カードのAPPLIEDが必要な場合に、下記の区切り条件を判定する。検証失敗時は関係カードの修正を優先する。

## batchを区切る条件

次のいずれかまで、新着を含む取得可能な全READYを順に追加する。固定の少数件で区切ったり、1件の実装完了だけを理由に適用したりしない。

- 上記のVERIFY依存の解消・再確認後も、全READYにOwner・依存・競合の条件を満たして取得できるREADYがない。
- 次の実装にbatch内の先行カードのAPPLIEDが必要、または正規Task経路で一貫した完成snapshotとしてまとめて適用できない。
- 是正を新規READYの実装待ちで遅らせるべきでない、または実装・レビューの失敗や具体的な外部条件により続行できない。
- ユーザー指定の件数・範囲を処理した、または停止指示がある。

区切った理由を記録する。未完成差分をデプロイ対象へ混ぜず、関係カードを修正または下記の状態へ収束させる。完成分だけを適用できると確認できた場合に限り、そのbatchを進める。分離できなければ適用を止め、残存差分と妨げを報告する。停止指示があれば追加の検証・適用を行わず現在状態を報告する。

## 統合検証とVERIFY

検証範囲は、公式guardrailと変更境界から、今回の変更によって壊れ得る動作に絞る。既存テスト・保存済み検証で確認できる部分を再利用し、不足する部分だけ検証を追加する。専用の検証計画書やチェックリストは作らない。

batchの実装・レビューが完了したsnapshotに、必要なunit test、race、構文検査、クロスビルド、統合検査を選んで各1回実行する。列挙した検査を一式必須とはせず、AGENTS.md等で明示された必須検査は維持する。全体検証で覆える個別テストやビルドをカードごとに重ねない。

必要な検証が成功したらVERIFYへ進め、batchの区切り条件に従って適用へ進む。追加確認・再実行は、具体的な失敗、不一致、今回の変更に関係する未確認の故障条件、または確認済み結果に影響する変更がある場合に限り、その範囲だけ行う。網羅性や安心感を高めることだけを目的に検証を増やさない。この終了条件はデプロイ後の本番確認にも適用する。

成功後に各カードのResult・Historyへ変更範囲と検証結果を記録し、最新versionを確認して`DOING -> VERIFY`へ進める。失敗時は関係カードと、その修正に依存するカードをDOINGに保つ（VERIFYならDOINGへ戻す）。修正後は影響範囲を再検証する。

検証・ビルド・deployの実行ログや作業用スクリプトは一時ディレクトリへ置き、再利用に必要なコード・構成の時点、コマンド、結果、確認範囲と必要な抜粋をResult・Historyへ残す。

## まとめて適用

適用直前に全対象がVERIFYであること、現在diffと検証済みsnapshotの一致、他作業の未完成差分を含まないこと、作業ディレクトリ、Taskfileの役割・ホスト・影響、進行中RUNを再確認する。APPLIEDの件数では取得・適用を止めない。

batch全体を反映できる最小の正規`task deploy-*`経路でまとめて適用する。同じcomponentの転送・restart/reloadをカードごとに繰り返さない。複数componentやschemaを含む場合は現行Taskfileの正規経路を選び、必要な実行順を守る。

本番確認もbatch単位で1回行う。変更が実効する経路に必要なservice・log・代表endpoint・設定hashなどを確認し、カード間で共通する確認は共有する。成功後だけ各対象を`VERIFY -> APPLIED`へ進め、`--expect-owner <自分> --release-owner`でOwner解除も同時に行う。CLIが発行した新しいapplication_idを確認してverifierへ渡す。不採用に伴う是正対象もAPPLIEDへ戻し、下記の是正手順で次の手動ベンチを待つ。状態変更とOwner解除を行うtransitionのreasonに、batchの対象ID、Task・host/service・restart/reload、snapshot、共有の検証結果と次の手動ベンチで判定する内容を含める。application_idはCLIが同じHistoryへ追記する。引き渡したカードには以後書き込まない。

適用や本番確認に失敗した場合は部分適用と原因を確認し、関係カードをDOINGへ戻して限定修正・再検証・正規deployを行う。成功を確認できないカードをAPPLIEDにしない。

## 差し戻しと継続

無関係なリファクタを混ぜない。一枚のカード内に別々に採否を判断すべき独立変更が見つかった場合や、境界・因果の再調査が必要になった場合は実装を止め、Ownerを外してINVESTIGATEへ差し戻す。具体的な外部待ちは[workflowのBLOCKED条件](../../../../tools/backlog/backlog-workflow.md#blocked)に従って記録する。適用前の候補に技術的反証や公式仕様・明示された要求への違反が判明した場合は、根拠を記録しREJECTEDにする。適用済みの変更は、下記の是正を完了するまでREJECTEDにしない。

batchの適用・カード更新後は[継続・終了手順](../../_shared/card-continuation.md)で最新一覧を確認し、OwnerなしDOINGまたは新着を含む全READYに取得可能なカードがあれば次のbatchを続ける。具体的な外部条件で適用できない場合はその状態と再開条件を報告する。

## verifierからの是正

開始時・各実装レビュー後・batch適用後・終了直前に`list --status DOING --unowned`も確認する。現在のカード本文と最新の引き渡しHistoryから、限定修正か不採用の是正か、根拠RUN・適用ID、帰属、是正する範囲、残す変更、完了条件を読む。過去Historyは不足した点だけ追加取得する。読み取り順と参考コマンドは[取得範囲と再利用](../../_shared/card-continuation.md#取得範囲と再利用)に従う。現在の適用ID・差分・依存と照合し、古い版への指示をそのまま実行しない。

`update --owner <worker-session> --expect-owner '' --expect-card-version <version>`で取得する。状態はDOINGのまま、取得理由をHistoryへ記録する。既存依存が退行している場合は、その是正も含む現在の依存関係を確認する。他Ownerのカードや差分を変更せず、必要な担当の引き渡しを先に行う。

- 限定修正: 同じChange boundaryの中で修正し、統合検証・VERIFY・正規deploy・本番確認後、新しい適用IDのAPPLIEDへ戻してOwnerを解除する。次のユーザー実行ベンチでverifierが再判定する。
- 不採用の是正: 現行コードと後続変更を確認し、必要な除去・修正を行う。batchやコミットを機械的にrevertして他カードを巻き込まない。旧実装への復元は必須ではなく、AGENTS.mdに従い専用のロールバック機構は追加しない。必要な検証・VERIFY・正規deploy・本番確認を終えてから`VERIFY -> APPLIED`とOwner解除を行い、CLIが発行した新しいapplication_idを確認する。reasonには`rejection-cleanup application`であること、復元・是正内容、チェック結果、次の手動ベンチでverifierがREJECTEDにすることを明記する。除去やdeployが不要なら、その根拠と確認結果を残して同じくAPPLIEDへ戻す。workerはREJECTEDへ遷移しない。

複数の是正は原則batchでまとめ、緊急の復旧や先行適用が必要な依存は理由を残して先に適用する。是正を新規READYの蓄積で遅らせない。検証・deployに失敗したカードはDOINGへ戻して是正を継続し、REJECTEDにしない。完了後は最新一覧から次の是正・READYへ進む。
