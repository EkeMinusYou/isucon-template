# 全面再設計の準備

[isucon-setup](../SKILL.md)で使う準備手順。旧アプリを標準計測付きで完成させる工程ではない。

## 取得するもの

1. 公式ルール、API・正当性・採点・初期化・復元・外部連携の資料を確認する。
2. 読み取り専用SSHで資源・実行環境・接続先を調べる。初期実装と設定、初期データ・画像・外部サービスの関連資材を正規の`task setup-*`で取得する。
3. 初期実装は、応答内容・状態遷移・境界条件の根拠として読む。テーブル、関数、プロセス分割を新設計へ写す理由にはしない。
4. 取得元の設定と、新実装を置く予定の設定を混同しない。新しいホスト配置・service・状態管理・初期化手順はbootstrapの設計で決める。

初期実装はGitの取得時点のcommit等から再参照できればよく、旧・新の実装を同じサービスで互換運用する仕組みは作らない。新実装の置き場所はビルド・配布しやすい構成にし、参考用コードや生成物を誤って配布しない。

## HARからポータル操作を準備する

- ジョブ投入のURL・method・対象・body、認証、返却ID、ポーリング、完了判定、スコア・合否・原文の取得元を確認する。秘密情報はGit対象外の環境変数へ渡す。
- まず`tools/contest/`の設定で表現する。設定で表せない通信・形式だけを共通ツールへ追加する。未観測の出力を推測で作らない。
- `task portal-bench-check`とHARの保存応答で検証する。実ジョブの投入は確認に必要な場合だけ行う。
- ベンチの実行・RUN回収は`task bench`を使う。進捗が提供されなければ観測不能とし、運営専用の出力を取得しない。
- 結果を読むときは参加者向け本文と`BENCHMARK_START/END`等の制御行を区別する。未解釈行の検証には、時刻付き制御行も含む実際の保存形式を使う。

## 新実装の検証へ渡すもの

使用できる資源、外部サービス、取得した仕様・初期データと、未確認点を示す。初期アプリの全計測導入や再デプロイは行わず、新実装に[標準計測](measurement.md)を接続する。

`task setup-check`・`task db-recreate`・`task setup-postflight`は、bootstrapで新実装の配置・初期化・計測が揃ってから実行する。既存の配布検査や操作ロックは維持する。schema取得などの機械的な注意点は[取得と構文検査](../../../../tools/setup/README.md)を参照する。
