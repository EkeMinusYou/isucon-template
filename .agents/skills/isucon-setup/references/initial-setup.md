# 準備とセッション分離

setupは既存ソースを参照して振る舞いを抽出し、bootstrapはそのソースを読まずに設計する。両者は別セッションで実行する。

## 調査するものと保存先

1. 公式ルール・外部仕様を先に読み、初期実装を照合して入力・応答・状態遷移・境界条件を確認する。内部のクラスやテーブルではなく、利用者から観測できる操作単位で整理する。
2. `task setup`は業務ロジックを持たない汎用Go土台の`APP_DIR`を維持し、旧アプリを`REFERENCE_DIR/webapp/`へ取得する。`REFERENCE_DIR`の既定はリポジトリと別の隣接ディレクトリであり、リポジトリ内を指定できない。振る舞いの確認に必要な内部設定も同じ調査用領域へ取得する。
3. CPU・メモリ・disk・network、提供データ、外部サービスを確認する。管理対象ホストの停止対象unitと、nginxが引き継ぐ公開port・証明書等は運用条件として記録し、旧構成を新設計への要求にしない。
4. 仕様とソースが矛盾する場合や、ソースだけでは外部の意味が確定しない場合は、観測事実・実装の挙動・未確認点を区別する。必要なら許可された公開APIの入出力で確認する。

旧ソースは調査用領域に置いたままにし、新実装ディレクトリやリポジトリの履歴へコピーしない。取得先に旧ソースが混ざっている場合は、bootstrap用にはそれを含まない作業場所を用意する。

提供データはGoがファイルから直接読める形式へ取り出す。元のDBサービスや内部スキーマがなくても初期状態を再現できる内容とし、変換時の件数・参照関係等を照合する。証明書など秘密情報はGitへ入れず、必要な配置条件だけを渡す。nginxの取得済み設定も他の初期ソースと同様に`REFERENCE_DIR`へ置き、リポジトリにはコピーしない。公開listener・証明書参照・静的URLの外部要件を`docs/behavior.md`へ整理し、新しい設定の作成はbootstrapへ任せる。`/etc/nginx/mime.types`は各ホストの標準ファイルを保持する。TLS資材は`nginx/tls/`などGit対象外かつ配布時の削除対象外に置く。

## 操作をまたぐ仕様と初期データの確認

各APIの通常経路を読むだけでは、別の操作が変える受付条件・一覧の対象・集計値・通知順序を取りこぼす。外部に返す値と業務上の判定から、それを変える操作を逆にたどって抽出を閉じる。初期ソース側で照合に使う内部の識別子や参照先はsetupの調査領域に留め、引き継ぎには外部動作だけを記す。

### 判定・応答と更新操作の照合

受付可否、検索対象、上限・残数、集計、通知順序など、新実装の正当性に関係する条件ごとに、次を照合する。

- 何を満たすと条件が成立するか。その条件を変える操作はどれか。作成だけでなく、割当、完了、通知、取消等のうち実際に関係する操作を追う。同じ対象でも、検索に出す条件と次の処理を受理する条件が同一とは限らない。
- 更新の受理、業務上の確定、外部副作用の成功、通知の送信・受信のうち、どの出来事から次の操作へ反映されるか。日時を返す場合は、その時刻が何を表すかと、対象データを選定する時点との関係を確認する。反映猶予は明記された対象だけに適用する。
- 関係する更新の直前・直後に後続の照会や更新を行うと、何が許されるか。公開仕様の保証、参照動作、競合時に未確認の部分を分ける。全組合せの競合試験は要求しないが、未確認部分を通常経路から推測で保証しない。

照合結果は業務シナリオに沿って`docs/behavior.md`へ残す。条件の成立・解除と後続操作への効果が読み取れればよく、固定の表形式やソースの逐語訳は不要。

### 初期値の業務上の意味と充足性

上で抽出した判定を、提供初期状態から実行できるか確認する。件数・hash・参照先の一致は変換の完全性の確認であり、判定に必要な値が揃ったことの確認とは分ける。

- 残数・累積数・利用済み状態等について、初期値を直接提供するか、提供データだけで導ける計算規則と照合結果を示す。0も確認した値として明記する。
- 履歴や特典等から現在の状態を復元する場合、結び付けるID・コードと対象期間が実際に一致するか確かめる。不一致を見つけたら、類似した件数等で代用せず、参照動作でその履歴が現在の判定に含まれるか調査する。
- 必要な初期値が導けなければ、setupで値または外部動作を追加抽出する。引き継ぎ先が旧ソースを開く、過去の対応関係を推測する、未確認の値を0で埋める必要が残る状態を完了扱いにしない。

### 完了前の照合と報告

正当性に関係する判定ごとに、根拠、関連する更新操作、後続操作で見える結果、必要な初期値が説明されているか見直す。欠けた箇所は調査へ戻す。公開資料や許可された調査から確定できない場合は、未規定・参照動作のみ・未検証などを区別し、実装判断に残る不確実性を示す。まだ調べていないことを「未規定」としない。

完了報告では、ソース照合、提供データとの照合、公開APIでの観測、ベンチによる検証の範囲を区別する。APIパスがすべて記載されているだけで「全機能の振る舞いを確認済み」とは述べない。

## HARからポータル操作を準備する

- ジョブ投入のURL・method・対象・body、認証、返却ID、ポーリング、完了判定、スコア・合否・原文の取得元を確認する。秘密情報はGit対象外の環境変数へ渡す。
- まず`tools/contest/`の設定で表現する。設定で表せない通信・形式だけを共通ツールへ追加する。未観測の出力を推測で作らない。
- `task portal-bench-check`とHARの保存応答で検証する。ベンチの実行・RUN回収は`task bench`を使う。進捗が提供されなければ観測不能とし、運営専用の出力を取得しない。
- 結果を読むときは参加者向け本文と`BENCHMARK_START/END`等の制御行を区別する。未解釈行の検証には、時刻付き制御行も含む実際の保存形式を使う。

## bootstrapへ渡す内容

`docs/behavior.md`には、次の設計入力を必要な詳細で残す。全ソースの翻訳や機械的な転記は行わない。

- 全API・操作の入力、認証、応答、エラー、並び順、検索・比較、時刻・IDの意味。
- 操作前後の業務状態と後続操作への効果。同時更新、重複、更新の可視性、外部副作用、失敗時の結果。
- 初期状態、初期化・通常再起動後の要件、互換性に必要なデータの意味・表現。
- 得点条件と操作の依存関係。取得できる結果・進捗と、観測できない範囲。
- 資源・実行環境・外部接続・必要な運用識別子、提供データと利用可能なツール。
- 各仕様の確認範囲と未確認点。ソース照合で得た事実は外部動作として説明する。

コード片、内部ファイル・関数名、テーブル設計、process間の役割分担、旧実装の律速、採用を勧める新アーキテクチャーは含めない。内部まで説明する公式資料やsetup会話へのリンクを設計入力として渡さない。詳細なソース照合の根拠はsetup側で管理する。
必要なデータ・ポータル設定とこの仕様をcommitし、別セッションで`$isucon-bootstrap docs/behavior.md`を依頼する。会話のコピー・要約をbootstrapのコンテキストに入れない。

bootstrapで仕様不足が見つかった場合は、setupセッションでその振る舞いを再調査して仕様を更新する。実装や内部構成を見せることで解決しない。
新実装は汎用土台のある`APP_DIR`へ作成し、新構成が揃ってから`task setup-check`・正規deploy・初期化・`task setup-postflight`を実行する。
