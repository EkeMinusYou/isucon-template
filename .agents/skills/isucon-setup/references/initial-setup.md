# 全面再設計の準備

[isucon-setup](../SKILL.md)で使う準備手順。旧アプリを標準計測付きで完成させる工程ではない。

## 取得するもの

1. 公式の外部仕様からAPI・正当性・採点・初期化・復元・外部連携の要件を整理する。
2. 資源・実行環境・公開接続先と、独立して提供された初期データ・画像等を確認する。初期アプリのソース、内部設定、SQLスキーマ、設計資料は取得しない。
3. 曖昧な振る舞いは、許可された公開APIに対する入力と応答、後続操作への効果から確認する。外部から確認できなければ不明点として残し、ソースを読むことで埋めない。
4. 外部仕様・観測した入出力・データの意味と形式・資源条件を設計入力として整理する。初期ソースを含む会話・要約を設計用の入力に渡さない。内部の関数名、テーブル構造、process配置、別試行の解法は含めない。

`task setup`は空の`APP_DIR`を作るだけで、旧実装を取り込まない。`task setup-webapp`や既存サーバー設定の一括取得は使わない。初期コードが既に作業ディレクトリにある場合は、その内容を読まずに設計用の別ディレクトリへ移る。
新実装は空の`webapp/go/`（既定の`APP_DIR`）へ作成する。ここを使うのはビルド・配布の入口を再利用するためであり、初期コードの上書き・改修ではない。

## HARからポータル操作を準備する

- ジョブ投入のURL・method・対象・body、認証、返却ID、ポーリング、完了判定、スコア・合否・原文の取得元を確認する。秘密情報はGit対象外の環境変数へ渡す。
- まず`tools/contest/`の設定で表現する。設定で表せない通信・形式だけを共通ツールへ追加する。未観測の出力を推測で作らない。
- `task portal-bench-check`とHARの保存応答で検証する。実ジョブの投入は確認に必要な場合だけ行う。
- ベンチの実行・RUN回収は`task bench`を使う。進捗が提供されなければ観測不能とし、運営専用の出力を取得しない。
- 結果を読むときは参加者向け本文と`BENCHMARK_START/END`等の制御行を区別する。未解釈行の検証には、時刻付き制御行も含む実際の保存形式を使う。

## 新実装の検証へ渡すもの

使用できる資源、外部サービス、外部仕様・提供データと、未確認点を示す。初期アプリの参照・計測導入・再デプロイは行わず、新実装に[標準計測](measurement.md)を接続する。

`task setup-check`・`task db-recreate`・`task setup-postflight`は、bootstrapで新実装の配置・初期化・計測が揃ってから実行する。既存の配布検査や操作ロックは維持する。新構成の資材配置や構文検査の機械的な注意点は[取得と構文検査](../../../../tools/setup/README.md)を参照する。
