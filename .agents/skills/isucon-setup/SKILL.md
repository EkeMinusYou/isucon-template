# ISUCON redesign setup

新しい内部構成を設計・実装できる状態を整える第1段階。外部仕様と公開APIの入出力から必要な振る舞いを整理し、初期実装のソースや内部構成は参照しない。
全機能の設計・実装と実負荷確認は[isucon-bootstrap](../isucon-bootstrap/SKILL.md)、新実装の継続改善は[isucon-agent](../isucon-agent/SKILL.md)が担当する。
実行許可・正規操作・commitは`AGENTS.md`に従う。

## 準備

[準備手順](references/initial-setup.md)に従う。

- 公式の外部仕様、独立して提供された初期データ・画像、外部サービスのAPI仕様を確認する。初期アプリのソース・SQLスキーマ・内部設定は取得しない。必要なデータと旧プログラムを区別し、認証値・秘密鍵はGitへ含めない。
- 読み取り専用SSHでCPU・メモリ・disk・networkを確認し、公式資料から公開された接続先・外部サービスを確認する。既存のprocess分割・SQL・service設定を設計材料として調べない。
- HARからポータルへの投入・状態取得・結果取得を設定する。`task portal-bench-check`と、保存された応答による読み取り検証を使う。
- `Taskfile.yml`の接続先・ターゲット環境を合わせ、`task setup`で空の実装先を用意する。資材は必要なファイルだけ取得する。新構成のrole・deploy・初期化を決めるのはbootstrapである。

旧実装のprofile導入、N+1・索引修正、再デプロイ、全ホストのDB再作成、全計測の実負荷確認をsetupの完了条件にしない。`task setup-check`はアプリ・配置・計測を検査するため、新実装が用意できたbootstrapで使う。
基準RUNは、得点比較や振る舞いの確認に必要で、初期環境を大きく作り直さず取得できる場合に限る。取得しない場合も次段階へ進める。ベンチを実行するなら既存の正規経路・検査を迂回しない。

## 完了条件

- 外部仕様と必要な提供データを参照でき、出典・取得不足・不明な外部動作が分かる。初期ソースや内部構成を設計入力へ含めていない。
- 使用できる資源、接続先、実行環境、ポータル操作・結果保存の設定が分かる。
- 新実装の配布・初期化・計測を組み込む入口が分かる。未確定の新構成を既にdeploy済みと報告しない。

完了報告は参照先・資源・未確認点を短く示す。専用の引き継ぎ資料作成は要求しない。設計・実装まで依頼されていればそのままbootstrapへ進む。

## 既存環境の計測補修

計測だけの補修依頼は[計測確認手順](references/measurement.md)を使う。対象RUNと生成・回収・解析の不足を切り分け、必要な箇所だけ修正する。解析側の修正は保存済みRUNで確認し、収集変更の実負荷確認が必要な場合だけ次RUNを取得する。準備段階全体は繰り返さない。
