# ISUCON redesign setup

初期実装のソース・設定と公式資料を参照し、必要な振る舞いを整理する第1段階。既存コードの参照はこのsetupセッションで行う。
新構成の設計・実装は、初期ソースを読んでいない別セッションの[isucon-bootstrap](../isucon-bootstrap/SKILL.md)が担当する。setup中に新構成や最適化案を決めない。
実行許可・正規操作・commitは`AGENTS.md`、具体的な手順は[準備とセッション分離](references/initial-setup.md)に従う。

## 準備と振る舞いの抽出

- 公式資料と初期実装から、入力・応答・エラー・状態遷移・更新の可視性・初期化・復元・外部副作用を確認する。公式仕様と実装が異なる場合は区別する。
- 調査用ソースは`REFERENCE_DIR`へ取得する。新実装の`APP_DIR`やGit履歴へ旧ソースを入れない。内部設定も、振る舞いと運用条件の確認に必要な範囲で参照してよい。
- `task setup-nginx`で調査用に取得した設定から、公開URL・TLS証明書の配置・body上限・静的資材とキャッシュの更新条件・SSE/WebSocket等を抽出する。同梱nginx設定へ公開契約に必要な部分を反映し、旧upstreamやアプリ内部構成は持ち込まない。
- 資源・実行環境・公開接続先・外部サービスを確認する。使用可能な資源と、旧実装が選んだ配置を混同しない。
- HARからポータル操作と結果保存を設定し、`task portal-bench-check`と保存応答で検証する。基準RUNは必要で既存環境の大幅な変更なしに取得できる場合だけ使い、正規経路を迂回しない。
- 必要な初期データ・画像等は旧コードと分離する。データが旧スキーマに依存する場合は、このセッションで業務上の意味が分かるファイルへ取り出す。新実装がDBサービスや旧コードなしで初期状態を再現できるよう、形式・件数・整合性の確認範囲を記す。

旧アプリの性能改善・計測導入・再デプロイ、全ホストの状態初期化、全計測の実負荷確認はsetupの完了条件にしない。

## 別セッションへ渡す成果物

`docs/behavior.md`へ[引き継ぎ内容](references/initial-setup.md#bootstrapへ渡す内容)を保存する。これは設計の入力となる仕様であり、作業日誌やソースの構造説明ではない。
初期ソース、内部スキーマ・関数・process配置、旧実装の性能分析、新設計の提案、setupの会話履歴は渡さない。

次が揃ったらsetupを完了して、このセッションを終了する。

- 全機能の振る舞いと根拠・未確認点、提供データ、資源・接続・操作条件が分かる。
- 調査用ソースが実装先と分離され、設計入力へ混入していない。
- `docs/behavior.md`と必要なデータ・設定をcommitし、別セッションのbootstrapで使う参照先を短く報告した。

設計・実装まで一度に依頼されていても、このセッションでbootstrapを続けない。既存ソースを見ていない新しいセッションへ切り替える。

## 計測のみの補修

計測だけの依頼は[計測確認手順](references/measurement.md)を使い、生成・回収・解析の不足を切り分けて必要箇所だけ直す。bootstrapからの仕様確認依頼では、対象の振る舞いだけを調査して`docs/behavior.md`を更新し、旧ソースや内部構成は返さない。
