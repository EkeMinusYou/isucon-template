# ISUCON setup

3段階の第1段階として、初期環境の構築からベンチ実行・結果確認・計測の補修まで行い、標準計測を実負荷の分析に使える状態にする。性能改善とメモリ＋WAL移行は次段階の[isucon-bootstrap](../isucon-bootstrap/SKILL.md)、その後の自律改善は[isucon-agent](../isucon-agent/SKILL.md)が担当する。WALの存在や移行完了をsetupの条件にしない。
ユーザーがWebUIからベンチを実行した際のHARを参考に、ポータルの実行・状態確認・結果取得を設定し、必要ならベンチ実行ツールのコードを修正する。詳細は[HARからポータル実行を整える](references/initial-setup.md#harからポータル実行を整える)に従う。
スコアの記録方法も対象とし、生成元からRUNへの保存・分析まで整える。必要に応じてDuckDBの取り込みschemaと意味ビューも対応する。
既存環境の計測補修では、指定範囲とその生成・回収・読み手だけを調べ、初期構築全体を繰り返さない。
調査のみの依頼なら調査結果まで、整備の依頼なら必要なローカル修正・正規deploy・検証まで進める。

## 作業の選択と参照先

初期構築は[初回セットアップ](references/initial-setup.md)に従い、標準計測全件を「ベンチ前の整備」と「実RUNによる確認」に分ける。ベンチ未実行でも進められる作業を先に完了し、その後`task bench`を実行し、結果を確認して不足を補修する。既存環境の補修は下記の計測補修手順を使い、初期構築の手順はDB再作成フローなど該当箇所を補修する場合に参照する。

- `AGENTS.md`と`docs/official/`の関連資料。公式資料を優先する。
- [Tools](../../../tools/README.md)の基本方針と対象項目のチェックリスト。[RUNの比較](../../../tools/README.md#runの比較)がWALなしでも使えることを確認する。
- 計測を扱うときは[標準計測の確認手順](references/measurement.md)、Taskfileの役割・計測変数、collector/digester宣言。

## 作業境界

- Go採用、参考実装の参照専用扱い、生成物、クロスコンパイル、正規setup/deployはAGENTS.mdに従う。
- setup依頼には初回ベンチと計測補修に必要な検証を含む。対象ホスト・ポータルの実行対象を確認し、`task bench`で実行する。
- 作業環境・Taskfile・対象ホスト・進行中RUNの所有元を照合し、別環境を含め稼働中RUNへrestart・ローテート・計測条件変更を割り込ませない。
- 最適化の実装は行わず、初期構築と計測基盤の整備・補修に集中する。
- 既存の正規deploy経路を使う。DB再作成は`task db-recreate`へ分離し、通常の`task deploy-all`と分ける。
- 計測負荷比較と再起動後のスコア再現性検証は初期setupの完了条件に含めない。明示依頼時は別の検証範囲として扱う。

## 既存環境の計測補修

1. 対象RUNと実効設定を照合し、生成・起動条件・回収・形式・時刻・分析のどこで不足したかを切り分ける。
2. 対象ホスト、変更理由、元の値、適用方法を定め、出力側と回収・検査・読み手を一緒に修正する。
3. 変更に対応するテスト・構文検査・buildを行い、サーバー側変更があれば正規deployと疎通確認まで行う。
4. 保存済みRUNは上書きしない。分析側だけの修正は既存RUNで確認する。収集設定などを変更し実負荷の再確認が必要なら`task bench`で次RUNを取得する。

## 完了条件と報告

初回setupは、正規deploy、`task db-recreate`の整備、ベンチ実行、標準計測の実負荷での生成・回収・DuckDB分析まで確認して完了する。再作成対象と実機実行の有無・結果も報告する。
[ベンチ後の計測確認](references/initial-setup.md#ベンチ後の計測確認)に従い、結果原文・スコア・合否と各計測の内容・時間窓を確認し、不足を補修する。読み手の修正は既存RUNを使い、収集条件を変えた場合など必要な範囲で再実行する。
認証情報の不足やポータル停止などで進められない場合は、確認済みの範囲、阻害要因、必要な情報を報告する。setup由来の接続・初期化失敗は修正する。依頼範囲外のアプリの正当性失敗は切り分け、変更なしでベンチを繰り返さない。

計測ごとに対象ホスト・生成元・有効条件・回収先・読み手・根拠を会話で報告し、状態を
「実負荷で確認済み」「設定済み・実負荷未検証」「未設定」「取得失敗」「意図的に無効」「対象外」に分ける。
無効・対象外には理由を添える。初回setupでは標準計測全件、補修では依頼範囲について報告する。

ファイルの存在やヘッダーだけのfallback、HTTP 200だけで完了としない。対応する分析まで確認する。
baseline待ちは「設定済み、実負荷検証待ち」とし、全計測成立とは報告しない。
必須項目が未設定・取得失敗なら、その範囲のsetupは未完了。

RUN ID・合否・スコア、現行構成・配布commitと計測の確認根拠はRUNの成果物と会話で報告する。初期改善まで依頼されている場合は、setupの完了後に`isucon-bootstrap`へ続ける。
RUNがなければ会話で報告し、架空のRUNは作らない。報告ファイルはユーザーに指示された場合に保存する。
