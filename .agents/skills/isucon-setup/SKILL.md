# ISUCON setup

初期環境の構築と、標準計測を分析に使える状態にする作業を担当する。
スコアの記録方法も対象とし、生成元からRUNへの保存・分析まで整える。必要に応じてDuckDBの取り込みschemaと意味ビューも対応する。
既存環境の計測補修では、指定範囲とその生成・回収・読み手だけを調べ、初期構築全体を繰り返さない。
調査のみの依頼なら調査結果まで、整備の依頼なら必要なローカル修正・正規deploy・検証まで進める。

## 作業の選択と参照先

初期構築は[初回セットアップ](references/initial-setup.md)に従い、標準計測全件を「ベンチ前の整備・疎通確認」と「ユーザー実行RUNによる確認」に分ける。ベンチ未実行でも進められる作業を先に完了し、その後ユーザーへ初回ベンチを依頼する。既存環境の補修は下記の計測補修手順を使い、初期構築の手順はDB再作成フローなど該当箇所を補修する場合に参照する。

- `AGENTS.md`と`docs/official/`の関連資料。公式資料を優先する。
- [Tools](../../../tools/README.md)の基本方針と対象項目のチェックリスト。
- 計測を扱うときは[標準計測の確認手順](references/measurement.md)、Taskfileの役割・計測変数、collector/digester宣言。

## 作業境界

- Go採用、参考実装の参照専用扱い、生成物、クロスコンパイル、正規setup/deployはAGENTS.mdに従う。
- ベンチはユーザーが実行する。`task bench*`を含め代理実行しない。setup依頼をベンチ実行許可とみなさない。
- 作業環境・Taskfile・対象ホスト・進行中RUNの所有元を照合し、別環境を含め稼働中RUNへrestart・ローテート・計測条件変更を割り込ませない。
- 最適化の実装は行わず、初期構築と計測基盤の整備・補修に集中する。
- 既存の正規deploy経路を使う。DB再作成は`task db-recreate`へ分離し、通常の`task deploy-all`と分ける。
- 計測負荷比較と再起動後のスコア再現性検証は初期setupの完了条件に含めない。明示依頼時は別の検証範囲として扱う。

## 既存環境の計測補修

1. 対象RUNと実効設定を照合し、生成・起動条件・回収・形式・時刻・分析のどこで不足したかを切り分ける。
2. 対象ホスト、変更理由、元の値、適用方法を定め、出力側と回収・検査・読み手を一緒に修正する。
3. 変更に対応するテスト・構文検査・buildを行い、サーバー側変更があれば正規deployと疎通確認まで行う。
4. 保存済みRUNは上書きしない。実負荷の再確認が必要ならユーザーへ次RUNを依頼し、未検証範囲を明示する。

## 完了条件と報告

ベンチ前のsetupは、正規deploy、標準計測の生成・回収・DuckDB分析の疎通確認、`task db-recreate`の整備とdry-run確認で完了する。再作成対象と実機実行の有無・結果も報告する。
初回の実出力に依存する書式対応と実負荷確認は、[ベンチ後の計測確認](references/initial-setup.md#ベンチ後の計測確認)へ分離し、ベンチ前の完了条件に含めない。各保留項目に必要な出力・成果物と確認内容を示し、RUNがないことだけを理由に設定・adapter・読み手の整備を保留しない。
ベンチ前の必須作業が完了したら、対象worktree・ホストに合う実行コマンド、結果原文の保存方法、共有してほしいRUNを示してユーザーへベンチ実行を依頼する。ユーザーから結果が共有されたら、同じsetupの後段として確認を続ける。

計測ごとに対象ホスト・生成元・有効条件・回収先・読み手・根拠を会話で報告し、状態を
「実負荷で確認済み」「疎通確認済み・ベンチ待ち」「未設定」「取得失敗」「意図的に無効」「対象外」に分ける。
無効・対象外には理由を添える。初回setupでは標準計測全件、補修では依頼範囲について報告する。

ファイルの存在やヘッダーだけのfallback、HTTP 200だけで完了としない。対応する分析まで確認する。
baseline待ちは「設定・疎通確認済み、実負荷検証待ち」とし、全計測成立とは報告しない。
必須項目が未設定・取得失敗なら、その範囲のsetupは未完了。

RUNに紐づく結果はRUNの成果物と会話で報告する。
RUNがなければ疎通成果物と会話で報告し、架空のRUNは作らない。報告ファイルはユーザーに指示された場合に保存する。
