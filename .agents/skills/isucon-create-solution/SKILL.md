# ISUCON 共通の実装パターンを文書化する

異なる大会やアプリケーションで適用候補を探し、対象コードへ翻訳するための参照資料を作る。現行環境への適用評価は `isucon-use-solution` の役割とする。

## 調査と編集範囲

1. `AGENTS.md`、`docs/solutions/README.md`、`git status --short`、`rg --files docs/solutions docs/resources` を確認する。依頼されたテーマに近い既存文書を読み、目的・仕組み・適用条件が同じなら更新し、別のパターンなら新規作成する。テーマが未指定で会話からも決まらない場合は確認する。
2. 対象に関係する `docs/official/` と、`docs/resources/` のカタログ・公式解説・問題ソース・参加記を読む。ローカルのコード・schema・設定も根拠に使える。資料が示す事実、複数事例からの手法、適用時の推論、対象環境次第の未知を分ける。
3. **ISUCON13についてはWeb検索・取得を行わない。** ローカルの公式資料・保存済み資料を使う。他大会や一般技術について外部資料を使う場合は公式資料・原典を優先し、技術仕様は一次資料で確認する。リンクがローカル文書にあることを取得許可とみなさない。
4. 特定大会の名前・データ量・配置を一般則にせず、再利用できる機構と成立条件を抽出する。単一事例から一般化する場合は根拠の範囲を明示し、効果を断定しない。
5. `apply_patch` で対象の `docs/solutions/<slug>.md` と必要な `docs/solutions/README.md` の一覧だけを編集する。無関係な文書・コード・設定・公式資料・resources・Backlog は変更しない。

## 文書の形式

ファイル名は内容を表す小文字の kebab-case とし、`docs/solutions/README.md` が定める次の4章を含める。

- **概要**: 有効な問題と、削減する処理・待ち時間・資源、その機構。
- **適用条件・制約**: データ、構成、ランタイム、schema、適用できない条件。鮮度・整合性・認証認可・所有権・容量・複数ホスト・再起動後の復元など、対象に必要な制約。
- **探索方法**: 候補を見つけるファイル、シンボル、SQL、設定項目、検索語、呼び出し経路。「何が見つかれば適用候補か」を具体化する。
- **実装方法**: 正本と処理・データの流れ、変更方針、代表的なコード・SQL・設定例。置換すべき値と環境依存条件を明示する。

リポジトリ固有の例はその旨を書き、生成物の直接編集や設定値の無条件コピーを促さない。本文は日本語、例示コードのコメントは英語にする。利用した根拠は該当箇所または任意の「参考資料」章にリンクし、転載ではなく要約する。

計測手順・計測結果・採否判定基準・rollback 手順・作業履歴は solution 本文へ含めない。これらを追加章として必須化しない。build、deploy、service 操作、bench、Backlog 起票や分析レポート作成は行わない。

## 確認と完了報告

4章、成立条件と適用できない条件、具体的な探索方法、実装例の置換箇所、出典の裏付けとリンク先を確認する。カタログを追加・更新し、`git diff --check` を通す。作成・更新したファイルへのリンクと、扱うパターン・主要な適用条件を簡潔に報告する。
