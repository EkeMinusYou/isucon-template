# ISUCONの仮説検証ワークツリー

`main`では採用済みRUNを横断分析し、新しい仮説と優先順位を決めながらメインの改善を進める。別の改善仮説は一つのワークツリーに一つずつ割り当て、ユーザーが`docs/conversation/`の会話ログから選んだ仮説だけを扱う。ワークツリー内の分析は選ばれた仮説の調査と計測結果の評価に使う。仮説の出典となる会話と検証内容を確認してから着手する。仮説の履歴は会話ログとコミットに残し、曜日名に意味を持たせない。

## 作成と作業

1. `wt list`で使用中の名前を確認する。`monday`、`tuesday`、`wednesday`、`thursday`、`friday`、`saturday`、`sunday`の順に循環し、使用中の名前を飛ばして次の名前を使う。すべて空なら`monday`から始める。
2. `main`を起点に`wt switch --create <weekday> --base main`で作る。作成後は、そのワークツリーで選ばれた仮説を調査・実装する。ワークツリー管理には`wt`を使う。
3. 作成時のignoredファイルのコピーが終わったことを確認する。`runs/analysis.duckdb`はワークツリー固有の実ファイルとし、共有DBへのシンボリックリンクにしない。DB初期化用のignored資材もデプロイ前に揃える。コピーされていなければ`wt step copy-ignored --from main --to <weekday> --require-include`で補う。
4. 現行実装と保存済みRUNのEvidenceを調べ、仮説の効果と正当性を評価できる変更を実装する。検証対象のコード・設定は計測前にコミットし、計測時の状態を追えるようにする。

## デプロイと計測

仮説の選出や実装依頼だけではデプロイを許可されたとみなさない。ユーザーがこのワークツリーのデプロイを明示的に指示するまで、`task deploy-*`、`task apply-roles`などサーバーの状態を変える操作は行わない。指示後は`AGENTS.md`とTaskfileに従い、対象ホストと影響を確認して正規経路でデプロイする。

ベンチマーカーはエージェントが実行しない。ユーザーがこのワークツリーから計測し、RUN成果物を保存する。計測後はワークツリー固有のDuckDBへの同期を確認し、必要な場合に`task q-sync`を実行する。同条件の基準RUNとスコア・正当性・主要指標を比較し、採否前にはワークツリー作成後にmainへ追加されたRUNも確認する。欠損成果物や失敗RUNの扱いは`AGENTS.md`に従う。

## mainへの取り込み

計測結果の分析を担当ワークツリーの会話で報告する。ユーザーがその会話で採用とmainへのマージを指示したら取り込む。main側の会話から指示された場合も、対象のワークツリーとRUNを特定して同じ手順を使う。

効果と正当性を確認できた仮説だけをmainへ取り込む。対象の会話ログ、実装、RUN成果物、`runs/scores.tsv`がコミットされ、候補とmainの作業ツリーがcleanであることを確認する。`wt merge main`の既定はsquashとrebaseなので、計測したコミット履歴を保つためにワークツリーから`wt merge main --no-commit --no-rebase --no-ff`を使う。成功時は`wt`の既定の削除処理でワークツリーを片付ける。

競合は変更の意図とRUNの対応を確認して解決する。`scores.tsv`はRUNごとの行を保ち、空欄を0に変えない。競合解決で計測済みの実装の動作が変わった場合、元のRUNだけで効果を確定せず、ユーザーによる再計測を待つ。効果が確認できない仮説はマージせず、結論と根拠をmain側の会話に戻す。別の仮説が見つかった場合もmainへ戻し、ユーザーが次の検証対象を選ぶ。
