# ISUCONの実装分担ワークツリー

`main`はRUNの横断分析、仮説と優先順位の決定、実装の統合、デプロイ・計測、結果分析と採否判断を担当する。独立して進められる実装は専用worktreeとapp-server上の独立した通常のCodexタスクへ分担し、mainのベンチ・分析と重ねる。担当は調査・実装・ローカル確認・コミットまで行う。仮説の出典は現在の会話または`docs/conversation/`、実装の履歴はコミットで追い、曜日名に意味を持たせない。

担当はタスクID（thread ID）で指定する。Herdrのタブ・ペインや`HERDR_*`環境変数を使わず、実装担当にsubagentを使わない。

## 分担と進行の判断

- 実装担当はまず2人までとし、mainは統合・計測を進める。小さな修正や、同じ処理・スキーマ・データ構造を一体で変える改善はmainまたは一人の担当で進める。並行数はmainの手待ち、競合・引き継ぎの負担、取り込み・計測待ちの候補数を見て調整する。計測が追いつかなければ新しい実装の割り当てを抑え、必要な調査へ回す。
- 自律改善を依頼済みなら、mainがEvidenceから仮説と優先順位を選び、分担・統合・計測・採否判断まで進める。仮説ごと・マージごとの再確認は求めない。ユーザーが選んだ仮説、作成のみ、ローカル実装のみ、マージのみなどの明示的な範囲指定は優先する。
- 依頼には担当ワークツリー、仮説と根拠、変更範囲、基準RUN、評価指標、完了条件を含める。mainが次に状況を確認する目安も決め、想定より長引いたときに進捗と阻害要因を確認できるようにする。
- サーバー操作はmainへ集約する。実装担当はdeploy・ベンチ・DB操作・mainへのマージを行わない。独立した仮説は原則一つずつ統合・計測し、全担当の完了を待たない。現在のRUNをfinalizeしてから次の候補を取り込み、比較基準を揃える。
- subagentは、使う場合も特定クエリの調査や差分レビューなど短く完結する補助作業に限る。実装は独立タスクへ分担し、担当範囲の再分担はさせない。

## タスク操作の入口

利用可能な`codex_tui`のタスク操作ツールを優先する。呼び出し名の接頭辞は環境で確認する。

| 操作 | ツール |
| --- | --- |
| 既存の担当を確認 | `list_threads`、`read_thread` |
| 独立タスクを作成・開始 | `create_thread` |
| 担当へ追加指示 | `send_message_to_thread` |
| 完了・承認待ち・質問を確認 | `wait_threads` |

新規タスクの作成は、独立タスク作成を含むユーザーの明示的な依頼とツールの実行条件に従う。例: `$isucon-agent 独立したCodexタスクを新しく作ってworktreeで実装を分担し、mainで計測しながら改善して`。単なるスキル更新やworktree作成だけの依頼では担当を起動しない。既存タスクはタイトルだけで選ばず、会話・担当範囲・worktreeを照合してから再利用する。

操作ツールを使えない、または呼び出しが失敗した場合は、エラーと分担できていない段階を報告する。応答が不明な作成・送信は`list_threads`と`read_thread`で到達を確認し、重複して投入しない。既存の接続方法で解消できなければmainで進められる作業を続ける。スキルのために独自APIクライアントを追加したり、共有app-serverを再起動したり、Herdr・subagentへ切り替えたりしない。

## 作成と作業

worktreeの作成・管理には既存の`wt`を使う。独立タスクの作成とworktreeの作成は別の操作であり、タスクを作っただけでは作業場所は分離されない。

1. `wt list --branches`でワークツリーと既存のローカルブランチを確認する。`mon`、`tue`、`wed`、`thu`、`fri`、`sat`、`sun`の順に循環し、使用中の名前を飛ばして次の名前を使う。すべて空なら`mon`から始める。空きがなければ既存の担当状況を報告し、作業中のワークツリーやブランチを上書きしない。
2. `main`を起点に`wt switch --create <weekday> --base main --format json`で作り、返されたJSONの`path`からワークツリーの絶対パスを取得する。分岐元のmainのコミットも確認する。ワークツリーの作成・管理には`wt`を使い、mainの未コミット変更は分岐に含まれないことに注意する。
3. 作成時のignoredファイルのコピーが終わったことを確認する。調査に使う`runs/analysis.duckdb`はワークツリー固有の実ファイルとし、共有DBへのシンボリックリンクにしない。コピーされていなければ、`.worktreeinclude`の対象を確認して`wt step copy-ignored --from main --to <weekday> --require-include`で補う。ルートの`raw`は`.config/wt.toml`のhookでprimary worktreeと共有するため、コピー対象に加えない。
4. 担当へ渡すworktreeの絶対パス、ブランチ、分岐元mainのコミットを確認する。新規タスクはmainの作業ディレクトリを引き継ぐため、次の手順で担当の操作先を確認してから実装を開始する。

## 独立タスクへ修正を渡す

1. [isucon-agent](../isucon-agent/SKILL.md)を確認し、仮説の根拠、変更範囲、基準RUN、評価指標、完了条件、既存の合意を整理する。
2. `create_thread`で担当が分かるタイトル（`isucon-mon`など）の独立タスクを作る。初回プロンプトには担当worktreeの絶対パス、実装担当であること、`$isucon-agent`とそのworktree内の`.agents/skills/isucon-agent/SKILL.md`を指定する。最初は編集せず、指定worktreeを作業先にして`pwd`、`git rev-parse --show-toplevel`、ブランチ、HEADを確認・報告して待つよう指示する。モデルの指定がなければ引き継ぐ。
3. 返されたタスクIDを保持し、`read_thread`で確認結果を読む。すべてのコマンドの`workdir`と編集パスを担当worktreeへ向けることを明示する。作業先・必要な権限を確認できるまで編集を開始させず、mainへの書込みで代用しない。タスクの表示上のcwdがmainのままでも、実際のコマンド・編集先が分離されていることを確認する。
4. `send_message_to_thread`で上の実装指示、分岐元コミット、状況確認の目安を渡す。担当はローカル確認・commit・報告までで、サーバー操作とmainへのマージを行わないことを含める。作成・送信のプロンプトはそれぞれ1,000 UTF-8バイト以内に収める。長い指示は既存の会話ログ・コード・RUNへの参照を使うか、補足だけを先に送り、指示が揃った最後の送信で実装開始を明示する。新しい作業記録ファイルは作らない。
5. `read_thread`で指示の受領と担当範囲を確認したら、実装完了を待たずに他の担当を開始し、mainの作業へ戻る。タスクID、worktree、担当仮説、確認時のcursorの対応はmainの会話で追う。

担当Codexは現行実装と保存済みRUNのEvidenceを調べ、選ばれた仮説の効果と正当性を評価できる変更を実装する。必要なbuild・checkを行って担当変更をコミットし、実装コミット、差分、確認結果、未確定点、比較候補の基準RUNと評価指標、想定する対象ホストと影響を担当ワークツリーの会話で報告する。main側の担当がこの報告を確認して統合・計測へ引き継ぐ。新しい作業記録ファイルの作成は求めず、記録の扱いは`AGENTS.md`に従う。

## 完了待ちでmainを止めない

mainは担当を起動したら、ベンチ・分析や次の計測準備へ戻る。ベンチなど長時間のCLI呼び出しは短くyieldして継続し、待ち時間には読み取り専用の状況確認や保存済みRUNの分析を進める。待機だけを繰り返して担当全員の終了を待たない。

ベンチ・分析の区切りや依頼時の目安で`read_thread`を使い、実際の進捗・質問・完了報告を確認する。`wait_threads`は通常`timeoutMs: 0`で状態を取得し、同じタスクの前回の待機応答にcursorがあれば`afterCursor`へ渡して、古い完了を今回の完了と混同しない。他に進める作業がなく待つ場合も30秒程度で区切り、無期限の待機や即時pollの連続を避ける。実行中・idleなどの状態や一つのturnの終了だけで、担当実装が完了したと判断しない。質問は既存の合意とEvidenceで解決できればmainが回答し、必要な場合だけユーザーへ相談する。

想定より長引いたり同じ状態が続いたりした場合は、出力と差分から阻害要因を確認し、追加情報の提供、担当範囲の縮小、保留・別候補の先行計測を判断する。引き取る場合は担当へ編集停止と引き渡しを依頼し、実行中の編集・コマンドが終わったことを確認してからmainが編集する。メッセージ送信や観測のtimeoutを停止とみなさず、停止を確認できなければ別候補を進める。経過時間だけで失敗と決めず、状況確認なしに待ち続けない。

完了報告はcommit・差分・確認結果と照合し、優先度と依存関係から次の候補を選ぶ。mainの更新や新しいRUNで仮説・前提が変わったら、影響する担当へ変更点を伝え、継続・修正・保留を決める。実装中のワークツリーへmain側から同時にmergeや編集を行わない。

## mainへの取り込み

mainへのマージ指示、または自律改善の依頼範囲に基づき、対象ワークツリーと実装コミットを特定して取り込む。明示的な指示はmain側・担当ワークツリー側のどちらの会話でもよい。マージは計測対象をmainへ統合する段階であり、スコア改善の採用判断は計測後に行う。

main側の担当がmainのworktreeから次の手順で取り込む。担当が編集を終えて引き渡したことを確認し、worktreeでのベンチRUNや効果確認をマージ条件にしない。

1. 担当Codexの実装と必要なローカル確認が完了し、対象の変更がコミットされ、候補とmainの作業ツリーがcleanであることを確認する。取り込む差分と、分岐後にmainへ追加された変更・RUNを確認して、担当仮説の範囲と比較条件を揃える。
2. `git -C "<worktree-absolute-path>" merge-base --is-ancestor main HEAD`でmainが候補の祖先か確認する。mainが先へ進んでいる場合は、`git -C "<worktree-absolute-path>" merge --no-ff --no-edit main`を行い、競合があれば解決してコミットする。実装の履歴を保つためrebaseやsquashは行わない。競合は変更の意図を確認して解決し、統合で影響した範囲のbuild・checkを行う。既存RUNの成果物や`runs/scores.tsv`はRUNごとの対応を保ち、空欄を0に変えない。
3. `wt -C "<worktree-absolute-path>" merge main --no-commit --no-rebase --no-ff`を実行する。祖先関係・作業ツリーの検査は`wt`に任せ、拒否された場合に原因を確認して対処する。成功時は`wt`の既定の削除処理でworktreeを片付け、mainのマージコミットを確認する。担当タスクの会話は確認用に残し、削除したworktreeで作業を再開させない。mainが更新されて拒否された場合は、最新のmainとの差分を確認して取り込み直す。

新しい仮説はmain側の会話へ戻し、自律改善中はmainが次の実装対象と優先順位を決める。担当Codexは割り当てられた仮説を完了したら引き渡し、独自に次の改善へ進まない。

## mainでのデプロイ・計測・分析

mainではマージした仮説の評価条件と基準RUNを確認する。計測対象のコード・設定は計測前にコミットし、RUNとの対応を追えるようにする。

ローカル実装やマージだけを指定された場合は、その範囲に従う。mainのデプロイ指示、または`isucon-agent`による自律改善の依頼範囲に基づき、`AGENTS.md`とTaskfileに従い、対象ホストと影響を確認してmainから正規経路でデプロイする。DB初期化用のignored資材もmainに揃える。

main側の担当がmainから`task bench`を実行してRUN成果物を保存する。通常の`after-bench`が成功していればmainのDuckDBは同期済みとして分析へ進む。同期失敗や追加のRUN取り込みなど、同期が必要な場合だけ`task q-sync`を実行する。同条件の基準RUNとスコア・正当性・主要指標を比較し、自律改善中はmainが採否を判断して、結論と根拠、未確定点をmain側の会話で報告する。効果が確認できない変更の修正・取り消しもmainで扱う。欠損成果物や失敗RUNの扱いは`AGENTS.md`に従う。
