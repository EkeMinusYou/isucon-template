# 全面再設計の手順

初期実装は振る舞いを抽出する資料として使い、内部アーキテクチャーを設計の前提にしない。公式仕様を優先する。既存のHTTP表現や初期データ形式も、外部から必要とされる範囲を特定する。

## 振る舞いを抽出する

各操作について入力・認証・検証・応答・状態変化・参照される後続操作を対応付ける。併せて以下を調べる。

- 並び順・ページ境界・検索比較・時刻・IDの意味、エラー条件と外部から観測される結果。
- 同時更新、更新の可視性、重複実行、外部サービスとの順序・失敗時の状態。
- 初期化で戻す状態、受理済み更新の通常再起動後の復元、再初期化時の世代の扱い。

初期コードのテーブルや呼び出し関係の一覧を、そのまま仕様としない。動作の根拠として該当ソースを示し、未確認点は設計判断と区別する。すべてを文書へ転記することは要求せず、実装と検証に必要な対応関係を保つ。

## 資源と得点から構成を選ぶ

得点に至る操作列と必要な仕事量を整理する。基準スコアがなくても、対象件数・更新頻度・転送量などの既知情報と未確定の仮定から比較できる。

- 正本・索引・集計値の配置と更新コスト、初期データと負荷中の増加分を含むメモリ容量。
- 更新を直列化する単位、読者への公開方法、競合・待ちが集中する箇所。
- 永続化の単位・順序と復元方法、通信回数・転送量、外部サービスの制約。
- ホストごとのCPU・メモリ・disk・networkへの割り当てと、得点対象処理を制約すると予測する資源。

有力な代替案との比較で選定理由を短く示す。根拠のない細かなスコア予測は作らない。設計を左右する不明点だけを追加調査・小さな試作で確認し、判断が変わらない分析を続けない。
旧実装のDB・プロセス・関数境界や、最初から全ホストを使うことを制約にしない。新実装でも既存のライブラリや計測・配布ツールは利用できる。

## 実装と確認

選んだデータ構造・状態管理で全機能を実装する。旧ハンドラーを残して呼び分けることや、旧実装にN+1・索引修正を積み重ねることを全面再設計の代わりにしない。
同じ状態を参照・更新する経路は、認証・エラー処理・初期化・復元・外部連携まで揃える。新実装のGo moduleと配布対象から参考用コードを分離する。

振る舞いの確認には、同じ初期状態と操作列での参照実装との比較、仕様から導いた不変条件、公式ベンチを使う。時刻やIDの差は仕様上自由な部分だけを正規化し、状態変化や副作用の違いを隠さない。同時実行は単一の応答順との一致だけで判定せず、仕様の整合性条件を確認する。参照環境と新実装の状態を混ぜず、同じサーバーでの実行は直列にする。

計測は新実装へ組み込み、設計時に予測した律速を確認できるようにする。初回の全体構成を一つの設計仮説として評価し、部分的な速度だけで完成としない。初回PASS後は実測に従って構成を含めて改善する。
