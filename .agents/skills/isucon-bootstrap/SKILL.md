# ISUCON redesign bootstrap

[isucon-setup](../isucon-setup/SKILL.md)で整理した外部仕様・提供データ・資源情報だけから、nginx＋Goの構成で全機能を実装する。実行構成の制約は`AGENTS.md`の「全面再設計の方針」に従う。既存コードへの段階的な性能改善を既定の進め方にしない。
実行許可・正規操作・commitは`AGENTS.md`、得点への作用と比較は[Evidence基準](../_shared/evidence.md)に従う。

## 外部仕様から設計・実装

初期ソースを読んだsetupとは別の新しいセッションで開始する。最初に`docs/behavior.md`を読み、必要な提供データ・資源条件・準備済みツールを確認する。setupの会話・旧ソース・nginxを含む初期設定・旧アプリの内部構成は読まない。公開経路・TLS・静的資材の外部仕様を入力とし、[nginxの秘伝のタレ](../../../docs/special-sources/nginx.md)に基づく`nginx/common/`と`nginx/roles/`の汎用ベースを競技へ合わせる。配置・転送先はTaskfileで定義して`task gen`でホスト別に生成し、生成物を直接編集しない。
仕様不足はsetup側への振る舞いの確認依頼として返し、更新された外部仕様だけを受け取る。調査用ソースを自分で開いて補わない。

[全面再設計の手順](references/redesign.md)を読み、次を進める。

1. setupが整理した外部仕様と公開APIの観測から、各機能の応答・状態遷移・外部副作用・整合性・復元要件を確認する。曖昧な箇所は根拠と不明点を分け、旧ソース・内部ログ・SQL・他試行の実装を参照して埋めない。
2. 得点対象の操作列、データ量・増加量、使用できる資源をもとに構成を比較する。正本となる状態、派生データ、更新順序、永続化、ホスト配置を決める。[設計判断の共通基準](../_shared/evidence.md#新規設計の根拠)に従い、各案の得点への作用と資源上の成立条件を示す。
3. `webapp/go/`の汎用土台を使い、選んだ構成で全機能を新規実装する。待受・起動方法は変更してよいが、共通計測moduleとRUN回収の接続を維持する。同じ構成の成立に必要な参照・更新・初期化・復元を一体で扱う。実装の進捗を小さく区切ることと、旧構成を段階的に最適化することを混同しない。
4. 新実装へ[標準計測](../isucon-setup/references/measurement.md)を組み込み、正規build・deploy・初期化経路を揃える。得点につながる件数・進行・待ち時間を、[状態・操作の計測](../../../docs/measurement/state-and-operations.md)に従って確認できるようにする。重要な完了から次の開始までを`operation_pairs`、進行中の区間を`operation_intervals`へ設定する。[nginxアクセスログ](../../../docs/measurement/nginx-access-log.md)へセッション識別値・必要な実読取量を接続し、負荷期間の進行・同時数・受信量・接続を確認する。
5. [秘伝のタレ](../isucon-special-sauce/SKILL.md)を適用する。公開静的資材の更新・認可・初期化仕様からキャッシュ期限を決め、入口の実応答で確認する。SSE等のストリーミング、TLS、body上限も仕様に合わせる。
6. 公開HTTP応答の期待値と必要な操作列テストを[共通の検証runner](../../../tools/validation/README.md)へ宣言する。業務上の観測順序は外部仕様から競技側のテストに実装し、部品テストの成功と観測していない範囲を区別する。必要なローカル検証、`task setup-check`、正規deploy・初期化・`task setup-postflight`を行い、`task bench`で新構成を検証する。失敗は仕様・実装・環境・計測のどこかを切り分けて補修する。

[既知資料](../_shared/known-solutions.md)はGoでの設計に必要な場合だけ使う。メモリ配置・索引・並行処理・永続化方式は得点と資源から選ぶ。

## 完了条件

- nginxとGoが指定roleで稼働し、DB等の不要サービスは停止・無効化されている。通常処理・起動・初期化・復元にDB等を必要としない。公開入口のTLS・静的キャッシュ・圧縮・ストリーミングが仕様どおり機能する。
- 全機能を新構成で実装し、必要な初期化・外部連携・通常再起動後の復元が成立している。未実装機能や常に成功するstubでPASS相当と扱わない。
- 正規deployした新実装が公式ベンチでPASSし、得点・合否・計測の生成から回収・分析まで確認できる。CPU・heap/goroutine・runtime等は実際の負荷期間と対応させ、仕様上成立しない計測は理由を示す。
- [設計判断の共通基準](../_shared/evidence.md#新規設計の根拠)に従い、初回RUNから予測が支持された点と未検証の選択・選定理由を整理する。設計上の選択をすべて性能実験することをbootstrapの完了条件にせず、目標点への継続依頼では[isucon-agent](../isucon-agent/SKILL.md)の候補選定へ引き継ぐ。

基準となる旧実装のRUNは必須にしない。存在すれば構成差を明示して参考比較し、新実装の初回PASSを以後の改善比較の基準にする。設計・実装だけの依頼はここで完了し、継続依頼では同じスレッドで改善を続ける。
