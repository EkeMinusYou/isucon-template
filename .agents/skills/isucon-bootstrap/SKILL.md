# ISUCON bootstrap

## 担当範囲

[isucon-setup](../isucon-setup/SKILL.md)で整えた環境に、次の初期改善を実装する。メモリ＋WALへの移行と、その構成での計測整備も標準の担当範囲である。

実行許可・操作制約・commitは`AGENTS.md`、実験の評価は[Evidence基準](../_shared/evidence.md)に従う。初期対応で目指す構成の成立と、得点改善の実証を分ける。WAL移行を、現在の律速や事前の得点改善予測がないという理由だけで省略しない。公式仕様と両立できない場合は理由を示し、完了扱いにしない。

## 初期改善を進める

1. 現行構成・配布物・標準計測・基準RUNを確認する。setupの不足は[計測補修手順](../isucon-setup/SKILL.md#既存環境の計測補修)など該当範囲を補い、初回構築全体をやり直さない。比較可能なRUNがなければ`task bench`で取得する。
2. [isucon-special-sauce](../isucon-special-sauce/SKILL.md)で秘伝のタレを適用する。[N+1解消](../../../docs/solutions/n-plus-one.md)と[索引追加](../../../docs/solutions/database-index.md)を参考に、適用可能な変更を実装・計測する。未適用・適用済み・適用不能を区別する。
3. [nginx静的配信](../../../docs/solutions/nginx-static-files.md)、[オンメモリ化](../../../docs/solutions/in-memory.md)、[WAL付き状態管理](../../../docs/solutions/wal-backed-in-memory-state.md)を参考に移行する。最初に全機能の読み書き・状態遷移・外部副作用・復元方法を整理し、移行後の構成と関連経路を一体で変更する範囲を決める。
4. 静的ファイルはnginxから配信する。全機能の通常処理はメモリ上の状態とWALで成立させ、負荷中のDB読み書きはバックグラウンド投影も含めて全廃する。DBは初期データの読み込みにのみ使い、復元元は初期データとWALとする。参考資料のDB投影を伴う手順も、この要件に合わせる。通常のサービス・OS再起動後も受理済み更新を復元でき、外部サービス連携、重複実行防止、更新の可視性、処理順序などの公式仕様を維持する。
5. 移行と同時に[WAL構成の計測](references/wal-measurement.md)を整える。得点条件と処理の段階を対応付け、既存アクセスログ・WAL等から段階ごとの件数と進行を調べられるようにする。性能実装だけを終えて計測を別作業へ先送りしない。
6. 必要なbuild・check・commit、正規deploy、`task bench`で検証する。独立した改善は別RUNで評価し、同じ構成の成立に必要な関連経路は一体で扱う。正当性、移行要件、復元、回収・集計を確認し、不具合は修正する。変更前との得点差も報告するが、目標点への到達を初期対応の完了条件にはしない。

## 完了条件

次をRUN・コード・設定で確認し、会話で根拠を短く示す。作業記録ファイルは明示依頼時のみ作る。

- 指定範囲の実装と正規deployが完了し、移行後の構成でベンチがPASSしている。WAL移行では全機能の通常経路からDBアクセスがなくなった根拠と、通常再起動後の復元結果も示す。
- 得点計算と処理の段階、件数・進行を調べるquery、情報源・母数・時間窓・観測できない範囲が分かり、実RUNの元データとの対応を確認できる。観測不能を失敗や0件に置き換えず、全利用者の追跡や損失の数値化を完了の必須条件にしない。

初期対応だけの依頼はここで完了する。
