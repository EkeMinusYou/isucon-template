# Post benchmark

## 共通情報の事前取得

親は下記の共通確認を委任前に一度行う。取得結果は一意な一時ディレクトリへ保存し、全文を端末へ出さず要点と不足だけ表示する。資料は必要な節を読み、出力が切れたら保存ファイルから未確認部分だけ取り出す。同じ資料・カード・集計の全文再取得を避ける。ただしOwner取得と最終書き込み直前の最新version確認は省略しない。

委任前に揃える情報は、固定RUNのmanifest、対象カードJSON、関連Target・Objective・依存、全対象の比較要約、比較RUNと実負荷窓、保存済みworker検証の参照先と確認範囲である。関連エンティティはIDで重複を除いて取得し、Historyは適用・未解決事項・既存判断に関係する部分を読む。Owner取得後のカードも保存し、評価条件を固定する。全指標を委任前に分析する必要はなく、担当固有の不足はクラスタへ渡す。

### 取得・表示のコマンド例

リポジトリrootから実行する。RUNは選択済みID、カードIDはsnapshot照合で確定した対象へ置き換える。この例は読み取りと一時保存のみで、Owner取得はworkflowのCLIに従って別途行う。各コマンドの成功と保存JSONの妥当性を確認してから後続へ進む。

```sh
VERIFY_RUN=20260914-015739
VERIFY_DIR=$(mktemp -d "${TMPDIR:-/tmp}/isucon-verifier.XXXXXX")
cp "runs/$VERIFY_RUN/run.json" "$VERIFY_DIR/run.json"
jq '{run_id,phase,passed,score,roles,source,backlog_snapshot,comparison,load_window,missing,
  artifact_issues:[.artifacts[]? | select(.status != "ok" or
    (.quality.expected == true and .quality.status != "valid"))]}' "$VERIFY_DIR/run.json"
task artifacts-run RUN="runs/$VERIFY_RUN"

task --silent backlog -- show B-001 --format json > "$VERIFY_DIR/B-001.json"
jq '{id,version,status,owner,application_id,compare_run,target_ids,objective_ids,dependencies,
  sections:[.sections[]? | select(.name == "Hypothesis" or
    .name == "Change boundary" or .name == "Evaluation")]}' "$VERIFY_DIR/B-001.json"
task --silent backlog -- evidence --run "$VERIFY_RUN" B-001,B-002 --format json > "$VERIFY_DIR/evidence.json"
```

同じ`show`を対象カードと関連Target・Objectiveへ適用して保存する。後者は`target show`、`objective show`を使う。比較RUNのmanifestも同様に確認する。長いEvaluationは保存JSONから項目を分けて読み、Historyも必要なpositionだけ取り出す。

```sh
jq '.history[]? | select(.position >= 4)' "$VERIFY_DIR/B-001.json"
jq '.[] | select(.card_id == "B-001")' "$VERIFY_DIR/evidence.json"
```

`position >= 4`は例であり未確認履歴の位置へ置き換える。固定の行数で必要な根拠を捨てない。一時保存先は担当間で共有し、採否の根拠・比較条件・再取得SQLは最終的にカードHistoryと完了報告へ残す。取得JSON・集計CSV・実行ログ・SQLファイルは一時保存に留め、一時ファイルを永続Evidenceの参照先にしない。

## 共通確認と比較要約

1. [対象と手順](../SKILL.md#対象と手順)で選んだ対象RUN（未指定時は開始時点の最新RUN）と、そのbefore-bench APPLIED snapshotに含まれる今回の確認対象カード・適用IDを固定し、[workflowの所有権規則](../../../../tools/backlog/backlog-workflow.md#ownership-and-handoff)で取得する。取得後にEvaluation・Compare Runも固定する。finalized、pass/fail、score、各カードの宣言とsnapshotの対応、roles/sourceを確認する。RUN共通の確認はbatch全体で一度行い、使用する成果物のstatus・qualityも共有する。失敗RUNも確認対象とする。
2. カード群の比較要約を`task backlog -- evidence --run <RUN_ID> B-001,B-002`でまとめて取得する。機械処理には`--format json`を追加する。要約はEvaluationに記載された採否条件に対応する範囲で利用し、参照形式や限界を確認する必要があれば[Evaluationの指定方法](../../_shared/evaluation.md)を読む。
3. 指標の比較SQLを実行する前に、Evaluationと要約から採否を左右する比較を短く整理する。対象カード、下記の規則で選んだ比較RUN、機構・副作用・正確性の確認項目、旧参照と新参照を含む取得方法、単位・時間窓、取得済みか未取得かを対応付ける。既存の要約を再利用し、専用の帳票や新しいカード項目は作らず、形式統一のために宣言を更新しない。使用する両RUNの成果物・列・profile種別・sample種別・時間窓を確認し、不一致や欠落を先に区別する。確認済みのmetadataは再利用し、抽出されなかった値を0として先へ進めない。採否を左右しない参考観測や原因調査は必要な場合だけ追加し、Evaluationを埋めるために増やさない。
4. 親はここまでの共通情報から下記のクラスタを編成する。各担当は未取得の比較だけを、[集計の再利用方法](../../_shared/evaluation.md#集計の実行方法をカードに残す)に従って実行する。同じRUN・窓・集計定義の確認をカード間で共有する。既存DuckDB上の独立した集計は、可能なら一回の`task q`にまとめる。取得方法が未記載の対象カードは必要部分だけ具体化し、今回の確認で再利用する。同じ負荷窓の関連エラーは[Evidence](../../_shared/evidence.md#runの扱い)に従って確認する。JSONの抽出成功や警告なしを、正確性・採用の自動判定にしない。
5. 改善・横ばい・悪化・判定不能を分類する。単位・母数・時間窓、処理量・配置・同時変更の影響を区別する。採否の根拠が揃ったカードは下記の記録と確定へ進み、そのカードの追加調査を終える。問題のあるカードだけを次節へ進める。

## クラスタ検証と親の統合

親は共通取得後に残る検証を、機構・使用Evidence・相互影響の共通性でまとめる。同じtoken SQLや索引を評価するカードは同じクラスタへ寄せるなど、同一集計の重複を避ける。独立したクラスタが複数あればサブエージェントへ並列委任し、各対象カードの担当を一つに定める。クラスタ数やカード数を固定せず、共通確認で判断が済むカードのためだけに担当を増やさない。

委任には次を渡す。親も統合準備や未担当の検証を進める。

- 対象カードID、固定RUN・適用ID・評価条件・比較RUN、関連Target・Objective
- 保存JSONとworker検証のパス、共通確認済み事項、使用可能な成果物と欠損
- 取得済み指標・SQL・時間窓、および担当が解く残る問い
- 読み取りと判断案のみを担当し、Owner取得・Backlog更新・他スキル起動を行わない境界

クラスタ担当は共通確認を繰り返さず、保存情報から未取得の比較だけを行う。必要な列・profile/sample種別・単位・窓についても確認済み情報を再利用する。個別SQLはEvaluationの実在参照を使い、全カード共通の必須指標を増やさない。追加調査は次節の条件に従う。

複数クラスタが同じRUN・窓・集計定義を必要とする場合は、親が実行担当を一つに定めてSQLと結果を共有する。`task q`はq-syncを伴うため共有DuckDBへの同時実行を避け、SQLを親へ渡してまとめて実行するか、親が実行順を調整する。SQL待ちの担当は保存検証やコードとの対応確認を進める。取得済み指標の再計算は入力変更・不一致・不足がある場合に限る。

担当はカード別に、主要比較値と判定（改善・横ばい・悪化・判定不能）、正確性、採否案、差し戻す場合の修正差分の再調査結果と完了条件、寄与仮説への観測、Evidence/SQLの保存先を親へ返す。同時変更の個別寄与が不明な箇所と、他クラスタへ影響する観測を明示する。

親は対象カードの漏れ、同時変更による帰属、共通資源への費用移転、クラスタ間の判断の食い違いを照合する。取得済みデータを再集計せず、不一致が採否を変える部分だけ追加確認を割り当てる。クラスタ単位で一括採否を決めず、根拠が揃ったカードから親が下記の記録と確定を行う。判定済みカードは他クラスタの調査に合わせて深掘りしない。

## 必要な項目だけ追加調査する

要約の不一致・欠落、未抽出の条件、関連指標の悪化や機能エラーについて、採否に必要な部分だけ元成果物へ戻る。追加のSQL・profile・ログ調査や読み取り専用SSHの前に、**残る疑問と、その答えが採否・修正方針をどう変えるか**を短く明記する。既存DuckDB基盤で対象行・関数・時間窓を絞り、同じ抽出結果を複数カードで共有する。Evaluationに全体指標が列挙されていても、変更との関係を説明できる範囲を確認する。

failやcorrectness errorでは今回の変更との関連確認を優先し、帰属する問題があれば下記の修正差分を再調査してからworkerへ是正を引き渡す。関連が不明なエラーは経路・時刻・既存記録との最小限の照合に留め、接続を示す根拠がなければ深掘りしない。スコア差の説明、既存警告の原因究明、新しいボトルネック探索へ広げない。

保存済みの実装時検証・配置確認を再利用する。新しい不一致や適用状態への疑いがある場合だけ読み取り確認を追加し、修正方式の実現可能性・正当性は下記の読み取り調査で確認し、テスト再実行や実装後の確認はworkerへ渡す。判断が済んだカードの確認を、別カードの調査に合わせて増やさない。既存成果物で比較できない指標は不足理由とともに判定不能とし、その穴埋めだけの追加計測は行わない。比較不能でも、今回の変更に帰属する正確性の問題は修正対象とする。

## 継続価値の判断

退行の帰属を必要な範囲で確認したら、[workflowの継続・不採用規則](../../../../tools/backlog/backlog-workflow.md#rejection-after-application)に従い、修正方式を具体化する前に継続価値を判断する。単独カード、または既に具体化された後続カードを含む一連の改善が、介入前に対して純利益を見込めるかを評価する。修正方法を考案できたこと自体を、追加実装の理由にしない。

- 介入前のRUN・構成と現在までの推移を特定し、直前修正版からの回復と介入全体の利益を分ける。比較条件が違う箇所は判定の限界を明記し、得点差だけで帰属を断定しない。Compare Runとmanifestのcontrolは既存の選択規則を維持する。
- 保存済みEvidenceから減らせる仕事・待ちと残る追加費用を対応付け、正常完了・得点機会への経路と不確実性を説明する。正確な予測や効果量の実測は必須にしないが、関連Evidenceを調べても純利益の見込みを支持できなければ、不採用を基本とする。
- 後続改善を理由に一時的な退行を許容する場合は、後続カードID、今回の変更の必要性、実現可能性のEvidence、合算した費用と寄与、全体の評価条件、後続不成立時の今回の変更の扱いを記録する。未調査の将来案は根拠とせず、verifierの新規探索・起票や他Ownerのカード更新へ広げない。将来の利益と現在の実証・採用を区別する。
- 再差し戻しでは前回の継続条件と結果を照合する。次の結果が採用・継続・不採用のどれにつながるかをHistoryへ残す。条件を見直す場合は、介入全体の見込みを変えた新しいEvidenceを示す。部分回復だけで基準を直前RUNへずらしたり、未達条件を別の修正案へ置き換えたりしない。

継続が妥当なら限定修正、不採用なら必要な撤去・是正について次節の調査を行う。不確実性を反証と同一視せず、追加実装に投資する根拠の有無として判断理由を残す。回数による一律打ち切りや、他カードの新規探索は行わない。

## 修正差分の再調査

限定修正・不採用の是正をworkerへ渡す前に、元カードのHypothesis・Change boundary・Evaluation、Historyと保存済み調査を再利用し、今回のEvidenceで崩れた前提・追加費用・不具合に関係する差分だけをinvestigate相当の深さで調べる。有効な既存調査を繰り返さず、引き継ぐ部分と見直す部分を明示する。調査は対象カードの変更境界内に限定し、新規改善案の探索や別スキルの自動起動へ広げない。

- 退行・不具合の観測をコード上の処理と発生条件へ結び付け、事実と原因仮説を区別する。
- 関係する具体的な修正候補を現行と比較し、減る仕事・追加費用・正当性から方式を選び、選択理由を残す。候補数を目的に案を増やさない。
- 選ぶ方式が既存のコード・データ構造・並行処理・初期化・永続性と両立するか、変更に関係する部分を確認する。実装方針を左右する疑問を読み取り調査で解消する。
- 変更箇所と振る舞い、保持する既存変更、正当性の成立条件、workerが行う実装時検証、適用後の評価方法を具体化する。「復元費用を減らす」「キャッシュを見直す」だけでは引き渡さず、対象となる処理・データの生成、更新、保持、破棄など、方式を実装できる判断まで詰める。

完了基準は、前節で継続または不採用を選ぶ根拠を確認したうえで、その修正・是正差分について実装可能な方針と、それを選ぶ根拠が揃うことである。効果量の実測や原因の完全な証明は必須にせず、残る不確実性と影響、どの結果なら方針を変えるかを記録する。追加調査で方針を具体化できる間は原因候補だけを渡さず調査を続ける。具体的な外部情報不足はworkflowのBLOCKED規則に従い、未完了の引き渡しとして報告する。

再調査結果と修正後の評価条件はOwner解除前に対象カードのHistoryへ記録する。RUNに対応する適用時のChange boundary・Evaluationは書き換えず、検証対象と今後の修正差分を区別する。必要な本文更新と再適用はworkerが行う。カードを正本とし、カードだけで修正方針・根拠・完了条件を把握できるようにする。

## 採否と差し戻し

採用・差し戻しの状態変更前に、[関連指標の判定結果](#関連指標の判定結果)と[寄与仮説への引き継ぎ](#寄与仮説への引き継ぎ)を記録する。記録後の最新version・自分のOwner・適用IDと、固定した評価条件を再確認して確定する。

[workflowの採用条件](../../../../tools/backlog/backlog-workflow.md#adoption)を満たすカードは、[RUN・Owner・versionを明示した採用操作](../../../../tools/backlog/README.md#adoption-records)でVALIDATEDにする。効果量が曖昧でも、公式仕様・明示要求への適合と改善の方向が維持され、採用条件を満たすなら、不確実性を記録して採用できる。例外採用もworkflowのFORCE条件に従う。

アプリログのERROR、個別リクエストの5xx、減点の存在だけを採用不可や修正必須の理由にしない。ベンチマーカーの整合性判定と終了理由を確認し、整合性違反・異常終了・負荷走行の途中停止を、正常完走中の個別失敗と区別する。`passed=true`でも途中停止を通常完走と扱わず、今回の変更との関係と採否への影響を必要な範囲で判断する。途中停止だけで全カードを一括不採用にしない。

残存する減点要因の追加調査・修正は、期待する得点改善と調査・修正・再ベンチの作業時間を踏まえて判断し、エラーの完全解消を採用条件にしない。ユーザーが受容した残存課題を独自に採用条件へ戻さない。ただし、公式仕様への違反やworkflowの採用条件は別に扱う。採否に必要な根拠が有効な成果物で揃うなら、一部profileの欠損・品質検証失敗だけで再ベンチ待ちにしない。

今回の変更に帰属する正当性の問題や、採用前に解消すべき退行がある場合は、[継続価値の判断](#継続価値の判断)で限定修正か不採用かを選び、[修正差分の再調査](#修正差分の再調査)を済ませてworkerへ渡す。将来の改善を理由に正当性違反を許容しない。不採用と判断しても、この段階ではREJECTEDへ進めず、必要な是正をOwnerなしDOINGへ引き渡す。

差し戻しは[workflowの受け渡し規則](../../../../tools/backlog/backlog-workflow.md#ownership-and-handoff)と[CLI例](../../../../tools/backlog/README.md#ownership-and-handoff)に従う。`transition`のreasonへ限定修正／不採用の別と、調査済みの具体的な是正方針・根拠・評価条件・完了条件（同カードに先に記録したHistoryへの参照も可）を記録し、OwnerなしDOINGへ戻す。以後そのカードには書き込まず、対象RUNの残りのカードを処理する。

### 不採用是正後の再適用

workerが不採用の是正を完了したカードは、`VERIFY -> APPLIED`で新しい`application_id`を発行し、transitionのreasonに`rejection-cleanup application`、是正内容、実装・deploy確認、次の手動ベンチ後にverifierが`REJECTED`へ閉じることを明記する。このAPPLIEDは通常の採用候補ではない。verifierは最新Historyのこの明示的な記録で通常適用と区別し、`task pass`を実行しない。

次のユーザー実行RUNでは、通常の採否検証と同じくfinalized、成果物のstatus/quality、correctness、終了理由、対象経路の正常性を確認する。ただし目的は不採用理由を再評価することではなく、是正後の状態がcleanup条件を満たし、対象カードの変更が残っていない、またはHistoryに記録した是正状態になっていることを確認することである。元の不採用判断のRUN、application ID、介入前baseline、純利益判断は維持し、是正後RUNを新しい採用比較のbaselineへ置き換えない。

cleanup条件を満たしたら、関連指標・正常性・寄与仮説への引き継ぎをHistoryへ記録したうえで、verifierがOwnerとversionを再確認し、`APPLIED -> REJECTED`を`--release-owner`付きで行う。条件未達、別の帰属可能な故障、または是正の適用不一致があれば、REJECTEDにせず、必要な具体的修正を記録してAPPLIEDからOwnerなしDOINGへ戻す。従って、同じRUNに通常適用・限定修正後のAPPLIEDとcleanup後APPLIEDが混在する場合は、cleanup対象を先にREJECTEDへ閉じてから、cleanup対象を含めないカードIDだけで`task pass`を実行する。REJECTEDへ移行したカードを同じ採用操作へ渡してはならない。ベンチ実行とコード・deploy・テストの再実行は引き続きverifierの担当外である。

リンクがある場合、Targetの状態は[workflowのTarget規則](../../../../tools/backlog/backlog-workflow.md#target)に従い、今回の目標と評価条件に対する達成Evidenceから確認する。Intervention採用だけでRESOLVEDにしない。Objective・Targetとそのリンクは変更せず、達成候補や前提の変化を対象ID・Evidenceとともにisucon-targetへ報告し、Targetの更新・達成判定を任せる。

### 寄与仮説への引き継ぎ

採否の判断がまとまったら、状態変更・Owner解除の前に、今回の確認で得たEvidenceから、局所改善と想定した得点への寄与の関係を簡潔に整理する。カードの採用を、得点寄与の実証や同じ方向への追加投資の推奨と同一視しない。

局所改善に対して想定した後続の変化が確認できなかった場合や、寄与の成立条件の変化を観測した場合は、次を対象InterventionのHistoryへ残し、完了報告で要約する。引き継ぎの正本はカードとし、観測・判断すべき問い・根拠RUNとEvidenceの参照先をカードだけで把握できるようにする。

- 対象Intervention・Target・Objectiveと、想定していた寄与経路
- 局所結果 → 得点につながる行動・機会 → スコアについて、観測値と各関係の支持・反証・未確認。想定と観測が食い違う箇所を示し、「個別寄与未分離」だけで済ませない
- 次の範囲を選ぶ親とobjective・targetへ渡す継続仮説、重点の変更候補、または先に解く問い。何を確認し、どの結果なら選択が変わるかと、根拠となるRUN・Evidence

引き継ぎは各InterventionのHistoryに、そのカードの仮説・変更境界に対応する観測、寄与判断、次の問いとして記録する。関連Target・ObjectiveのID（Target未リンクならIntervention本文の寄与先）を明示する。複数カードの合算効果しか分からない場合も、各カードに関係と個別寄与が未分離であることを残す。共通の計測データはEvidenceの参照先を共有してよいが、そのカードの引き継ぎ内容を他カードへの参照だけで代用しない。未観測を横ばいと扱わず、スコア横ばいだけで他の制約の存在や所在を断定しない。

この整理のために追加の全体診断や計測を行わない。局所改善の採用理由と、同方向への追加投資を支持する根拠の有無を区別して引き継ぐ。次の優先判断を変え得る問いを示し、同じ未確認事項の繰り返しを推奨にしない。引き継ぎは既存の採否条件・継続手順を変更せず、Objective・Targetの更新や別スキルの自動起動も行わない。

## 比較RUNの選択

カードの`Compare Run`（`task backlog -- update <ID> --compare-run <RUN_ID>`で設定。通常のversion・actor・reason指定も必要）があれば優先する。空なら、対象RUNより前で`run.json`のrolesが同一の最新finalized RUNを使う。`task backlog -- evidence --run <対象RUN> <ID>`もこの規則で比較値を表示する。複数のCompare Runがあるカードは最新の指定RUNを使う。指定RUNが存在しない、対象RUN自身、または候補がない場合は比較なしとし、別RUNへ暗黙に切り替えない。

これはカードの機構指標を読む比較基準で、変更前RUNへの自動固定ではない。変更前を基準にし続ける必要がある場合は`Compare Run`を明示する。選択後は役割・source・計測窓・負荷条件・同時変更を確認し、比較不能な値を改善としない。診断に必要な場合は、保存済みの比較可能な過去RUNからの推移も使い、構成変更による低下からの回復と純増を区別する。その推移を採否用Compare Runや宣言controlへ暗黙に置き換えない。反復測定がなければ小差を有意な効果ともノイズとも断定しない。採用判定とスコア差分に使うmanifestのcontrolは別に確認し、`task pass`の互換性条件をこの選択で迂回しない。

## 関連指標の判定結果

採用・差し戻しの確定前に、各カードのHistoryへ、変更と評価指標の関係、主要な比較値、判定、関連するcorrectness、採否の根拠と帰属の限界を記録する。各カードには判断に必要な比較条件と関連する正常性の要点を残す。共通の計測データ・詳細な抽出結果は既存Evidenceの参照先を共有し、Result・Historyへ同じ詳細を重複転記しない。複数カードを同時適用したRUNでは個別寄与と断定せず、合算効果または個別寄与は未分離と明記する。

評価したカードの改善報告は、各カードの改善仮説に対して何がどれだけ改善したかを示す。主表は次の2列とし、カードごとに1行にまとめる。表の前に対象カードの採否・状態を示す。指標ごとに行を分割せず、変更内容・対象経路と観測結果を文章で結びつける。カードごとに比較RUNが異なる場合は比較の組ごとに表を分ける。比較RUNがなければ「比較なし」とする。

```text
比較: <比較RUN> → <対象RUN>
| カード | 確認できた改善 |
| --- | --- |
| B-001 | <対象経路・変更内容>により、<このカードの評価指標>が<比較値> → <対象値>（<単位・増減率>）。<改善仮説との関係、関連する悪化や帰属の限界> |
```

- 報告する指標は、各カードのHypothesis・Change boundary・Evaluationから選ぶ。全カードに共通の指標や優先順位を強制しない。SQL回数・時間、CPU、転送量、HTTP応答時間などのうち、そのカードの改善仮説を評価する指標を主役にする。HTTP応答時間自体が改善対象なら主指標としてよい。単なる数値の列挙や実装名の要約で終えず、なぜその観測が当該変更の改善を示すのかを説明する。
- 比較値には単位・母数・時間窓を示し、比較可能な値には増減率を添える。共通の比較条件は表外にまとめてよい。処理量・負荷条件が異なる場合はその限界を記す。処理の0件化は対象範囲と観測根拠を示し、欠損や抽出漏れを0件としない。
- 数値と構造変化の両方を必須にはしない。計測前や比較不能の場合は、コード・保存検証・plan・profileから確認できた処理の除去を具体的に示し、実負荷での削減量は「未確認」とする。表を埋めるために効果量を推測したり、追加計測へ作業を広げたりしない。
- 改善だけを抜き出さず、評価した横ばい・悪化・判定不能も同じカードの「確認できた改善」欄に明記する。改善を確認できなければ「改善は未確認」と書き、未観測・比較不能など判定不能の理由を添える。欠損を0や横ばいとして扱わない。
- 同時適用の合算効果は関係する各カードの行で「B-xxx・B-yyy合算、個別寄与は未分離」と明記する。カードをまとめた行で個別結果を置き換えず、共通指標を各カードの単独効果と断定しない。
- 正常性は主表の列にせず、表外にまとめる。対象API・経路の成功件数、5xx・機能エラー、関連する正確性確認など、観測結果と確認範囲を記す。カード固有の問題や未確認・成果物欠損はカードIDとともに補足する。全体HTTP 5xxだけの確認を、個別経路や公式仕様全体の正常性へ広げない。
- 採否理由の補足とEvidenceの参照先は表外に簡潔に記す。詳細な指標一覧はHistoryに残し、完了報告の主表は上記のカード単位の要約にする。
- `VALIDATED`への遷移やスコア差だけをカード固有の改善証拠にしない。指標の判定と採用条件は分け、判定不能を解消するためだけに調査を継続しない。
