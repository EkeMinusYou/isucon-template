# 得点制約の診断

[Evidence基準](../../_shared/evidence.md)に従い、得点が伸びない理由を切り分け、次の改善または実験を選ぶ。競技固有の操作や固定の試行回数を前提にしない。

## 原因を切り分ける

1. **伸びていない要素を特定する。** 公式の得点計算に沿って、得点機会の件数、1件の価値、失敗・未完了・減点による損失を必要な範囲で分ける。CPUやAPI時間の改善を、どの要素の増減に結び付けていたかを確認する。
2. **進行が途切れる境界を探す。** 時刻と利用者・処理対象などの識別情報を対応付け、得点機会の未開始、途中停止、完了、次の開始待ちを調べる。開始・完了できた対象に加え、その段階へ到達できなかった対象も含める。観測できない対象を未開始や件数0と決め付けない。全経路を網羅せず、得点への影響を説明できていない境界へ絞る。
3. **競合する原因仮説を立てる。** 例えば、処理能力が足りない、次の操作の開始条件が成立しない、対象や枠が足りない、失敗・再試行が得点機会を圧迫する、といった異なる説明を比較する。技術名やAPI名を変えただけの同じ説明を、別の仮説として数えない。観測・仕様・現行コードで支持または否定できる点と、未確認点を分ける。観測できないベンチ内部の振る舞いは確定しない。
4. **仮説ごとに異なる予測を示す。** 正しければどの段階の件数・待ち・結果が変わるか、どの結果ならその仮説の優先度が変わるかを明確にする。対象の処理時間を取り除いた場合、追加の得点機会が何によって発生するのかも考える。既存の得点機会が早く完了することと、得点機会が増えることを分ける。
5. **次の判断を変える観測・実験を選ぶ。** 保存済み成果物、公式仕様、現行コードで調べられる範囲から始める。比較条件と集計の母数・時間窓を揃え、必要な場合だけ追加計測や小さな介入を行う。改善幅が未確定でも、原因仮説を区別できる実験は選べる。同じ前提の精密化や再集計を続けず、結果を候補の選定へ反映する。

会話では、伸びていない要素、原因仮説と根拠のRUN・集計範囲、支持・反証・未確認の関係、次の調査・実験と判断が変わる条件を短く示す。根拠の詳細は原資料を参照できる形にし、作業記録の保存は`AGENTS.md`に従う。

## サブエージェントによる独立診断

メインの見立てだけでは原因を絞れない場合や、得点が停滞したまま同じ前提の改善を繰り返している場合に利用する。まず1人へ、原因を切り分ける読み取り調査を依頼する。

- 会話全体を継承させず、この診断手順とEvidence基準、公式資料、対象コード・構成、比較RUNと過去の実験事実を渡す。最初の入力にはメインが推している結論や候補順位を含めない。過去の不採用案も、観測結果と当時の成立条件を渡し、同じ実験の再提案を避ける。
- 原因仮説、支持・反証となるEvidence、未確認点、仮説を区別する次の調査・実験を求める。メインと異なる結論を出すこと自体を目的にしない。
- サブエージェントは依頼された読み取り調査までを担当し、実装・サーバー変更・ベンチ投入・追加の分担は行わない。追加計測が必要な場合は、観測する内容と判断への作用をメインへ返す。
- メインは結論を原資料と実験履歴に照合し、根拠と未確認点をもとに次の作業を決める。再提案された案は、過去との条件差や新しい根拠を確認する。診断結果を待つ間も、独立した集計や仮説の再評価を進めてよい。
