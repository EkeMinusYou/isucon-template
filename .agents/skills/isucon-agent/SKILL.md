# ISUCON agent

## 担当範囲

改善判断の前に、[共通のEvidence基準](../_shared/evidence.md)を読み、その基準に従う。

`AGENTS.md`・公式手順に従い、`docs/official/`、現行コード・設定、保存済みRUN、DuckDB基盤（`task q`）、読み取り専用SSHで調べる。RUNは指定がなければ最新finalizedを既定とする。

保存済みRUNの原文は上書きしない。調査・ベンチ実行とサーバー操作の制約は`AGENTS.md`に従う。計測不足は既存のsetup手順を参照して必要な範囲を補修し、改善判断に使える状態にする。

## 並行改善の分担

mainで自律改善を進め、ベンチ・分析中に独立した実装を重ねられる場合は、[isucon-worktree](../isucon-worktree/SKILL.md)に従ってapp-server上の独立したCodexタスクと専用worktreeへ分担する。実装担当はまず2人までを目安とし、小さな修正や密接に依存する変更は一人で進める。mainがタスクIDで指示・進捗・結果を確認し、完了した候補から順次統合・計測する。担当全員の終了を待たない。新規タスクの作成条件、作業先の確認、停滞時の対応とsubagentの使い分けは同スキルに従う。

実装担当として起動されたCodexは、指定された仮説の調査・実装・ローカル確認・コミット・報告までを担当する。サーバー操作とmainへのマージはmain担当へ任せ、担当範囲をさらに分担したり、次の仮説へ自律的に進んだりしない。

## 自律改善と実行許可

以下の一連の改善はmain担当が進める。分担された実装担当は上記の担当範囲に従う。

実装・デプロイ・ベンチ実行・分析・採否判断まで自律的に進める。競技環境の改善に必要な配布、serviceの停止・再起動、DB・テーブルの破棄と再作成、スキーマ・配置変更、不要なコード・設定の削除は許可済みとして扱う。対象ホストと影響を確認し、正規のTaskfileと操作ロックを使う。公式ルール・正当性の要件は守る。

1. 現行の配布物・構成・最新RUNを確認し、比較できる基準がなければ`task bench`で基準RUNを取得する。
2. 原則として1回のRUNでは1つの改善仮説を検証し、基準RUN・得点への作用・評価指標を決める。同じ仮説の成立に必要な複数経路の変更は一体で扱い、変更規模だけを理由に分割しない。独立した改善仮説は原則として別RUNで評価する。
3. ローカルで修正し、必要なbuild・checkを通して変更単位でcommitする。対象と影響を確認して`task deploy-*`や`task db-recreate`等の正規経路で反映する。
4. `task bench`を実行する。配布物一致・service状態の検査を通し、失敗RUNも通常回収でfinalizeする。投入後に通信が失敗した場合は既存ジョブの状態を確認し、重複投入を避ける。
5. 結果原文・合否・スコア・artifact status・missingを確認し、`task artifacts-run`とDuckDBで基準RUNに対する変化を比較する。正当性の失敗や悪化は原因を調べ、修正または変更の取り消しを行い、必要なら再計測する。想定外の結果や停滞は[Evidence基準の再評価手順](../_shared/evidence.md#想定外の結果と停滞)に従う。
6. 採用・不採用と根拠を短く報告し、得られたEvidenceから改善候補の優先順位を更新して次の仮説を選ぶ。同じ処理の改善を重ねても期待した得点の伸びが得られない場合、当初残すと決めた処理や構成も見直し、追加改善と置き換えを比較する。一度の実装やベンチ完了で止まらず、依頼範囲内の改善を続ける。

## 報告と終了

ユーザーの停止指示、指定された目標・作業範囲の達成、時間・予算の上限、または権限・認証・外部障害など自力で解消できない阻害要因で終了する。改善候補が見つからないことを終了理由にしない。候補が尽きた場合も、既存の前提・未確定点を見直し、観測・分析を深めて新たな仮説を探し、実装・計測・評価を続ける。同じ失敗条件のまま再実行を繰り返さない。
