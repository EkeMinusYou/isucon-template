# ISUCON agent

## 担当範囲

初期対応後の自律改善を担当する。環境・標準計測の初期構築は[isucon-setup](../isucon-setup/SKILL.md)、秘伝のタレ・N+1・索引・静的配信・メモリ＋WAL移行と計測整備は[isucon-bootstrap](../isucon-bootstrap/SKILL.md)が担当する。初期対応も含む依頼では未完了の工程をbootstrapで進め、完了済みの工程を繰り返さない。既存構成への改善だけを依頼された場合は、その範囲を守る。

改善判断の前に、[共通のEvidence基準](../_shared/evidence.md)を読み、その基準に従う。

`AGENTS.md`・公式手順に従い、`docs/official/`、現行コード・設定、保存済みRUN、DuckDB基盤（`task q`）、読み取り専用SSHで調べる。RUNは指定がなければ最新finalizedを既定とする。

保存済みRUNの原文は上書きしない。調査・ベンチ実行とサーバー操作の制約は`AGENTS.md`に従う。改善中の計測維持も担当し、構成・状態管理・ログ形式を変えた場合は生成・回収・集計を一緒に更新する。診断に必要な情報が不足した場合は[setupの補修手順](../isucon-setup/SKILL.md#既存環境の計測補修)や[WAL構成の計測](../isucon-bootstrap/references/wal-measurement.md)を参照して必要な範囲を補い、初期対応へ戻ることを必須にしない。

## 自律改善と実行許可

実装・デプロイ・ベンチ実行・分析・採否判断まで自律的に進める。競技環境の改善に必要な配布、serviceの停止・再起動、DB・テーブルの破棄と再作成、スキーマ・配置変更、不要なコード・設定の削除は許可済みとして扱う。対象ホストと影響を確認し、正規のTaskfileと操作ロックを使う。公式ルール・正当性の要件は守る。

1. 現行の配布物・構成・保存済みRUNを確認して改善を始める。比較できる基準がなければ`task bench`で基準RUNを取得する。
2. 公式の得点計算と、得点機会が発生・進行・完了する条件を整理する。[Evidence基準](../_shared/evidence.md#仮説と結果の評価)に従い、保存済みRUNから件数・価値・損失のどこが制約されているかを調べ、改善仮説を立てる。
3. 検証する仮説を選び、比較に使うRUNと評価指標を決める。複数の候補がある場合は、得点への作用を比較し、選んだ仮説を他の有力候補より優先する理由を短く示す。変更によってシナリオの進み方や得点がどう変わると予測しているかを明確にする。原則として1回のRUNでは1つの改善仮説を検証する。同じ仮説の成立に必要な複数経路の変更は一体で扱い、変更規模だけを理由に分割しない。独立した改善仮説は原則として別RUNで評価する。
4. ローカルで修正し、必要なbuild・checkを通して変更単位でcommitする。対象と影響を確認して`task deploy-*`や`task db-recreate`等の正規経路で反映する。
5. `task bench`を実行する。配布物一致・service状態の検査を通し、失敗RUNも通常回収でfinalizeする。投入後に通信が失敗した場合は既存ジョブの状態を確認し、重複投入を避ける。
6. 結果原文・合否・スコア・artifact status・missingを確認する。`task artifacts-run`とDuckDBを使って基準RUNと比較し、[Evidence基準](../_shared/evidence.md#仮説と結果の評価)に従って処理、得点対象操作の進行、得点への作用を評価する。正当性の失敗や悪化は原因を調べ、修正または変更の取り消しを行い、必要なら再計測する。
7. 変更の採否と根拠に加え、[Evidence基準](../_shared/evidence.md#仮説と結果の評価)に従って今回の結果を候補の優先順位へどう反映し、次に何を選んだかを短く報告する。想定外の結果は[Evidence基準の分岐](../_shared/evidence.md#想定外の結果と停滞)で切り分け、原因の説明や次の選定が進まない場合は[診断工程](#診断工程)へ移る。一度の実装やベンチ完了で止まらず、依頼範囲内の改善を続ける。

## 診断工程

診断の責任と次の実験の選定はメインが持つ。狙った処理を改善しても得点機会が増えず理由を説明できない、原因が絞れず候補を比較できない、または得点が停滞したまま同じ前提の改善を繰り返している場合は、次の通常改善を選ぶ前に[診断手順](references/diagnosis.md)を読む。

得点が伸びない現象を競合する原因仮説で説明し、観測・実験で切り分ける。メインの見立てだけでは絞れない場合は、同手順の独立診断をサブエージェントへ依頼する。利用できない場合もメインで診断を続ける。

改善対象を選べる根拠が得られるか、仮説を区別する次の実験が決まったら、実装・計測へ進む。原因の確定を実装の必須条件にはしない。得点制約と改善の根拠が十分な場合は、そのまま改善を進め、診断の深掘りや独立診断を毎RUNの必須作業にしない。

## 報告と終了

ユーザーの停止指示、指定された目標・作業範囲の達成、時間・予算の上限、または権限・認証・外部障害など自力で解消できない阻害要因で終了する。改善候補が見つからないことを終了理由にしない。候補が尽きた場合も、既存の前提・未確定点を見直し、観測・分析を深めて新たな仮説を探し、実装・計測・評価を続ける。同じ失敗条件のまま再実行を繰り返さない。
